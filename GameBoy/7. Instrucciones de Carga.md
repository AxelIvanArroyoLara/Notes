Las **instrucciones de carga** se abrevian mediante `LD` y siempre tienen dos entradas: el destino en la izquierda y la fuente en la derecha. Se denominan de esta manera ya que tienen la capacidad de copiar y sobrescribir el valor original del destino, mientras que el de la fuente se conserva igual. 

Existe una gran cantidad de instrucciones de carga. Las más sencillas se encuentran en las posiciones 0x40 hasta 0x7F de la tabla (omitiendo 0x76); estas simplemente cargan el valor de un registro de 8 bits a otro sin modificar las banderas. Ahora bien, al ser posible hacer este procedimiento entre cada par de registros, se requiere del uso de un helper que disminuya todo esto a una sola operación.

![[Pasted image 20260721140512.png]]

Las columnas comenzando con 0x02 y 0x0A cargan valores que se encuentran en un registro de 16 bits hacia registros de 8; en ocasiones, modificando incluso la dirección (`HL+`).

![[Pasted image 20260721140831.png]]

Por su parte, ambas columnas 0x01 y 0x0E hacen algo diferente: utilizan valores inmediatos. En lugar de cargar un valor hacia o desde un registro, estos extraen el siguiente valor (de 8 o 16 bits) desde la RAM y lo cargan en el registro correspondiente. Esto se logra al leer los datos a los que apunta el `PC`, mismo que se incrementa a continuación. Para cargas de 16 bits, eso significa extraer dos veces y combinar los bytes obtenidos en un solo valor (con `fetch_u16`).

![[Pasted image 20260721141136.png]]

Ahora, la instrucción 0x08, es una con varios pasos. Primero obtiene el valor siguiente de 16 bits desde el `PC`, tratándolo como una dirección de memoria y almacenándolo en el registro `SP`.

![[Pasted image 20260721141319.png]]

Consiguientemente, las instrucciones `0xE0`, `0xF0`, `0xE2` y `0xF2`, todas toman un valor de 8 bits (extrayendo o desde el valor almacenado en `C`) y le suman `0xFF00` para obtener una nueva dirección de memoria. Después de eso, lo almacenan en el registro `A`.

![[Pasted image 20260721141632.png]]

Por último, se describen las instrucciones restantes. `0xEA` y `0xFA` hacen algo similar a `0x08`, extrayendo un valor de 16 bits y guardando en el mismo el valor de `A` (en lugar de `SP`). Por su parte `0xF9` solo copia el valor de `HL` a `SP`, mientras que `0xF8` lo hace al revés. 

![[Pasted image 20260721142011.png]]

Las instrucciones de carga tienen una importancia sumamente elevada. Muchas de ellas mantienen un comportamiento común, pero suelen requerir un acercamiento particular respecto a su implementación. Para ello, se aprovecharán los comportamientos de algunos helpers ya desarrollados previamente, al estos cubrir los comportamientos comunes entre estas funciones. En este caso, solo una de las `LD` modifican banderas, y además ya se tienen funciones como `set_r8` y `set_r16` que permiten almacenar valores dentro de registros.

---
## Carga de 8 bits

La gran mayoría de las instrucciones de carga utilizan transferencias entre registros de 8 bits; por ejemplo `0x41` o `LD B, C`. Hemos de recordar que durante una operación de carga, el registro fuente se encuentra en la derecha y el destino en la izquierda. Teniendo esto en cuenta, se asume que primero debe obtenerse el valor del registro `C` y almacenarlo en el `B`:

```
// In cpu/opcodes.rs

// LD B, C
// ----
fn ld_41(cpu: &mut Cpu) -> u8 {
    let val = cpu.get_r8(Regs::C);
    cpu.set_r8(Regs::B, val);
    1
}
```

Un detalle de interés se encuentra en el hecho de que existen un cierto número de instrucciones en las que nada ocurre, en las que tanto los registros de fuente como destino son los mismos. Estos, funcionalmente son lo mismo que las funciones `NOP`; por ejemplo, `0x40`:

```
// In cpu/opcodes.rs

// LD B, B
// ----
fn ld_40(_cpu: &mut Cpu) -> u8 {
    // Don't need to copy a value from a register to itself, do nothing
    1
}
```

Al ser instrucciones que se copian a sí mismas, pueden ser ignoradas; son consecuencia de los desarrolladores originales queriendo mantener la estructura de las tablas intacta.

![[Pasted image 20260804145423.png]]

A continuación, existen instrucciones que utilizan valores inmediatos, viéndose muy similares al patrón básico. Por ejemplo, `0x1E`:

```
// In cpu/opcodes.rs

// LD E, u8
// ----
fn ld_1e(cpu: &mut Cpu) -> u8 {
    let val = cpu.fetch();
    cpu.set_r8(Regs::E, val);
    2
}
```

En lugar de leer un valor desde un registro, se lee desde la RAM haciendo uso de `fetch`. Nótese que esta instrucción toma dos ciclos en lugar de uno.

## Carga de 16 bits

Ahora, las instrucciones para la carga de 16 bits. En el caso de `0x01` `LD BC, u16`, se necesita obtener un valor del tamaño especificado, igualmente desde la memoria RAM. Para esto se utiliza el helper `fetch_u16` (estas aun no han sido implementadas).

```
// In cpu/opcodes.rs

// LD BC, u16
// ----
fn ld_01(cpu: &mut Cpu) -> u8 {
    let val = cpu.fetch_u16();
    cpu.set_r16(Regs16::BC, val);
    3
}
```

La carga de un valor de 16 bits en memoria debe tratarse con especial cuidado; tómese de ejemplo la función `0x08` `LD (u16), SP`. El StackPointer es un valor de 16 bits, pero la función `write_ram` solo acepta cantidades `u8`. Por lo tanto, para lograr la carga correctamente, el valor de `SP` tiene que dividirse en 2 grupos, el low y high bytes como se ha descrito con anterioridad. Posteriormente, se guarda el low en la dirección especificada, y el high en una dirección consecutiva. 

```
// In cpu/opcodes.rs

// LD (u16), SP
// ----
fn ld_08(cpu: &mut Cpu) -> u8 {
    let addr = cpu.fetch_u16();
    let val = cpu.get_r16(Regs16::SP);
    cpu.write_ram(addr, val.low_byte());
    cpu.write_ram(addr + 1, val.high_byte());
    5
}
```

En adición a las implementaciones de 16 bits, existen algunas que no solo almacenan su valor en una dirección de memoria, sino que la incrementan al finalizar; por ejemplo `0x2A`:

```
// In cpu/opcodes.rs

// LD A, (HL+)
// ----
fn ld_2a(cpu: &mut Cpu) -> u8 {
    let addr = cpu.get_r16(Regs16::HL);
    let val = cpu.read_ram(addr);
    cpu.set_r8(Regs::A, val);
    cpu.set_r16(Regs16::HL, addr.wrapping_add(1));
    2
}
```

En esta instrucción existen dos detalles importantes a destacar. Primeramente, no se incrementa el valor en HL hasta después de que se utiliza como una dirección de memoria. En segundo lugar, Rust no añade overflow, por lo que se utiliza la ya antes descrita `wrapping_add`.

Los últimos tipos de instrucciones de carga que se van a tratar en el capítulo, son los que obtienen un valor y lo utilizan como offset para una dirección de memoria, como `0xE0`. Este suma el valor de `fetch` a `0xFF00` y posteriormente guarda el valor de `A` en esa dirección:

```
// In cpu/opcodes.rs

// LD (FF00+u8), A
// ----
fn ld_e0(cpu: &mut Cpu) -> u8 {
    let offset = cpu.fetch() as u16;
    let addr = 0xFF00 + offset;
    let val = cpu.get_r8(Regs::A);
    cpu.write_ram(addr, val);
    2
}
```

Por último, se tiene `0xF8` `LD HL, SP+i8`, que es un caso muy similar al anteriormente revisado, pero con una diferencia sustancial. El valor que se extraiga, tiene que ser tratado como un *signed byte*, lo que se muestra en el opcode en la forma de `i8` en lugar de `u8`. Esto, en otras palabras, significa que tendrá signo. Existe una manera para castear correctamente el valor para convertirlo a `i8`, sobretodo porque también debe castearse a `u16` previo a que Rust permita su adición al valor de `SP`:

```
// In cpu/opcodes.rs

// LD HL, SP+i8
// 00HC
fn ld_f8(cpu: &mut Cpu) -> u8 {
    let offset = cpu.fetch() as i8 as i16 as u16;
    let sp = cpu.get_r16(Regs16::SP);
    let set_c = check_c_carry_u8(sp.low_byte(), offset.low_byte());
    let set_h = check_h_carry_u8(sp.low_byte(), offset.low_byte());

    cpu.set_r16(Regs16::HL, offset.wrapping_add(sp));
    cpu.set_flag(Flags::Z, false);
    cpu.set_flag(Flags::N, false);
    cpu.set_flag(Flags::C, set_c);
    cpu.set_flag(Flags::H, set_h);
    3
}
```

Aquí, la conversión funciona de manera que se transforma el valor `u8` obtenido para interpretarlo como un valor con signo en `i8`, luego lo extiende a `i16` (representando al mismo número pero ahora en 16 bits) y finalmente reinterpretando para el `u16`. 

```
offset.wrapping_add(sp)
```

`sp` y `offset` son `u16`.

Pero `offset` viene de:

```
let offset = cpu.fetch() as i8 as i16 as u16;
```

Eso hace una extensión de signo. Por ejemplo, si el byte inmediato es `0xFE`:

```
0xFE como i8  = -2
-2 como i16   = -2
-2 como u16   = 0xFFFE
```

Entonces, si:

```
SP = 0xD000
offset = 0xFFFE
```

la suma modular es:

```
0xD000 + 0xFFFE = 0x1CFFE
```

Como `u16` solo conserva 16 bits:

```
HL = 0xCFFE
```

Eso equivale correctamente a:

```
0xD000 - 2 = 0xCFFE
```

`wrapping_add` permite que el resultado dé la vuelta cuando supera `0xFFFF`.

Para esta instrucción de Game Boy, `H` y `C` no se calculan observando toda la suma de 16 bits.

Se calculan como si se sumara:

```
byte bajo de SP + byte inmediato
```

Por eso se hace:

```
sp.low_byte()
offset.low_byte()
```

Supongamos:

```
SP = 0xD0F8
offset = +8
```

Sus bytes bajos son:

```
SP bajo     = 0xF8
offset bajo = 0x08
```

Entonces:

```
0xF8 + 0x08 = 0x100
```

Hay acarreo fuera del byte, por lo tanto:

```
C = 1
```

Para `H`, solo se observan los cuatro bits bajos:

```
0x8 + 0x8 = 0x10
```

Hay acarreo del bit 3 al bit 4:

```
H = 1
```

Mientras tanto, la suma completa sigue siendo:

```
0xD0F8 + 8 = 0xD100
```

Así que:

```
HL = 0xD100
H = 1
C = 1
```

## Introducción

A continuación se presenta la aplicación del **Object Query Language** (OQL); el lenguaje estándar ODMG para la gestión de bases de datos orientadas a objetos. De esta manera, el esquema de la base es declarado en un lenguaje de definición (ODL), el programa se escribe en un lenguaje anfitrión (dígase C++ o Java) y durante la ejecución, la aplicación interactúa con el motor DBMS para realizar las consultas, estando la base de datos no limitada a tablas, sino que se maneja naturalmente a través de *objetos* con identidad, estado y comportamiento propios, así como relaciones navegables entre ellos.

Conceptualmente, el flujo se realiza de la siguiente manera:

1. El desarrollador escribe el esquema ODL.
	
2. Se programa la aplicación mediante el lenguaje anfitrión, se compila y se enlaza. 
	
3. El ejecutable interactúa durante tiempo de ejecución con el ODBMS.
	

De tal suerte, que los datos junto con su manipulación, se encuentra integrada con el paradigma orientado a objetos en lugar del enfoque relacional clásico.

## Modelo de Base de Datos: Operaciones Fundamentales sobre una Object Database

Dentro de ODMG, una ***Object Database*** se define como la noción lógica que provee la *persistencia* para los objetos, mismos que se almacenan con una identidad y dirección persistente. Para ello, se genera la lista para las operaciones típicas que pueden hacerse sobre la base:

- `open(database_name)`: abre una base identificada por nombre.
    
- `close()`: cierra la base.
    
- `bind(object, name)`: asocia un objeto con un nombre (un “punto de entrada”).
    
- `unbind(name)`: elimina la asociación nombre→objeto.
    
- `lookup(name)`: encuentra el objeto asociado a un nombre.
    
- `schema()`: devuelve el esquema de la base.
    

Estas operaciones permiten introducir dos ideas que suelen aparecer con regularidad:

- En OODBMS, es común tener puntos de entrada con nombre (con nombres globales para objetos relevantes).
	
- Además de navegar desde nombres, también se tiene el concepto de *extent*: la colección de todas las instancias persistentes de una clase.

##### Ejemplo:

El ejemplo abre una base (`base1`), inicia una transacción, crea dos objetos `Person` (`P` y `T`), y luego los “publica” mediante `bind` con nombres (“Yves” y “Chairman”). Tras hacer `commit`, esos objetos quedan persistidos y pueden recuperarse:

- por el nombre: `lookup("Yves")` o usando el identificador del nombre en OQL,
    
- o por el extent de la clase `Person` (por ejemplo, consultando `Persons`, el conjunto de todas las personas persistentes).
    

En este caso, el `name` funciona a manera de "alias" de alto nivel para hallar los objetos especiales; por su parte, el `extent` funge como el universo consultable de todas las instancias de una clase, de manera similar a una tabla conceptual pero con objetos.

## Acceso a Metadatos: Clases como Instancias de Type

En ODMG, el **acceso a metadatos** señala que las *clases* (en forma de esquema) pueden ser definidas como instancias de un tipo meta conocido como `Type`, mismo que se modela como un subtipo de `Atomic_Object` y expone una serie de propiedades típicas para introspección:

- `has_operations`: conjunto de operaciones (métodos) del tipo.
    
- `has_properties`: conjunto de propiedades/atributos.
    
- `has_subtypes`: subtipos del tipo.
    
- `name`: nombre del tipo.
    
- `extent`: conjunto de instancias (colección de `Atomic_object`).
    
- `name_of_extent`: nombre del extent.
    

Además, `Type` ofrece operaciones útiles para manipulación dinámica:

- `create_instance(list(property: property_value))` para crear una instancia, devolviendo un objeto denotable.
    
- `create_extent(name)` para crear un extent con un nombre.
    

Gracias al uso de estas operaciones, el modelo permite no solo utilizar las *clases*, sino también *inspeccionarlas* y, en ciertos casos, crear instancias o colecciones más dinámicamente, apoyando herramientas y *frameworks* capaces de operar sobre el esquema.

## Concurrencia: *Locks* y Control de Acceso a Objetos

ODMG incorpora un control de **concurrencia** a través de bloqueos (*locks*) sobre objetos. A continuación se presentan tres tipos:

- `read` (compartido): múltiples lecturas concurrentes.
    
- `write` (exclusivo): acceso exclusivo para escritura.
    
- `upgrade` (intención de lectura o escritura).
    

Así bien, se distingue entre:

1. **Locks explícitos**, solicitados por el programador con `lock()` o `try_lock()`.
    
2. **Locks implícitos**, adquiridos automáticamente cuando se navega el “grafo de composición” del objeto (es decir, al seguir referencias/relaciones que forman parte de la estructura compuesta del objeto).
    

Se muestra una interfaz `Object` (a nivel de idea) que define el enum `Lock_Type` y la excepción `LockNotGranted`, además de las operaciones para solicitar el lock.

En OODBMS, al ser el acceso de manera navegacional, es decir, a partir de referencias, el sistema es capaz de inferir qué objetos están relacionados y, mediante ello, aplicar *locks* implícitos; sin embargo, se permite al desarrollador tomar el control de su manejo cuando sea necesario.

## Transacciones

Dentro del paradigma, todo *acceso*, *creación*, *modificación* y *eliminación* de objetos se lleva a cabo dentro de una **transacción** (concepto *ACID*). Ahora bien, para el modelo presentado:

- Las *transacciones distribuidas* no se consideran como norma, sino que una *transacción* corre como hilo dentro de un solo proceso.
	
- Si hay múltiples transacciones en un proceso, se debe asegurar la capacidad de aislamiento; existen operaciones para asociar y desacoplar transacciones respecto al hilo de control.
	
- Para escenarios multihilo, la validación ocurre cuando un hilo ejecuta un `commit`; pueden existir múltiples asociaciones de hilos a una misma transacción, y no hay *locks* entre ellos automáticamente, sino que el control de acceso al código recae sobre el programador.
	

### Operaciones típicas de `Transaction`:

Se listan operaciones:

- Creación y contexto: `new()`, `current()`.
    
- Control de ciclo de vida: `begin()`, `commit()` (libera locks), `abort()`.
    
- Puntos de control: `checkpoint()` (no libera locks).
    
- Asociación con hilos: `join()` (asocia al hilo actual), `leave()` (desasocia).
    
- Estado: `isOpen()`.
    

Si una aplicación abre una *transacción*, navega entre los objetos, modifica atributos y posteriormente ejecuta `commit`, se espera una consistencia y liberación de *locks*. En caso de que el flujo falle, `abort` revierte los efectos. El `checkpoint` funciona como un punto intermedio de seguridad sin soltar los *locks*, lo que resulta útil en operaciones largas en donde se desea un estado parcialmente asegurado.

## *Object Query Language* (OQL)

Ahora, se introduce al *Object Query Language*, OQL por sus siglas; un lenguaje con una sintaxis similar a SQL-2, pero diseñado para un enfoque capaz de retornar tanto *objetos* como *valores*, y que, además, permite navegar las relaciones entre los objetos (*paths*). Este lenguaje es declarativo, cualidad que lo vuelve optimizable. Así bien, las actualizaciones explícitas se hacen a través de *métodos* definidos dentro de los mismos *objetos*. Una de las más grandes ventajas del lenguaje, es su capacidad para integrarse de forma nativa con el lenguaje anfitrión.

##### Ejemplo:

Se define un `struct address` con `street`, `city`, `code`, y una clase `Person` con `extent Persons`, con atributos como `name`, `gender` (enum), `address`, `phones` (set), `birthdate`, y relaciones como:

- `spouse` (uno a uno) con inversa `Person::spouse`.
    
- `children` y `parents` (sets) con inversas cruzadas.
    

Además, `Person` define operaciones (métodos) como `age()`, `lives_in(string)`, `oldest_child()`, `activities()`.

![[Pasted image 20260226103324.png]]

Luego `Employee` extiende `Person` con su propio `extent Employees` y atributos (`hireDate`, `salary`, `deptno`) y una relación jerárquica `subordinates` con inversa `chef`, además de métodos como `seniority()`, `hire()`, `fire()` (con excepción), y redefinición de `activities()`. Se indica también que `Chairman` es un **name** que referencia un objeto de tipo `Person`.

## Expresiones OQL

Se muestran ejemplos de expresiones y el tipo del resultado:

- `2` → `short`
    
- `2 + 2` → `short`
    
- `Chairman` → `Person`
    
- `Persons` → `set<Person>`
    
- `Chairman.name` → `string`
    
- `Chairman.address.city` → `string`
    
- `Chairman.phones` → `set<string>`
    
- `Chairman.age` → `short`
    
- `nil` → `null`
    

Se destaca que OQL es un lenguaje *fuertemente tipado*, en donde cada consulta tiene un tipo particular de salida. Una consulta es capaz de devolver un objeto completo, una colección de objetos o valores escalares / estructurados.

## Construcción de Valores

OQL permite construir literales y colecciones:

- `struct(name: "Peter", age: 36)` construye una estructura.
    
- `set(3, 1, 2)` crea un conjunto (sin duplicados).
    
- `bag(3, 3, 1, 2, 2)` crea multiconjunto (permite repetidos).
    
- `list(1, 2, 3, 3)` crea lista (ordenada, repetidos permitidos).
    

Además, permite construir objetos:

- `Person(name: "Pat", birthdate: Date '1956-3-8')`
    
- `Employee(name: "Michel", salary: 30000)`
    

Esto permite destacar que OQL no solo es capaz de realizar consultas, sino que también puede ensamblar resultados complejos (dígase, estructuras de datos), lo que facilita la construcción de vistas o DTOs sin abandonar sus características como lenguaje de consulta.

---

## Consultas

Se muestran variantes:

1. `select p.age 
2. ``from Persons p`` 
3. ``where p.name = "Pat"``  
    retorna `bag<short>` (porque puede haber varios resultados y por defecto es bag).

O

1. `select distinct p.age 
2. ``from Persons p ``
3. ``where p.name = "Pat"``  
    retorna `set<short>` (distinct elimina duplicados, por tanto set).

Y
1.  ``select distinct struct(age: p.age, sex: p.gender)``
2. ``from Persons p`` 
3. ``where p.name = "Pat"`  
    retorna `set<struct(age: short, sex: gender)>`.
    

Aquí se ve una regla práctica: **distinct tiende a llevar resultados a set**, mientras que sin distinct se preserva la multiplicidad y se retorna bag.

---

## Objetos y Valores

Los resultados obtenidos pueden entrar en una de dos categorías principales:

- **Objetos:** Por ejemplo `Chairman`, o `element(select p from Person p where p.name="Pat")` cuando se fuerza a extraer un único elemento.
	
- **Valores:** Como literales o colecciones.
	

##### Ejemplos:

- `select distinct p.name from Persons p` → `set(string)`
    
- `select [distinct] p.name from Persons p order by p.name` → `list(string)`
    
- `select t from Persons t order by *` → `list(Person)`
    

La propiedad `order by` induce una lista, porque el resultado ordenado implica secuencia.

## Formato general de select y “paths” (navegación)

Se resume el formato:

`select ... from ... [where ...]` donde el `from` toma **entry points**, que pueden ser nombres (como `Chairman`), extents (como `Persons`) o incluso resultados de subconsultas.

### Paths

Los “paths” son navegación:

- Atributo simple: `select e.salary from Employees e` → `bag<float>`
    
- A través de relación: `select p.spouse.address.city from Persons p` → `bag<string>`
    
- Usando paths en el `from`: `select distinct c.address from Persons p, p.Children c` → `set<Address>`
    

**Nota conceptual:** el uso de `from Persons p, p.Children c` expresa una navegación tipo join, pero desde una relación de objetos (children) en vez de una condición sobre claves externas.

---

## Construcción de valores complejos dentro de select

Se muestra un ejemplo que construye un `struct` con un subresultado:

Se selecciona un `struct(name: e.name, hps: (subconsulta))` donde la subconsulta obtiene subordinados con salario alto. El resultado es:

`set<struct(name: string, hps: bag<Employee>)>`

**Interpretación:** OQL facilita producir resultados “anidados” (por ejemplo, para cada empleado, incluir un conjunto de subordinados filtrados) sin necesidad de múltiples pasos en el lenguaje anfitrión.

---

## From con subconsulta y alias

Ejemplo:

`from (select e from Employees e where e.seniority="10") as x`  
y luego se consulta sobre `x`. Se retorna una `bag<struct(...)>`.

**Idea clave:** el `from` puede alimentarse con resultados intermedios, como en SQL con subqueries, pero manteniendo tipos orientados a objetos.

---

## From: join (estilo relacional sobre objetos)

Se ejemplifica:

Dado `Flowers: set<Person>`, se hace:

`select p from Persons p, Flowers f where f.name = p.name` → `bag<Person>`

Aunque se está en un mundo de objetos, OQL sigue permitiendo joins por condiciones, lo cual es útil cuando no existe una relación explícita ya modelada (o cuando se requiere correlación por valores).

---

## Predicados y operadores agregados

Se muestran predicados con condiciones múltiples y agregados:

- Uso de navegación `p.children c`
    
- Comparación de strings
    
- `count(p.children) >= 2`
    
- Comparaciones entre ciudades del hijo y del padre
    
- Chequeo contra `nil` y condiciones sobre atributos anidados (`p.address.city = "Paris"`).
    

**Lectura conceptual:** el where combina lógica booleana, agregados y navegación, permitiendo expresar restricciones semánticas directamente sobre el grafo de objetos.

---

## Valores indefinidos: UNDEFINED, is_defined e is_undefined

Un punto importante en OQL es el manejo de valores indefinidos (por ejemplo, cuando una parte del path no existe). Se muestran casos:

- Consultar `e.address.city` para empleados puede dar una bolsa con valores como `"Puebla"`, `"Cholula"` y `UNDEFINED` si algún empleado no tiene dirección definida.
    
- Para filtrar, existe `is_defined(e.address.city)` o, inversamente, `is_undefined(e.address.city)`.
    

También se ilustra una sutileza lógica:

- `where is_undefined(e.address.city)` devuelve empleados sin dirección.
    
- `where not(e.address.city = "Paris")` devuelve empleados que no viven en París, lo cual **no es lo mismo**: incluye a quienes no tienen ciudad definida y a quienes sí la tienen pero es diferente.
    

**Ejemplo explicativo (intuición):** si una condición compara con “Paris”, un valor indefinido no puede evaluarse igual que “no es Paris” sin aclarar la semántica. Por eso ODMG expone predicados explícitos para “definido/indefinido”.

---

## Operadores útiles en OQL

Se listan operadores típicos:

- Agregados: `count`, `min`, `max`, `sum`, `avg`.
    
- `element`: extrae el único elemento de un set (cuando se espera cardinalidad 1).
    
- Transformaciones: `listtoset`, `flatten`.
    
- Cuantificadores: `for all` (universal), `exists` (existencial).
    
- `like`: comparación de cadenas.
    
- `define`: nombrar resultados de consulta.
    
- Operaciones de conjuntos: `union`, `intersect`, `except`.
    
- Pertenencia: `in` (por ejemplo, `Chairman in Persons`).
    

**Idea clave:** OQL mezcla lo mejor de SQL (agregados, group by, order by) con construcciones propias para colecciones y objetos.

---

## Consultas usando métodos (comportamiento dentro de la consulta)

Se muestra que OQL puede invocar métodos del esquema:

- `select max(select c.age from p.children c) from Persons p where p.name="Charles"` → `set<short>`
    
- `select p.oldest_child.address.street from persons p where p.lives_in("Grenoble")` → `bag<string>`
    
- `select p.activities from Persons p` → `bag<set<string>>`
    

Aquí se aprecia el valor de tener comportamiento en el modelo: operaciones como `lives_in` o `oldest_child` encapsulan lógica, y la consulta las reutiliza.

## Abreviaciones estilo SQL

Se presentan abreviaciones sintácticas:

- `select p: name, salary, section_id from Professors p, p.teaches`
    
- `select * from Persons p`
    
- `select count(*) from ...` equivalente a `count(select * from ...)`
    

Estas abreviaciones hacen OQL familiar para quien viene de SQL, pero el resultado sigue siendo típicamente un `bag<struct(...)>` o colecciones de structs/objetos, no “filas” en sentido relacional puro.

---

## Group by y Having en OQL

Se muestran formas de agrupar:

- `select * from Persons p group by p.age` produce structs con `age` y una `partition` (una bolsa con los elementos del grupo).
    
- `select age, persons_num: count(partition) ... group by p.age` produce conteos por edad.
    
- `select city, partition: (select t.p from partition t) ... group by p.address.city` agrupa por ciudad.
    

Con `having`, se filtran grupos, por ejemplo:

- ciudades con más de 10000 personas,
    
- departamentos con salario promedio mayor a 30000.
    

**Interpretación:** `partition` es el concepto clave: al agrupar, se genera una partición (colección) por grupo sobre la que pueden correr subconsultas o agregados.

---

## Define: nombrar consultas

`define` permite guardar una consulta con un nombre (como una vista o variable consultable):

- `define Q1 as element(select c from Persons c where c.name="Yohan")`
    
- `Q1`
    
- `define Q2 as select e from Employees e where e.salary > 50000`
    

Esto facilita componer consultas complejas y reutilizar resultados sin repetir expresiones.

---

## Order by y tipos de salida

Se muestran ejemplos de ordenamiento:

- `select p from Persons p order by p.name` → `list<Person>`
    
- `select p from Employees p order by p.age desc, p.name asc, p.salary` → `list<Person>`
    
- `select t.name from t in Q2 order by *` → `list<string>`
    

**Regla práctica:** ordenar transforma el resultado en lista, y se puede ordenar por múltiples claves con direcciones asc/desc.

## Síntesis conceptual de lo esencial en esta parte

En esta “tercera parte” el mensaje principal es que un OODBMS (en ODMG) integra:

1. **Persistencia de objetos** con identidad y puntos de entrada (nombres) además de extents.
    
2. **Transacciones y locks** para controlar concurrencia y garantizar propiedades ACID, con particularidades al trabajar con threads.
    
3. **OQL** como lenguaje declarativo tipado, capaz de:
    
    - navegar paths de objetos y relaciones,
        
    - construir resultados complejos (structs, colecciones anidadas),
        
    - manejar indefinidos explícitamente (`is_defined/is_undefined`),
        
    - usar agregados, `group by`, `having`, `order by`,
        
    - e invocar métodos definidos en el esquema.

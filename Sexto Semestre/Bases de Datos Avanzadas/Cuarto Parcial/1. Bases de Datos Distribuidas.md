## Introducción general

Las bases de datos distribuidas surgen como respuesta a la necesidad de administrar información que no se encuentra físicamente concentrada en un único lugar, sino repartida entre varios sitios conectados mediante una red. Esta distribución puede responder a razones organizacionales, técnicas, geográficas o de rendimiento. En lugar de obligar a que todos los datos residan en un solo servidor central, un sistema distribuido permite que diferentes nodos almacenen, procesen y compartan partes de una misma base de datos lógica.

El objetivo principal de un sistema de bases de datos distribuidas es que, aunque los datos estén físicamente separados, el usuario pueda trabajar con ellos como si pertenecieran a una sola base de datos integrada. Para lograr esto, el sistema debe ocultar varios detalles internos, como la ubicación real de los datos, la existencia de réplicas, la forma en que las relaciones están fragmentadas y la coordinación entre sitios.

---

## Sistema centralizado

Un sistema centralizado concentra el procesamiento, el almacenamiento y la administración de datos en una sola ubicación principal. En este tipo de arquitectura, existe un conjunto central de recursos de hardware y software que atiende las solicitudes de múltiples terminales.

La estructura típica de un sistema centralizado incluye un sistema operativo, software de aplicación, programas de aplicación, editores de texto, compiladores, un sistema gestor de bases de datos, controladores de terminales, dispositivos de entrada/salida en disco, impresoras, CPU, memoria, controladores y un bus de comunicación interno.

Las terminales conectadas al sistema no realizan procesamiento autónomo importante; funcionan principalmente como puntos de entrada y salida. El procesamiento real ocurre en la máquina central. Por eso, si el sistema central falla, el funcionamiento completo puede verse afectado.

En este modelo, el DBMS reside en el sistema central y controla directamente el acceso a los datos. Las aplicaciones, los compiladores y otros programas interactúan con los recursos centralizados. Esto simplifica la administración, pero también limita la escalabilidad y puede generar cuellos de botella.

## Arquitectura cliente / servidor

### Concepto general

La arquitectura cliente / servidor separa las responsabilidades entre máquinas cliente y servidores especializados. Los clientes ejecutan aplicaciones o interfaces de usuario, mientras que los servidores ofrecen servicios específicos, como impresión, archivos o administración de bases de datos.

En este modelo pueden existir varios clientes conectados mediante una red a diferentes tipos de servidores, por ejemplo:

- Servidor de impresión.
    
- Servidor de archivos.
    
- Servidor DBMS.
    
- Clientes distribuidos en diferentes sitios.
    

A diferencia del sistema centralizado, aquí los clientes pueden tener cierta capacidad de procesamiento local. La red conecta a los clientes con los servidores, permitiendo que cada servidor se especialice en una función determinada.

### Arquitectura cliente / servidor distribuida

En una arquitectura cliente / servidor distribuida pueden existir varios sitios. Algunos sitios funcionan como clientes, otros como servidores y otros pueden combinar ambos roles. La comunicación entre sitios ocurre mediante una red.

Por ejemplo, puede existir un Sitio 1 con un cliente, un Sitio 2 con otro cliente, un Sitio 3 con un servidor, y un Sitio N con cliente y servidor. Todos estos componentes se comunican mediante una red de comunicación.

![[Pasted image 20260506171200.png]]

### Arquitectura cliente / servidor en bases de datos relacionales

En bases de datos relacionales, la arquitectura cliente / servidor suele organizarse de la siguiente manera:

**Servidor:** conserva las consultas y transacciones del lado de la base de datos. Esto significa que las operaciones centrales de acceso, actualización, control de concurrencia y procesamiento de datos se ejecutan en el servidor DBMS.

**Cliente:** ejecuta las aplicaciones. El usuario interactúa con la aplicación cliente, pero las operaciones de consulta y transacción se envían al servidor de bases de datos.

Para conectar las aplicaciones cliente con el DBMS se utilizan mecanismos estándar de conectividad, entre ellos:

**ODBC:** Open Database Connectivity. Es una interfaz estándar que permite que una aplicación se conecte a diferentes sistemas gestores de bases de datos usando controladores.

**JDBC:** Java Database Connectivity. Es una API utilizada en aplicaciones Java para conectarse y ejecutar operaciones sobre bases de datos.

Este esquema permite separar la lógica de presentación o aplicación de la lógica de administración de datos.

### Arquitectura cliente / servidor en bases de datos orientadas a objetos

En bases de datos orientadas a objetos, la interacción cliente / servidor suele ser más estrecha o acoplada. Esto se debe a que algunos módulos del DBMS pueden residir directamente en el cliente.

En este caso, las responsabilidades se dividen así:

**Lado del servidor:** contiene módulos de almacenamiento, control de concurrencia, recuperación, buffer y caché. Además, proporciona datos al cliente en forma de páginas de disco.

**Lado del cliente:** contiene módulos de interfaz, catálogo y optimización de consultas. La interacción se realiza mediante un lenguaje anfitrión o _host language_.

Esto significa que el cliente no es solamente una interfaz pasiva. Puede participar en tareas internas del DBMS, como optimizar consultas o manejar información del catálogo.

## Distributed DBMS o DDBMS

Un sistema gestor de bases de datos distribuidas, o DDBMS, surge al integrar dos áreas principales:

**Tecnología de bases de datos:** incluye modelos de datos, consultas, transacciones, recuperación, concurrencia, integridad y administración de información.

**Tecnología de redes y comunicación de datos:** incluye sistemas operativos distribuidos, comunicación entre nodos, transferencia de datos y coordinación entre sitios.

Las aplicaciones que utilizan DDBMS suelen tener dos intereses principales:

**Descentralizar procesos a nivel de sistema:** esto permite que distintas partes del procesamiento se realicen en diferentes sitios, reduciendo la dependencia de una sola máquina central.

**Integrar fuentes de información a nivel lógico:** aunque los datos estén repartidos físicamente, se busca que formen parte de una misma base de datos lógica.

Por esta razón, muchas aplicaciones adoptan una estrategia de desarrollo basada en DDBMS con arquitectura cliente / servidor.

## Conceptos de bases de datos distribuidas

### Sistema de cómputo distribuido

Un sistema de cómputo distribuido está formado por un conjunto de elementos de procesamiento que cooperan para realizar tareas asignadas. Estos elementos no necesariamente son homogéneos; pueden tener distinto hardware, distinto sistema operativo o distintas capacidades de procesamiento.

Un sistema distribuido cumple tres condiciones esenciales:

**Tiene varios elementos de procesamiento:** no depende de una sola unidad central.

**Los elementos están interconectados mediante una red de computadoras:** la comunicación entre nodos ocurre a través de enlaces de red.

**Los elementos cooperan para realizar tareas asignadas:** los nodos no trabajan de manera aislada, sino coordinada.

La idea central es que el sistema completo funcione como una unidad coordinada, aunque internamente esté compuesto por varios nodos independientes.

### Base de datos distribuida

Una base de datos distribuida puede definirse como una colección de múltiples bases de datos lógicamente interrelacionadas y distribuidas sobre una red de computadoras.

La palabra clave es “lógicamente”. Aunque los datos estén físicamente repartidos entre varios sitios, desde el punto de vista conceptual forman parte de una sola base de datos. Las distintas partes están relacionadas y deben poder consultarse, integrarse y reconstruirse cuando sea necesario.

Por ejemplo, una empresa con oficinas en diferentes ciudades podría almacenar datos de empleados, proyectos y departamentos en servidores locales. Sin embargo, desde el punto de vista global, todos esos datos pertenecen a la misma organización y deben poder consultarse de manera integrada.

### DDBMS

Un DDBMS se define como un sistema de software que administra una base de datos distribuida mientras hace que la distribución sea transparente para el usuario.

Esto significa que el usuario no debería preocuparse por detalles como:

- En qué sitio está almacenado un fragmento.
    
- Si existen réplicas de un dato.
    
- Cómo se reconstruye una relación fragmentada.
    
- Qué nodos participan en una consulta.
    
- Qué comunicación ocurre entre sitios.
    
- Cómo se recupera el sistema ante una falla parcial.
    

El DDBMS se encarga de ocultar esos detalles y ofrecer una visión integrada de la base de datos.

## Paralelismo vs. distribución

Aunque los sistemas paralelos y los sistemas distribuidos pueden parecer similares porque ambos involucran múltiples procesadores, no son equivalentes.

### Arquitecturas multiprocesador

Existen varios tipos de arquitecturas de sistemas multiprocesador. Dos de las más importantes son:

### Arquitectura de memoria compartida

La arquitectura de memoria compartida, también llamada _tightly coupled architecture_, consiste en múltiples procesadores que comparten tanto el almacenamiento secundario como la memoria primaria.

En este modelo, todos los procesadores acceden a la misma memoria principal y al mismo almacenamiento en disco. Este tipo de arquitectura es común en sistemas paralelos de bases de datos.

Su característica principal es el acoplamiento fuerte entre procesadores, ya que todos dependen de recursos compartidos.

### Arquitectura de disco compartido

La arquitectura de disco compartido, también llamada _loosely coupled architecture_, consiste en múltiples procesadores que comparten el almacenamiento secundario, pero cada uno tiene su propia memoria primaria.

En este caso, los nodos pueden ser simétricos y homogéneos. Todos acceden a los mismos discos, pero cada uno administra su propia memoria.

Esta arquitectura tiene menor acoplamiento que la de memoria compartida.

### Diferencia con los DDBMS

Los sistemas DDBMS comúnmente están compuestos por nodos con hardware y sistemas operativos heterogéneos. Esto significa que no necesariamente todos los sitios tienen las mismas características técnicas.

La distribución no solo implica tener varios procesadores; implica también que los datos están repartidos a través de una red, que los nodos pueden ser diferentes y que el sistema debe coordinar consultas, transacciones, réplicas, fallos y seguridad entre sitios.

Por eso, el paralelismo se enfoca más en acelerar el procesamiento mediante múltiples procesadores, mientras que la distribución se enfoca en administrar datos localizados en diferentes sitios de una red.

## Ventajas de los DDBMS

### Administración de datos distribuidos con transparencia

Una de las ventajas principales de un DDBMS es la administración de datos distribuidos mediante diferentes niveles de transparencia. La transparencia busca dar al usuario la impresión de estar trabajando con un sistema centralizado, aunque internamente exista distribución.

Los tipos de transparencia más importantes son:

### Transparencia de distribución o de red

La transparencia de distribución, también conocida como transparencia de red, permite ocultar la ubicación física de los datos. El usuario no necesita saber en qué sitio se encuentra una tabla, fragmento o réplica.

Incluye dos aspectos importantes:

**Transparencia de ubicación:** el usuario puede acceder a los datos sin indicar explícitamente el sitio donde están almacenados.

**Transparencia de nombres:** los objetos de la base de datos pueden referenciarse de forma uniforme, sin necesidad de incluir detalles físicos de red.

### Transparencia de replicación

La transparencia de replicación oculta al usuario la existencia de múltiples copias de un mismo dato. Si una relación o fragmento está replicado en varios sitios, el DDBMS decide qué copia utilizar.

La replicación mejora:

**Disponibilidad:** si un sitio falla, puede accederse a otra copia.

**Rendimiento:** una consulta puede atenderse desde una réplica cercana.

**Confiabilidad:** la existencia de varias copias reduce el riesgo de pérdida o inaccesibilidad de datos.

### Transparencia de fragmentación

La transparencia de fragmentación oculta el hecho de que una relación está dividida en partes. El usuario consulta la relación como si estuviera completa, mientras el DDBMS se encarga de acceder a los fragmentos necesarios y reconstruir los resultados.

La fragmentación puede ser:

**Horizontal:** división por tuplas o filas.

**Vertical:** división por atributos o columnas.

### Confiabilidad y disponibilidad

Los DDBMS pueden aumentar la confiabilidad y disponibilidad del sistema.

**Confiabilidad:** se define de manera amplia como la probabilidad de que un sistema esté funcionando, es decir, que no esté caído, en un punto específico del tiempo.

**Disponibilidad:** se define como la probabilidad de que un sistema esté continuamente disponible durante un intervalo de tiempo.

La diferencia entre ambas es importante. La confiabilidad observa si el sistema funciona en un momento específico. La disponibilidad observa si el sistema se mantiene funcionando durante un periodo continuo.

Un DDBMS puede mejorar ambas porque no depende necesariamente de un solo sitio. Si un nodo falla, otros nodos pueden seguir funcionando o proporcionar copias de ciertos datos.

### Mejor rendimiento

Un DDBMS puede mejorar el rendimiento al fragmentar la base de datos y mantener los datos cerca del lugar donde más se necesitan.

Por ejemplo, si una oficina regional consulta principalmente los datos de sus propios empleados, esos datos pueden almacenarse localmente en esa oficina. Así se reduce la comunicación remota y se mejora el tiempo de respuesta.

También puede lograrse paralelismo en consultas:

**Inter-query parallelism:** se ejecutan varias consultas al mismo tiempo en diferentes sitios.

**Intra-query parallelism:** una sola consulta se divide en partes que se ejecutan en paralelo en distintos sitios.

Cuando hay un número pequeño de transacciones, esta ejecución paralela puede mejorar el rendimiento porque aprovecha varios nodos simultáneamente.

### Expansión más sencilla

Los DDBMS permiten una expansión más flexible en dos sentidos:

**Agregar más datos:** se puede incrementar el tamaño de la base de datos distribuyendo nuevos fragmentos o relaciones entre sitios.

**Agregar más procesadores o nuevos sitios:** se pueden incorporar nodos adicionales a la red.

Esta capacidad de expansión impacta las características que deben proporcionar tanto el sistema operativo como el DBMS. El sistema debe ser capaz de coordinar más nodos, más datos, más comunicación, más transacciones distribuidas y posiblemente más fallos parciales.

## Características adicionales requeridas por un DDBMS

Un DDBMS necesita capacidades adicionales que no siempre son necesarias en un DBMS centralizado tradicional.

### Seguimiento de datos

El sistema debe tener la capacidad de rastrear la distribución, fragmentación y replicación de los datos. Para ello, el catálogo del DDBMS debe expandirse.

El catálogo no solo debe almacenar información común, como nombres de tablas, atributos, restricciones e índices, sino también información distribuida, por ejemplo:

- Qué fragmentos existen.
    
- En qué sitio se encuentra cada fragmento.
    
- Qué fragmentos están replicados.
    
- En qué sitios existen copias.
    
- Cómo se reconstruye una relación global.
    
- Qué políticas de acceso se aplican.
    

Sin esta información, el DDBMS no podría resolver consultas distribuidas correctamente.

### Procesamiento distribuido de consultas

El DDBMS debe tener la capacidad de acceder a sitios remotos y transmitir consultas y datos entre sitios.

Esto significa que una consulta puede requerir:

- Identificar qué fragmentos contienen los datos necesarios.
    
- Enviar subconsultas a otros nodos.
    
- Recibir resultados parciales.
    
- Combinar resultados.
    
- Reducir costos de transferencia de datos.
    
- Decidir dónde ejecutar cada parte de la consulta.
    

El procesamiento distribuido de consultas es más complejo que el procesamiento centralizado porque el costo no depende solo de CPU y disco, sino también del costo de comunicación en red.

### Administración distribuida de transacciones

El sistema debe diseñar estrategias de ejecución para consultas y transacciones que acceden a datos de más de un sitio.

Una transacción distribuida puede modificar datos en varios nodos. Por eso el DDBMS debe garantizar que la transacción mantenga las propiedades de integridad de la base de datos completa.

También debe sincronizar el acceso a datos distribuidos para evitar inconsistencias. Por ejemplo, si dos usuarios actualizan datos relacionados en sitios distintos, el sistema debe coordinar esas operaciones para evitar conflictos.

### Administración de datos replicados

Cuando un dato está replicado, el DDBMS debe decidir qué copia utilizar para lectura y cómo mantener consistentes todas las copias.

Esto implica resolver preguntas como:

- ¿Qué réplica se consulta?
    
- ¿Todas las réplicas se actualizan inmediatamente?
    
- ¿Se permite que algunas copias se actualicen después?
    
- ¿Qué ocurre si una réplica no está disponible?
    
- ¿Cómo se detectan y resuelven inconsistencias?
    

La replicación mejora disponibilidad y rendimiento, pero también aumenta la complejidad de actualización, concurrencia y recuperación.

### Recuperación de bases de datos distribuidas

Un DDBMS debe recuperarse no solo de fallas locales, sino también de nuevos tipos de fallas propias de sistemas distribuidos.

Entre estas fallas se encuentran:

**Caídas de sitios individuales:** un nodo puede dejar de funcionar mientras los demás continúan activos.

**Fallas de enlaces de comunicación:** la red puede interrumpirse entre ciertos sitios, aunque los nodos sigan funcionando.

Estas fallas son más complejas que una caída total, porque el sistema puede quedar parcialmente activo. Algunos nodos pueden creer que otros están caídos cuando en realidad solo existe un problema de comunicación.

La recuperación distribuida debe asegurar que la base de datos global conserve su integridad.

### Seguridad

Las transacciones distribuidas deben ejecutarse con una administración adecuada de seguridad, datos y privilegios de autorización/acceso de los usuarios.

En un DDBMS, la seguridad es más compleja porque los datos pueden encontrarse en diferentes sitios y los usuarios pueden acceder desde distintos puntos de la red.

El sistema debe controlar:

- Autenticación de usuarios.
    
- Autorización de operaciones.
    
- Privilegios locales y globales.
    
- Protección durante la transmisión de datos.
    
- Acceso a réplicas.
    
- Acceso a fragmentos específicos.
    

Una política de seguridad distribuida debe ser coherente en todos los sitios participantes.

### Administración distribuida del directorio o catálogo

El directorio o catálogo contiene metadatos necesarios para administrar la base de datos distribuida.

La ubicación y distribución del directorio son decisiones de diseño y política. El catálogo puede ser:

**Local:** cada sitio conserva información sobre sus propios datos.

**Global:** existe una visión completa de toda la base de datos distribuida.

**Distribuido:** la información del catálogo también se reparte entre sitios.

**Replicado:** se mantienen copias del catálogo en varios nodos.

La decisión afecta rendimiento, disponibilidad, seguridad y complejidad de mantenimiento.

## Diseño de bases de datos distribuidas

El diseño de una base de datos distribuida define cómo se divide, replica y asigna la información entre distintos sitios.

Los conceptos principales son:

- Fragmentación de datos.
    
- Fragmentación horizontal.
    
- Fragmentación vertical.
    
- Fragmentación híbrida.
    
- Esquema de fragmentación.
    
- Esquema de asignación.
    
- Replicación.
    
- Asignación de fragmentos o copias a sitios.
    

---

## Fragmentación de datos

La fragmentación consiste en dividir una relación en partes más pequeñas llamadas fragmentos. Estos fragmentos pueden almacenarse en diferentes sitios del DDBMS.

La fragmentación tiene como objetivo colocar los datos cerca de donde se utilizan, mejorar rendimiento, aumentar disponibilidad y facilitar la administración local.

Existen tres tipos principales de fragmentación:

### Fragmentación horizontal

La fragmentación horizontal divide una relación en subconjuntos de tuplas. Es decir, separa filas de la tabla.

Cada fragmento horizontal se especifica mediante una condición sobre uno o más atributos.

Por ejemplo, si se tiene una relación EMPLOYEE, puede fragmentarse por número de departamento:

- Empleados con `Dno = 5`.
    
- Empleados con `Dno = 4`.
    
- Empleados con `Dno = 1`.
    

Cada fragmento conserva todos los atributos de la relación original, pero solo algunas filas.

### Fragmentación vertical

La fragmentación vertical divide una relación en subconjuntos de atributos. Es decir, separa columnas de la tabla.

Cada sitio puede no necesitar todos los atributos de una relación. Por eso se pueden almacenar distintos grupos de columnas en distintos sitios.

Por ejemplo, una oficina puede necesitar datos personales de empleados, mientras otra necesita datos salariales y de administración.

Para que la relación pueda reconstruirse, los fragmentos verticales suelen compartir la clave primaria.

### Fragmentación híbrida

La fragmentación híbrida combina fragmentación horizontal y vertical.

Primero puede dividirse una relación por filas y luego cada subconjunto dividirse por columnas, o al revés.

Este tipo de fragmentación permite un diseño más flexible, pero también aumenta la complejidad de reconstrucción y administración.

## Esquema de ejemplo

Para ejemplificar la fragmentación se utiliza el siguiente esquema relacional:

```text
DEPARTMENT( Dno, Dname, MgrSsn )

PROJECT( Pno, Pname, Ploc, Dno )

EMPLOYEE( Ssn, Name, Sex, Bdate, Address,
          Salary, MgrSsn, Dno )
```

La relación `DEPARTMENT` contiene información de departamentos:

**Dno:** número de departamento.

**Dname:** nombre del departamento.

**MgrSsn:** número de seguro social del gerente del departamento.

La relación `PROJECT` contiene información de proyectos:

**Pno:** número de proyecto.

**Pname:** nombre del proyecto.

**Ploc:** ubicación del proyecto.

**Dno:** número de departamento asociado.

La relación `EMPLOYEE` contiene información de empleados:

**Ssn:** número de seguro social del empleado.

**Name:** nombre.

**Sex:** sexo.

**Bdate:** fecha de nacimiento.

**Address:** dirección.

**Salary:** salario.

**MgrSsn:** número de seguro social del gerente.

**Dno:** número de departamento al que pertenece.

## Fragmentación horizontal

### Fragmentación horizontal completa

Una fragmentación horizontal completa es un conjunto de fragmentos horizontales cuyas condiciones $C_1, C_2, ..., C_n$ incluyen todas las tuplas de una relación $R$.

Esto significa que cada tupla de la relación original debe aparecer en al menos uno de los fragmentos. Cada grupo debe tener algún significado lógico.

Por ejemplo, si todos los empleados pertenecen a los departamentos 1, 4 o 5, entonces una fragmentación por esas condiciones podría cubrir toda la relación:

```text
Dno = 1
Dno = 4
Dno = 5
```

Cada condición define un grupo con significado lógico: empleados del departamento 1, empleados del departamento 4 y empleados del departamento 5.

### Fragmentación horizontal completa y disjunta

Una fragmentación horizontal es completa y disjunta si no existen tuplas en $R$ que satisfagan simultáneamente $C_i$ y $C_j$ para todo $i \ne j$.

Esto significa que una misma tupla no debe pertenecer a dos fragmentos al mismo tiempo.

Por ejemplo, si un empleado solo puede pertenecer a un departamento, entonces las condiciones `Dno = 1`, `Dno = 4` y `Dno = 5` son disjuntas entre sí.

### Reconstrucción de una relación fragmentada horizontalmente

Para reconstruir la relación original $R$ a partir de fragmentos horizontales, se aplica la operación `UNION`.

Si los fragmentos son $R_1, R_2, ..., R_n$, entonces:

$$  
R = R_1 \cup R_2 \cup ... \cup R_n  
$$

La unión funciona porque todos los fragmentos horizontales conservan la misma estructura de atributos, pero contienen diferentes tuplas.

## Fragmentación vertical

### Fragmentación vertical completa

Una fragmentación vertical completa es un conjunto de fragmentos verticales cuyas listas de atributos $L_1, L_2, ..., L_n$ incluyen todos los atributos de la relación $R$, pero comparten únicamente la clave primaria de $R$.

Esto permite que cada fragmento conserve una parte de las columnas de la relación, manteniendo una clave común para poder reconstruirla.

### Condiciones de fragmentación vertical

Las condiciones formales son:

$$  
L_1 \cup L_2 \cup ... \cup L_n = ATTRS(R)  
$$

Esto significa que la unión de todas las listas de atributos debe contener todos los atributos de la relación original.

También debe cumplirse:

$$  
L_i \cap L_j = PK(R) \quad \text{para cualquier } i \ne j  
$$

donde $PK(R)$ es la clave primaria de la relación.

Esto significa que la intersección entre dos fragmentos verticales debe ser solamente la clave primaria. Así se evita duplicar atributos no necesarios y se conserva la posibilidad de reconstrucción.

### Reconstrucción de una relación fragmentada verticalmente

Para reconstruir la relación $R$ a partir de fragmentos verticales, se aplica la operación `FULL OUTER JOIN`.

Esta operación se usa incluso cuando también se ha aplicado alguna fragmentación horizontal.

Si los fragmentos verticales son $R_1, R_2, ..., R_n$, se reconstruyen combinándolos por su clave primaria.

La necesidad de compartir la clave primaria es fundamental porque permite identificar qué partes de distintos fragmentos corresponden a la misma tupla original.

---

## Ejemplos de fragmentación

### Fragmentación horizontal primaria

La fragmentación horizontal primaria crea fragmentos directamente sobre una relación usando predicados definidos sobre sus atributos.

Por ejemplo, se pueden crear tres fragmentos de `EMPLOYEE` y `PROJECT` usando los predicados:

```text
Dno = 5
Dno = 4
Dno = 1
```

En el caso de `EMPLOYEE`, esto separa empleados por departamento.

En el caso de `PROJECT`, esto separa proyectos por departamento.

La fragmentación primaria depende directamente de condiciones aplicadas sobre la relación que se fragmenta.

### Fragmentación horizontal derivada

La fragmentación horizontal derivada aplica un predicado usando una fragmentación horizontal primaria de otra relación.

Por ejemplo, puede usarse la información almacenada en `DEPARTMENT` para fragmentar `EMPLOYEE` y `PROJECT`.

Esto ocurre cuando una relación se fragmenta tomando como base la forma en que otra relación relacionada ya fue fragmentada.

Por ejemplo:

- `DEPARTMENT` se fragmenta por departamento.
    
- `EMPLOYEE` se fragmenta según el departamento al que pertenece.
    
- `PROJECT` se fragmenta según el departamento responsable.
    

La fragmentación derivada mantiene la localidad semántica de los datos relacionados.

### Fragmentación vertical de EMPLOYEE

Una posible fragmentación vertical de `EMPLOYEE` es:

```text
L1 = { Ssn, Name, Sex, Bdate, Address }

L2 = { Ssn, Salary, Mgr, Dno }
```

En este ejemplo, `L1` contiene datos personales del empleado:

- `Ssn`
    
- `Name`
    
- `Sex`
    
- `Bdate`
    
- `Address`
    

Mientras que `L2` contiene datos administrativos o laborales:

- `Ssn`
    
- `Salary`
    
- `Mgr`
    
- `Dno`
    

El atributo `Ssn` aparece en ambos fragmentos porque funciona como clave común para reconstruir la relación original.

---

## Fragmentación híbrida

La fragmentación híbrida combina los fragmentos horizontales y verticales de una relación.

Por ejemplo, se pueden combinar las condiciones horizontales:

```text
Dno = 5
Dno = 4
Dno = 1
```

con los fragmentos verticales de la relación `EMPLOYEE`.

Si hay tres fragmentos horizontales y dos fragmentos verticales, se generan seis fragmentos en total.

Esto ocurre porque cada grupo horizontal puede dividirse nuevamente por atributos. Por ejemplo:

- Empleados del departamento 5 con atributos personales.
    
- Empleados del departamento 5 con atributos administrativos.
    
- Empleados del departamento 4 con atributos personales.
    
- Empleados del departamento 4 con atributos administrativos.
    
- Empleados del departamento 1 con atributos personales.
    
- Empleados del departamento 1 con atributos administrativos.
    

### Representación formal de fragmentos híbridos

Los fragmentos se especifican mediante una combinación de selección y proyección:

$$  
\pi_L(\sigma_C(R))  
$$

Donde:

**$\sigma_C(R)$:** selección de tuplas de la relación $R$ que cumplen la condición $C$.

**$\pi_L$:** proyección sobre la lista de atributos $L$.

**$R$:** relación original.

**$C$:** condición de selección.

**$L$:** lista de atributos seleccionados.

### Casos posibles

**$C = true$ y $L \ne ATTRS(R)$:** selecciona un fragmento vertical, porque no se filtran filas, pero sí se eligen solo ciertos atributos.

**$C \ne true$ y $L = ATTRS(R)$:** selecciona un fragmento horizontal, porque se filtran filas, pero se conservan todos los atributos.

**$C \ne true$ y $L \ne ATTRS(R)$:** selecciona un fragmento mixto o híbrido, porque se filtran filas y también se seleccionan atributos.

**$C = true$ y $L = ATTRS(R)$:** selecciona la relación completa $R$, porque no se filtran filas ni columnas.

## Esquemas en bases de datos distribuidas

### Esquema de fragmentación

El esquema de fragmentación es la definición del conjunto de fragmentos que incluyen todos los atributos y todas las tuplas almacenadas en la base de datos.

La condición fundamental es que toda la base de datos pueda reconstruirse a partir de los fragmentos mediante alguna secuencia de operaciones `OUTER JOIN` y `UNION`.

Esto garantiza que la fragmentación no pierda información.

En otras palabras, una fragmentación válida debe cumplir con:

**Completitud:** todos los datos originales deben estar representados en los fragmentos.

**Reconstruibilidad:** debe ser posible reconstruir las relaciones originales.

**Consistencia lógica:** los fragmentos deben corresponder a divisiones significativas y administrables.

### Esquema de asignación

El esquema de asignación describe cómo se asignan los fragmentos a los sitios del DDBMS.

Un fragmento puede almacenarse en un sitio específico o puede replicarse en varios sitios.

El esquema de asignación responde preguntas como:

- ¿Dónde se almacena cada fragmento?
    
- ¿Qué sitio contiene qué copia?
    
- ¿Qué fragmentos están replicados?
    
- ¿Qué datos necesita cada sitio?
    
- ¿Qué asignación mejora rendimiento y disponibilidad?
    

La asignación es una decisión de diseño clave porque afecta directamente el costo de las consultas, la velocidad de acceso, la disponibilidad y la complejidad de mantenimiento.

---

## Replicación y asignación

### Replicación

La replicación consiste en mantener copias de datos en más de un sitio. Su objetivo principal es mejorar la disponibilidad de la información.

Si un sitio falla, otro sitio puede conservar una copia del dato. Además, si una consulta se realiza desde un sitio cercano a una réplica, se puede reducir el costo de comunicación y mejorar el rendimiento.

Sin embargo, la replicación también tiene costos. Cuando un dato replicado se actualiza, deben mantenerse consistentes todas sus copias. Esto vuelve más costosos el control de concurrencia y la recuperación.

### Replicación completa

La replicación completa ocurre cuando todos los sitios tienen una copia de toda la base de datos.

Esta estrategia maximiza la disponibilidad, porque cualquier sitio puede consultar la base completa. Sin embargo, puede ralentizar las operaciones de actualización, ya que cada cambio debe propagarse a todos los sitios.

Además, hace que las técnicas de control de concurrencia y recuperación sean más caras. El sistema debe asegurarse de que todas las copias se mantengan consistentes.

### Sin replicación

La ausencia de replicación ocurre cuando cada fragmento se almacena exactamente en un sitio.

Esta estrategia reduce la complejidad de actualización, porque solo existe una copia de cada fragmento. Sin embargo, disminuye la disponibilidad, ya que si el sitio que almacena un fragmento falla, ese fragmento puede quedar inaccesible.

También puede afectar el rendimiento si los usuarios de otros sitios necesitan consultar datos remotos con frecuencia.

### Replicación parcial

La replicación parcial representa un espectro amplio entre la replicación completa y la ausencia de replicación.

Algunos fragmentos se replican y otros no.

Esta estrategia suele ser más flexible porque permite replicar únicamente los datos que realmente necesitan alta disponibilidad o acceso frecuente desde varios sitios.

Por ejemplo, una tabla de catálogos generales puede replicarse en todos los sitios, mientras que datos operativos locales pueden almacenarse solo en la sede correspondiente.

### Asignación

La asignación consiste en colocar un fragmento, o una copia de un fragmento, en un sitio particular.

Encontrar la asignación óptima es un problema complejo de optimización. No basta con decidir arbitrariamente dónde colocar los datos; deben considerarse múltiples factores.

Entre los criterios principales están:

**Rendimiento y disponibilidad de la información requerida en cada sitio:** los datos deben estar cerca de los usuarios o procesos que más los necesitan.

**Tipos y frecuencias de transacciones sometidas en cada sitio:** si un sitio realiza muchas consultas sobre ciertos datos, conviene almacenar esos datos localmente o mantener una réplica cercana.

La asignación adecuada busca equilibrar rendimiento, disponibilidad, costo de almacenamiento, costo de actualización, comunicación de red y complejidad de recuperación.

## Resumen integrador

Una base de datos distribuida permite administrar datos repartidos físicamente en varios sitios, pero conectados lógicamente como una sola base de datos. El DDBMS es el software encargado de hacer posible esta administración y de ocultar al usuario los detalles de distribución.

La arquitectura cliente / servidor sirve como base para muchos sistemas distribuidos, ya que separa aplicaciones cliente de servicios especializados, como servidores de bases de datos. En bases de datos relacionales, las consultas y transacciones suelen permanecer del lado del servidor, mientras que las aplicaciones se ejecutan en el cliente. En bases de datos orientadas a objetos, la interacción puede ser más estrecha, con algunos módulos del DBMS residiendo en el cliente.

La distribución se diferencia del paralelismo porque los DDBMS suelen operar sobre nodos heterogéneos conectados por red, mientras que los sistemas paralelos se enfocan en múltiples procesadores que comparten memoria o disco.

Las ventajas principales de los DDBMS son la transparencia, la confiabilidad, la disponibilidad, el rendimiento y la facilidad de expansión. Sin embargo, estas ventajas exigen características adicionales, como procesamiento distribuido de consultas, administración de transacciones distribuidas, manejo de réplicas, recuperación ante fallas parciales, seguridad distribuida y administración del catálogo.

El diseño de una base distribuida se apoya en la fragmentación, la replicación y la asignación. La fragmentación puede ser horizontal, vertical o híbrida. La horizontal divide tuplas y se reconstruye con `UNION`. La vertical divide atributos y se reconstruye con `FULL OUTER JOIN`. La híbrida combina selección y proyección mediante expresiones como:

$$  
\pi_L(\sigma_C(R))  
$$

Finalmente, la replicación mejora disponibilidad y rendimiento, pero aumenta el costo de actualización, concurrencia y recuperación. La asignación decide en qué sitio se almacena cada fragmento o copia, considerando rendimiento, disponibilidad y frecuencia de transacciones.

## Introducción

En una llamada RPC, cliente y servidor no comparten el mismo espacio de memoria. Esto introduce un problema fundamental: los parámetros de una llamada no pueden manipularse exactamente igual que en una llamada local.

Cuando un programa local llama a una función, puede pasar valores, referencias, apuntadores o estructuras complejas utilizando direcciones que tienen significado dentro del mismo espacio de memoria. En un sistema distribuido esto cambia completamente, porque el cliente y el servidor se ejecutan en espacios de direccionamiento diferentes y, además, pueden encontrarse en máquinas con arquitecturas distintas.

Por ello, una implementación RPC necesita resolver tres problemas principales relacionados con los parámetros:

1. cómo representar los datos;
    
2. cómo transmitirlos por la red;
    
3. cómo reconstruirlos correctamente en la máquina remota.
    

A partir de estos problemas aparecen conceptos como **serialización, XDR, generación automática de stubs y skeletons, lenguajes de descripción de interfaces e IDL**.

---

## Gestión de parámetros en RPC

### Espacios de direccionamiento diferentes:

El cliente y el servidor se ejecutan normalmente en procesos distintos y, por tanto, poseen espacios de direccionamiento diferentes.

Puede visualizarse así:

```
MÁQUINA CLIENTE

Memoria del cliente
+----------------------+
| variable x           |
| objeto A             |
| apuntador 0x1234     |
+----------------------+


MÁQUINA SERVIDOR

Memoria del servidor
+----------------------+
| variable y           |
| objeto B             |
| dirección 0x1234 ?   |
+----------------------+
```

Aunque ambas máquinas puedan utilizar una dirección numéricamente idéntica, no significa que se refieran al mismo dato.

Una dirección de memoria solo tiene significado dentro del espacio de direccionamiento donde fue creada.

---

## Por qué no existe paso por referencia directo

### Referencias locales:

En una llamada local puede realizarse algo semejante a:

```
funcion(&x)
```

La función recibe una referencia a la posición de memoria donde está almacenada `x`.

Esto funciona porque ambas partes comparten el mismo espacio de memoria.

```
Programa llamador
       |
       | dirección de x
       v
Procedimiento
       |
       v
misma memoria
```

### Referencias remotas:

En RPC, si el cliente enviara simplemente:

```
0x12345678
```

esa dirección no tendría necesariamente significado para el servidor.

```
CLIENTE                    SERVIDOR

0x12345678 ------X------> 0x12345678
   |                         |
 apunta a x                puede apuntar
                           a otra cosa
```

Por ello, el material señala que **no existe un paso por referencia directo** entre cliente y servidor.

---

## Problema de los apuntadores

Los apuntadores constituyen uno de los casos más claros de por qué las estructuras complejas son difíciles de transmitir.

Considérese:

```
struct Persona {
    char *nombre;
    int edad;
}
```

En memoria podría existir:

```
Persona
+------------------+
| nombre = 0x1000  | ----> "Bruno"
| edad = 21        |
+------------------+
```

Si se envía literalmente el contenido de la estructura, también se estaría enviando:

```
nombre = 0x1000
```

Pero esa dirección pertenece a la memoria del cliente.

En el servidor:

```
0x1000
```

no tiene por qué contener `"Bruno"`.

Por tanto, no basta con copiar la estructura byte por byte. Es necesario seguir los apuntadores, obtener los datos reales y convertir toda la estructura en una representación transmisible.

---

## Transmisión de parámetros sobre la red

Los parámetros deben convertirse a una forma capaz de viajar por la red. El material señala que esto se realiza mediante una **representación serializada de las estructuras**.

La transformación general es:

```
Estructura en memoria
        |
        | serialización
        v
Secuencia transmisible
        |
        v
       RED
```

Después, el receptor realiza la operación contraria:

```
Secuencia recibida
        |
        | reconstrucción
        v
Estructura utilizable
```

---

## Serialización

### Concepto:

La **serialización** convierte datos estructurados en una representación lineal.

Por ejemplo:

```
Objeto original:

Persona
├─ nombre = "Ana"
├─ edad = 20
└─ activo = true
```

podría convertirse conceptualmente en:

```
[ "Ana" | 20 | true ]
```

o en alguna secuencia binaria equivalente.

El objetivo no es conservar direcciones de memoria, sino conservar el **significado de los datos**.

---

## Heterogeneidad entre cliente y servidor

Otro problema importante aparece cuando cliente y servidor utilizan arquitecturas distintas.

El material indica que las máquinas pueden ser heterogéneas y que, por ello, puede ser necesaria una **conversión de formatos**.

La heterogeneidad puede aparecer en:

- arquitectura del procesador;
    
- sistema operativo;
    
- representación de enteros;
    
- representación de números reales;
    
- tamaño de tipos;
    
- orden de bytes;
    
- alineamiento de estructuras.
    

Esto significa que una misma secuencia binaria podría ser interpretada de manera diferente por dos máquinas.

---

## Problemas de representación

El material identifica varios problemas específicos de representación que deben resolverse al transmitir parámetros.

### Little endian y big endian:

Uno de los ejemplos más importantes es el **orden de los bytes**.

Considérese un número compuesto por varios bytes:

```
0x12345678
```

Una máquina podría almacenarlo como:

```
12 34 56 78
```

mientras que otra podría almacenarlo como:

```
78 56 34 12
```

Estas convenciones corresponden a diferentes formas de ordenar los bytes de un valor.

La red necesita una representación común o mecanismos de conversión para evitar interpretaciones incorrectas.

### Representación conceptual:

```
Valor lógico:
0x12345678

Máquina A:
12 34 56 78

Máquina B:
78 56 34 12
```

Si los bytes se transfieren sin conversión:

```
Máquina A ---> Máquina B
```

el valor reconstruido podría ser incorrecto.

---

## Orden de octetos en cadenas

También debe establecerse cómo se transmiten los bytes que forman una cadena de caracteres.

Por ejemplo:

```
"ABC"
```

puede representarse mediante una secuencia de códigos:

```
A | B | C
```

La interpretación correcta requiere que ambas máquinas conozcan:

- la codificación;
    
- el orden;
    
- la longitud;
    
- la terminación de la cadena.
    

---

## Representación de números enteros

Los enteros pueden presentar diferencias tanto en orden como en tamaño.

Por ejemplo:

```
Máquina A:
int = 32 bits

Máquina B:
int = 64 bits
```

Si ambas máquinas suponen tamaños diferentes, un mismo conjunto de bytes puede interpretarse de forma incorrecta.

El material menciona específicamente las limitaciones de tamaño, por ejemplo enteros de 32 y 64 bits.

---

## Representación de números reales

Los números de punto flotante también presentan dificultades.

Por ejemplo:

```
float
double
```

pueden tener distintas representaciones internas o tamaños.

Por ello, la comunicación distribuida necesita una representación definida y compartida.

---

## Representación de estructuras complejas

Cuando los datos incluyen:

```
estructuras
arreglos
uniones
apuntadores
estructuras anidadas
```

el problema se vuelve más complejo.

Una estructura podría contener:

```
Objeto A
├─ entero
├─ cadena
├─ arreglo
└─ apuntador
       |
       v
    Objeto B
```

La representación transmitida debe conservar correctamente todas estas relaciones.

---

## Soluciones normalizadas para la representación

Para resolver los problemas anteriores pueden utilizarse representaciones estándar.

El material menciona **ASN.1** como una solución normalizada.

### ASN.1:

**ASN.1** significa:

**Abstract Syntax Notation One**

Su propósito consiste en describir de manera abstracta la estructura de los datos.

La idea es separar:

```
QUÉ datos existen
        |
        v
Sintaxis abstracta
```

de:

```
CÓMO se representan internamente
        |
        v
Máquina concreta
```

Esta separación permite construir una descripción que no dependa directamente de:

- procesador;
    
- sistema operativo;
    
- representación local;
    
- lenguaje específico.
    

---

## Independencia de representación

Una definición abstracta puede indicar:

```
Persona:
    nombre -> cadena
    edad   -> entero
```

sin establecer necesariamente cómo se almacenan esos elementos en la memoria de una arquitectura concreta.

Después, herramientas específicas generan conversiones adecuadas para cada plataforma.

El material destaca precisamente que ASN.1 permite una codificación independiente de las máquinas y sistemas operativos.

---

## Otras soluciones para la representación

Además de ASN.1, el material presenta otras posibilidades.

### Representación externa común:

Cliente y servidor convierten sus datos locales a una representación estándar.

```
Formato cliente
      |
      v
Formato común
      |
      v
Formato servidor
```

Esto simplifica la interoperabilidad.

Sin embargo, si ambos sistemas utilizan ya el mismo formato, podrían realizarse conversiones innecesarias.

### Conversión explícita en el servidor:

Otra posibilidad consiste en transmitir la representación del cliente y hacer que el servidor la convierta.

```
Formato cliente
      |
      | transmisión
      v
Servidor
      |
      | conversión
      v
Formato servidor
```

### Negociación:

Cliente y servidor también pueden negociar qué representación utilizar.

```
Cliente:
Puedo usar formato A o B

Servidor:
Uso formato B

Resultado:
Se usa B
```

Esto puede evitar conversiones innecesarias si ambos soportan un formato común.

---

## XDR

Una solución importante presentada en el material es **XDR**, desarrollado por Sun.

XDR significa:

**External Data Representation**.

XDR proporciona:

- un formato de transmisión sobre la red;
    
- una biblioteca de rutinas para convertir datos.
    

Su objetivo es permitir que diferentes máquinas compartan una representación común.

---

## Idea central de XDR

Puede entenderse mediante el siguiente esquema:

```
Formato interno cliente
        |
        | XDR
        v
Formato de red
        |
        | transmisión
        v
Formato de red
        |
        | XDR
        v
Formato interno servidor
```

XDR actúa como intermediario entre la representación local y la representación utilizada para transmitir los datos.

---

## Tipos soportados por XDR

El material indica que XDR proporciona rutinas para distintos tipos de datos de C.

Entre ellos se encuentran:

### Datos elementales:

Por ejemplo:

```
int
unsigned int
float
double
```

### Estructuras simples:

Como:

```
arreglos
cadenas
uniones
```

### Apuntadores y memoria:

XDR también incluye mecanismos para tratar apuntadores y administrar memoria.

Esto es importante porque, como se explicó anteriormente, no puede transmitirse simplemente una dirección de memoria.

---

## Empaquetado y desempaquetado con XDR

Las rutinas XDR se utilizan tanto para convertir datos hacia el formato de red como para reconstruirlos posteriormente.

```
EMPAQUETADO:

Formato interno
      |
      | XDR
      v
Formato de red
```

```
DESEMPAQUETADO:

Formato de red
      |
      | XDR
      v
Formato interno
```

Normalmente estas operaciones son generadas automáticamente por herramientas asociadas al sistema RPC.

Para casos más complejos, el programador también puede intervenir directamente.

---

## Rutinas de conversión XDR

El material muestra ejemplos concretos de funciones XDR.

Por ejemplo:

```
bool_t xdr_int(XDR *xdrs, int *ip);
```

Esta función puede convertir un entero entre su representación interna y el formato de red.

La idea importante es que:

```
ip
```

apunta al valor, mientras que:

```
xdrs
```

describe la corriente XDR y el sentido de la operación.

---

## Misma rutina para ambos sentidos

Una propiedad interesante de XDR es que una misma rutina puede utilizarse tanto para:

```
codificar
```

como para:

```
decodificar
```

El sentido se especifica mediante el contexto XDR.

Por tanto:

```
xdr_int(...)
```

puede utilizarse conceptualmente así:

```
modo = ENCODE
int local ---> formato de red
```

o:

```
modo = DECODE
formato de red ---> int local
```

El material señala precisamente que la misma rutina sirve para ambos sentidos.

---

## Conversión de arreglos con XDR

También existen rutinas para estructuras más complejas, como arreglos.

El material muestra:

```
xdr_array(...)
```

que necesita información como:

- dirección del arreglo;
    
- número de elementos;
    
- tamaño máximo;
    
- tamaño de cada elemento;
    
- función XDR utilizada para convertir cada elemento.
    

  

Conceptualmente:

```
Arreglo:
[1, 2, 3, 4]
```

XDR necesita conocer:

```
cantidad = 4
tipo = entero
rutina = xdr_int
```

y aplica la conversión correspondiente a cada elemento.

---

## Generación automática de talones

La estructura de los stubs y skeletons es suficientemente regular como para ser generada automáticamente.

Esto evita que el desarrollador tenga que escribir manualmente toda la lógica repetitiva de comunicación.

Para generar estos componentes se necesitan dos tipos de información.

### Información dependiente del ambiente:

Incluye elementos como:

- procedimientos de conversión;
    
- protocolo de comunicación.
    

Esta información depende de la infraestructura RPC utilizada.

### Información dependiente de la aplicación:

Incluye:

- procedimientos disponibles;
    
- formato de parámetros;
    
- tipos de resultados.
    

Esta información cambia según el servicio que se desea implementar.

---

## Separación entre infraestructura y aplicación

Puede visualizarse así:

```
INFORMACIÓN DE INFRAESTRUCTURA

protocolos
conversiones
bibliotecas RPC


INFORMACIÓN DE APLICACIÓN

procedimientos
parámetros
resultados
```

Un generador combina ambas categorías para producir código automáticamente.

---

## IDL

La información específica de la aplicación suele describirse mediante un **IDL**.

IDL significa:

**Interface Definition Language**

o:

**lenguaje de descripción de interfaces**.

El material indica que la información dependiente de la aplicación se define mediante este tipo de lenguaje.

---

## Interfaz como contrato

La interfaz representa el **contrato entre cliente y servidor**.

Un contrato establece:

```
qué operaciones existen
qué parámetros reciben
qué resultados producen
qué errores pueden aparecer
```

Por ejemplo:

```
sumar(IN int a, IN int b) -> int
```

El cliente sabe cómo utilizar la operación.

El servidor sabe qué debe implementar.

Ambos dependen de la misma definición común.

---

## Independencia del IDL

Una característica importante es que la interfaz se define de forma abstracta.

El material indica tres tipos de independencia:

- independencia de un lenguaje particular;
    
- independencia de representación de tipos;
    
- independencia de máquina.
    

  

Esto significa que una misma interfaz podría utilizarse para generar código específico para distintos lenguajes o plataformas.

---

## Independencia de lenguaje

Supóngase una interfaz:

```
obtenerUsuario(id)
```

El cliente podría estar escrito en:

```
C
```

y el servidor en otro lenguaje.

La definición de la interfaz actúa como punto común.

```
IDL
 |
 +--> cliente
 |
 +--> servidor
```

El objetivo es que el contrato no dependa de la sintaxis interna de un lenguaje concreto.

---

## Contenido mínimo de una interfaz

Según el material, una descripción de interfaz debe incluir varios elementos esenciales.

### Identificación de procedimientos:

Debe indicarse:

```
nombre
versión
```

La versión es importante porque un servicio puede evolucionar.

Por ejemplo:

```
ServicioUsuarios v1
ServicioUsuarios v2
```

### Tipos de parámetros:

Debe especificarse qué recibe cada procedimiento.

```
crearUsuario(
    nombre: cadena,
    edad: entero
)
```

### Resultados:

También debe definirse qué devuelve.

```
crearUsuario(...) -> identificador
```

### Excepciones:

Puede especificarse qué errores forman parte de la interfaz.

Por ejemplo:

```
UsuarioExistente
DatosInvalidos
```

---

## Modos de paso de parámetros

El material distingue tres modos básicos:

- **IN**;
    
- **OUT**;
    
- **IN-OUT**.
    

  

### Parámetro IN:

Un parámetro `IN` entra al procedimiento.

```
Cliente ---> Servidor
```

Ejemplo:

```
sumar(IN a, IN b)
```

El cliente proporciona los valores.

### Parámetro OUT:

Un parámetro `OUT` representa información producida por el servidor.

```
Cliente <--- Servidor
```

Por ejemplo:

```
consultarUsuario(
    IN id,
    OUT nombre
)
```

### Parámetro IN-OUT:

Un parámetro `IN-OUT` viaja inicialmente hacia el servidor y posteriormente regresa modificado.

```
Cliente ---> Servidor
Cliente <--- Servidor
```

Ejemplo conceptual:

```
actualizarContador(IN-OUT contador)
```

---

## Extensiones de una interfaz

Además del contenido mínimo, pueden definirse otras propiedades.

Entre ellas:

### Conversión de tipos complejos:

Puede especificarse cómo deben manejarse estructuras que no tienen una conversión trivial.

### QoS:

También pueden incluirse propiedades no funcionales relacionadas con **Quality of Service**.

Por ejemplo:

```
latencia
prioridad
disponibilidad
```

El material únicamente las presenta como extensiones posibles de la descripción de interfaz.

---

## Especificación común para cliente y servidor

La definición IDL debe ser compartida por ambas partes.

```
               IDL
                |
        +-------+-------+
        |               |
        v               v
    Cliente          Servidor
```

De esta forma, ambos utilizan una interpretación coherente de:

- procedimientos;
    
- tipos;
    
- parámetros;
    
- modos de paso.
    

El material señala que esta especificación común puede adaptarse incluso a múltiples lenguajes.

---

## Generación de stub y skeleton desde IDL

Una de las principales ventajas del IDL es que puede utilizarse para generar automáticamente:

- el **stub del cliente**;
    
- el **skeleton del servidor**.
    

  

Conceptualmente:

```
          IDL
           |
           v
Generador de talones
      /        \
     /          \
    v            v
 Stub         Skeleton
cliente       servidor
```

Esto garantiza que ambos componentes utilicen la misma definición de interfaz.

---

## Modo general de operación

El proceso completo puede entenderse como una combinación de código escrito por el programador y código generado automáticamente.

```
          DESCRIPCIÓN DE INTERFAZ
                    |
                    v
          GENERADOR DE TALONES
              /             \
             v               v
         Stub cliente     Skeleton servidor
             |               |
             v               v
Código cliente          Código servidor
             |               |
             v               v
        Compilador        Compilador
             |               |
             v               v
      Ejecutable cliente  Ejecutable servidor
```

El material muestra precisamente esta separación entre procedimientos de cliente, procedimientos de servidor, bibliotecas, compiladores y generadores de talones.

---

## Ejemplo con rpcgen

El material presenta el caso concreto de una herramienta denominada **rpcgen**.

Supóngase que existen tres elementos iniciales:

```
proc_client.c
proc_server.c
proc.x
```

donde:

```
proc_client.c
```

contiene la lógica específica del cliente;

```
proc_server.c
```

contiene la lógica del servidor;

y:

```
proc.x
```

contiene la descripción de la interfaz.

---

## Archivos generados por rpcgen

A partir de la descripción de interfaz, `rpcgen` genera componentes adicionales.

Entre ellos:

```
proc_clnt.c
```

para el stub cliente;

```
proc_svc.c
```

para el skeleton servidor;

```
proc_xdr.c
```

para las rutinas de conversión XDR;

```
proc.h
```

para las definiciones compartidas.

El flujo puede visualizarse así:

```
                   proc.x
                     |
                     v
                   rpcgen
          /-----------|-----------\
         /            |            \
        v             v             v
proc_clnt.c     proc_svc.c      proc_xdr.c
     |               |                |
     +---------------+----------------+
                     |
                   proc.h
```

---

## Construcción del cliente

Para generar el ejecutable cliente se combinan:

```
proc_client.c
+
proc_clnt.c
+
proc_xdr.c
+
proc.h
+
bibliotecas
```

y se compilan.

```
gcc
 |
 v
Cliente ejecutable
```

---

## Construcción del servidor

De manera similar, el servidor combina:

```
proc_server.c
+
proc_svc.c
+
proc_xdr.c
+
proc.h
+
bibliotecas
```

Después se compila para producir el servidor ejecutable.

---

## Separación entre código manual y código generado

Esta arquitectura permite distinguir claramente:

```
CÓDIGO DEL PROGRAMADOR
----------------------
proc_client.c
proc_server.c
proc.x


CÓDIGO GENERADO
---------------
proc_clnt.c
proc_svc.c
proc_xdr.c
proc.h
```

La herramienta automatiza la infraestructura repetitiva de RPC.

El programador puede concentrarse principalmente en:

```
qué servicio existe
+
qué debe hacer
```

en lugar de implementar manualmente:

```
serialización
mensajes
stubs
skeletons
conversiones
```

## Ventajas del IDL

El material resume varias ventajas importantes de utilizar un lenguaje de descripción de interfaces.

### Independencia de los tipos concretos:

Distintos lenguajes pueden utilizar diferentes representaciones para conceptos semejantes.

Por ejemplo:

```
Lenguaje A:
entero

Lenguaje B:
int

Lenguaje C:
Integer
```

La descripción IDL define el tipo de forma abstracta.

Después, cada implementación lo adapta a su lenguaje concreto.

### Independencia del sistema:

Los tipos también pueden representarse de manera distinta según la plataforma.

El IDL evita basar el contrato directamente en esas representaciones locales.

### Tipos complejos:

Puede describirse cómo deben tratarse argumentos, resultados y excepciones.

Cuando aparecen estructuras complejas, pueden generarse procedimientos adicionales de conversión.

### Tratamiento de heterogeneidad:

En conjunto, el IDL permite construir un proceso sistemático para manejar las diferencias entre cliente y servidor.

---

## Relación entre IDL y XDR

IDL y XDR resuelven problemas relacionados, pero diferentes.

### IDL responde:

> ¿Qué interfaz existe?

Por ejemplo:

```
sumar(IN int a, IN int b) -> int
```

Define:

- nombre del procedimiento;
    
- parámetros;
    
- tipos;
    
- resultado.
    

### XDR responde:

> ¿Cómo se representan esos datos para transmitirlos?

Por ejemplo:

```
int local
   |
   v
representación XDR
   |
   v
red
```

Por tanto:

```
IDL = definición lógica de la interfaz

XDR = representación externa de los datos
```

Ambos pueden utilizarse juntos.

---

## Relación completa del proceso RPC

Todos los elementos estudiados pueden integrarse en una sola secuencia.

```
1. El programador define la interfaz
              |
              v
             IDL
              |
              v
2. Se generan automáticamente:
      - stub cliente
      - skeleton servidor
      - rutinas XDR
      - definiciones comunes
              |
              v
3. Se compilan cliente y servidor
              |
              v
4. El cliente llama al stub
              |
              v
5. Los parámetros se serializan
              |
```

## Idea fundamental de la gestión de parámetros

El problema más importante de toda esta sección puede resumirse mediante una comparación.

En una llamada local:

```
parámetro
   |
   v
misma memoria
```

En una llamada remota:

```
parámetro
   |
   v
serialización
   |
   v
representación externa
   |
   v
red
   |
   v
reconstrucción
   |
   v
otra memoria
```

Por eso RPC necesita mecanismos adicionales que no son necesarios en una llamada local.

# Ideas fundamentales de la clase

En RPC, cliente y servidor poseen espacios de direccionamiento diferentes. Debido a ello, los apuntadores y referencias locales pierden su significado cuando deben transmitirse a otra máquina. Los parámetros deben convertirse a una representación independiente de la memoria local.

La transmisión de parámetros requiere **serialización**, ya que estructuras, arreglos y valores deben transformarse en una secuencia capaz de viajar por la red. Posteriormente, el receptor debe reconstruir esos datos.

La heterogeneidad entre máquinas introduce problemas adicionales. Diferentes sistemas pueden utilizar distintas representaciones para enteros, números reales, cadenas, estructuras y orden de bytes. Por ello resulta necesario utilizar mecanismos de conversión.

**XDR** proporciona una representación externa común para transportar datos entre sistemas diferentes. Sus rutinas convierten entre el formato interno de una máquina y el formato utilizado en la red, pudiendo emplearse tanto para empaquetar como para desempaquetar.

La estructura de los stubs y skeletons puede generarse automáticamente porque sigue patrones bien definidos. Para realizar esta generación se necesita una descripción abstracta de la interfaz del servicio.

Un **IDL** define el contrato entre cliente y servidor de manera independiente de un lenguaje, máquina o representación concreta. Describe procedimientos, versiones, tipos, resultados, excepciones y modos de paso como `IN`, `OUT` e `IN-OUT`.

Herramientas como **rpcgen** utilizan una descripción de interfaz para producir automáticamente el stub cliente, el skeleton servidor, las rutinas XDR y las definiciones compartidas. De esta manera, gran parte de la infraestructura RPC queda automatizada.

Finalmente, IDL y XDR cumplen funciones complementarias. El IDL describe **qué servicio existe y qué datos utiliza**, mientras que XDR define **cómo representar esos datos para poder transmitirlos entre máquinas heterogéneas**.

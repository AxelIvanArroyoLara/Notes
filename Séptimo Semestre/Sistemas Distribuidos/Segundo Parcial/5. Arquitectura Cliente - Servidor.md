## Introducción

El modelo **cliente-servidor** es una de las arquitecturas fundamentales de los sistemas distribuidos. Su idea básica consiste en separar las responsabilidades entre una entidad que solicita un servicio y otra que lo proporciona.

El **cliente** inicia la interacción enviando una petición. El **servidor** recibe esa petición, ejecuta el servicio correspondiente y devuelve una respuesta. Este patrón puede parecer sencillo, pero admite muchas variaciones dependiendo de cómo se administre el estado, cómo se realice la comunicación y cómo se ejecute el servidor internamente.

La abstracción general es:

```
Cliente                     Servidor

   |                           |
   |-------- request --------->|
   |                           |
   |        execution          |
   |                           |
   |<------- response ---------|
   |                           |
```

A partir de esta estructura básica pueden distinguirse tres grandes dimensiones de diseño:

- administración del estado;
    
- modelo de comunicación;
    
- modelo de ejecución del servidor.
    

  

---

## Características generales del modelo cliente-servidor

### Administración del estado:

El estado puede analizarse desde dos perspectivas diferentes:

- el estado mantenido por el servidor;
    
- la relación entre las diferentes solicitudes de un cliente.
    

El material distingue:

```
Servidor:
persistente o no persistente

Servicio:
stateful o stateless
```

Estas dos clasificaciones están relacionadas, pero no significan exactamente lo mismo.

Un servidor puede modificar datos persistentes y, aun así, tratar cada petición del cliente como independiente de las anteriores.

Por ello debe distinguirse cuidadosamente:

```
¿El servidor modifica información permanente?
```

de:

```
¿La siguiente petición depende de las peticiones anteriores?
```

---

## Servidor sin datos persistentes

### Concepto:

Un servidor sin datos persistentes ejecuta cada operación utilizando únicamente los parámetros proporcionados en la solicitud.

Esto significa que la ejecución:

```
request
   |
   v
función(parámetros)
   |
   v
resultado
```

no modifica permanentemente el contexto del servidor.

Por ejemplo, puede existir un servicio remoto encargado de calcular:

```
sqrt(25)
sin(x)
cos(x)
log(x)
```

Cada resultado depende exclusivamente de los parámetros recibidos.

### Ejemplo:

Un cliente solicita:

```
calcularCuadrado(5)
```

El servidor devuelve:

```
25
```

Posteriormente otro cliente solicita:

```
calcularCuadrado(8)
```

y obtiene:

```
64
```

La segunda ejecución no depende de la primera.

---

## Ventajas de un servidor sin persistencia

El material señala que este tipo de servidor representa una situación ideal para:

- tolerancia a fallas;
    
- control de concurrencia.
    

  

### Tolerancia a fallas:

Si el servidor falla después de ejecutar una petición, normalmente no existe un estado interno modificado que deba reconstruirse.

Por ejemplo:

```
f(10) → 20
```

Si el servidor cae posteriormente, puede reiniciarse y volver a calcular:

```
f(10)
```

sin necesitar recuperar un estado previo.

### Concurrencia:

También resulta más sencillo ejecutar varias peticiones al mismo tiempo.

```
Cliente A ---> f(5)
Cliente B ---> f(8)
Cliente C ---> f(3)
```

Como una ejecución no depende de otra, existe menos riesgo de interferencia entre las operaciones.

---

## Servidor con datos persistentes

### Concepto:

En un servidor con persistencia, las ejecuciones sucesivas pueden modificar datos que permanecen después de finalizar una petición.

La estructura puede representarse como:

```
Request 1
   |
   v
Servidor
   |
   v
Estado persistente cambia

Request 2
   |
   v
Servidor
   |
   v
utiliza estado ya modificado
```

Esto introduce una complejidad considerablemente mayor.

---

## Modificación del contexto de ejecución

Supóngase una base de datos con:

```
saldo = 1000
```

Una primera petición realiza:

```
retirar(200)
```

y modifica:

```
saldo = 800
```

La siguiente petición ya no se ejecuta sobre el estado inicial de 1000, sino sobre 800.

Esto significa que el servidor debe mantener correctamente la información entre diferentes ejecuciones.

---

## Problemas de concurrencia

Cuando múltiples clientes acceden simultáneamente a datos persistentes, aparece el problema del acceso concurrente.

Por ejemplo:

```
Saldo inicial = 1000

Cliente A quiere retirar 700
Cliente B quiere retirar 500
```

Si ambos leen:

```
saldo = 1000
```

antes de que cualquiera actualice el valor, podrían producirse resultados inconsistentes.

La secuencia problemática podría ser:

```
Cliente A lee 1000
Cliente B lee 1000

Cliente A calcula 300
Cliente B calcula 500

Cliente A guarda 300
Cliente B guarda 500
```

El resultado final podría ser incorrecto.

Por ello, los servidores con datos persistentes deben controlar cuidadosamente la concurrencia. El material señala explícitamente que la persistencia introduce problemas en el control del acceso concurrente a los recursos.

---

## Tolerancia a fallas con persistencia

Cuando un servidor mantiene datos persistentes, recuperarse de un fallo también se vuelve más complicado.

Debe determinarse:

```
¿Qué operaciones terminaron?

¿Qué operaciones quedaron incompletas?

¿Qué cambios fueron almacenados?

¿Qué cambios deben revertirse?
```

Por ello, la tolerancia a fallas deja de ser trivial.

El material presenta como ejemplos de servidores con datos persistentes:

- servidores de bases de datos;
    
- sistemas de archivos distribuidos.
    

  

---

## Servicios stateless

### Concepto:

Un servicio **stateless** no mantiene información sobre la secuencia de solicitudes realizadas por un cliente.

Cada petición puede procesarse independientemente.

Por ejemplo:

```
Request A
Request B
Request C
```

pueden interpretarse como:

```
A independiente
B independiente
C independiente
```

El servidor no necesita recordar:

```
qué pidió antes el cliente
```

para comprender la petición actual.

---

## Independencia entre peticiones

En un servicio stateless, una petición contiene toda la información necesaria para ser procesada.

Por ejemplo:

```
obtenerHoraActual()
```

No importa si el mismo cliente preguntó la hora cinco minutos antes.

Cada solicitud se evalúa por sí sola.

Por ello, el material señala que el orden entre solicitudes no es importante.

---

## Stateless no significa ausencia de datos globales

Un punto importante es que un servicio stateless puede modificar o consultar información global.

La diferencia consiste en que la **solicitud actual no depende de la historia particular de solicitudes anteriores del mismo cliente**.

Por ejemplo:

```
GET /producto/15
```

puede consultar una base de datos cuyo contenido cambia con el tiempo.

Sin embargo, para interpretar esa solicitud no es necesario saber:

```
qué pidió antes ese cliente
```

Esto sigue siendo conceptualmente stateless.

---

## Ejemplo: NTP

El material utiliza el servicio de sincronización de reloj de red como ejemplo de servicio stateless:

**NTP — Network Time Protocol**.

Un cliente solicita información temporal.

Cada petición puede resolverse independientemente de las anteriores.

```
Cliente
   |
   | ¿qué hora es?
   v
Servidor NTP
   |
   | hora actual
   v
Cliente
```

---

## Servicios stateful

### Concepto:

Un servicio **stateful** procesa las nuevas solicitudes tomando en cuenta el estado producido por solicitudes anteriores.

En este caso:

```
Request 2
```

puede depender del resultado de:

```
Request 1
```

Por ello, el orden de las solicitudes se vuelve importante.

---

## Ejemplo de servicio stateful

Supóngase un servicio que permite leer un archivo secuencialmente.

Inicialmente:

```
puntero = 0
```

Primera operación:

```
read()
```

lee los primeros bytes y modifica:

```
puntero = 100
```

Segunda operación:

```
read()
```

comienza desde:

```
posición 100
```

La segunda operación depende directamente del estado generado por la primera.

Esto es exactamente el ejemplo de acceso secuencial a archivos señalado en el material.

---

## Estado de un objeto remoto

Otro ejemplo de servicio stateful es la llamada a métodos de objetos remotos.

Supóngase:

```
Contador remoto
valor = 0
```

Un cliente ejecuta:

```
incrementar()
```

Ahora:

```
valor = 1
```

Una llamada posterior:

```
obtenerValor()
```

devuelve:

```
1
```

El resultado depende del estado interno modificado por la operación anterior.

El material utiliza precisamente este tipo de situación como ejemplo de servicio stateful.

---

## Comparación entre stateless y stateful

|Característica|Stateless|Stateful|
|---|---|---|
|Recuerda solicitudes anteriores|No|Sí|
|Orden de solicitudes importante|Generalmente no|Sí|
|Escalabilidad|Más sencilla|Más compleja|
|Recuperación ante fallas|Más sencilla|Más difícil|
|Ejemplo|NTP|Acceso secuencial a archivo|

La diferencia fundamental puede resumirse así:

```
STATELESS

request actual
    |
    v
se procesa sola
```

```
STATEFUL

request anterior
    |
    v
estado
    |
    v
request actual
```

---

## Diferencia entre persistencia y statefulness

Es importante no confundir ambos conceptos.

### Persistencia:

Responde a:

> ¿El servidor mantiene datos modificados entre ejecuciones?

### Statefulness:

Responde a:

> ¿La petición actual depende del estado producido por peticiones anteriores?

Estas dimensiones pueden combinarse.

Por ejemplo, un servidor de base de datos contiene datos persistentes, pero una consulta individual puede tratarse de forma independiente respecto de las consultas anteriores de un determinado cliente.

---

## Modelo de comunicación

Después de estudiar el estado, otra característica fundamental es la forma en la que cliente y servidor intercambian mensajes.

El material distingue dos criterios:

- orientado a conexión o basado en datagramas;
    
- síncrono o asíncrono.
    

  

---

## Modos de conexión

### Diferencia principal:

La diferencia fundamental entre un modo orientado a conexión y uno basado en datagramas se encuentra en la **confiabilidad de entrega de los mensajes**.

---

## Comunicación orientada a conexión

Un protocolo orientado a conexión proporciona mayores garantías.

El material señala tres propiedades principales.

### Entrega garantizada:

El sistema intenta asegurar que los mensajes lleguen al receptor.

Si aparece un error, la entrega puede volver a intentarse.

### Orden conservado:

Si se envían:

```
Mensaje 1
Mensaje 2
Mensaje 3
```

el receptor debería observar:

```
Mensaje 1
Mensaje 2
Mensaje 3
```

y no:

```
Mensaje 2
Mensaje 1
Mensaje 3
```

### Control de errores:

La infraestructura utiliza mecanismos para detectar y corregir ciertos problemas de transmisión.

El material resume estas propiedades como entrega garantizada, respeto del orden y reintentos cuando sea necesario.

---

## Comunicación basada en datagramas

El otro enfoque sigue una filosofía de **best effort**.

Esto significa que la infraestructura intenta entregar el mensaje, pero no garantiza que realmente llegue.

Pueden ocurrir varios casos:

```
Mensaje enviado
     |
     +--> llega correctamente
     |
     +--> se pierde
     |
     +--> llega duplicado
     |
     +--> llega fuera de orden
```

---

## Posible pérdida de mensajes

El cliente podría enviar:

```
A
B
C
```

y el servidor recibir solamente:

```
A
C
```

porque:

```
B
```

se perdió durante la transmisión.

---

## Posible duplicación

También podría ocurrir:

```
A
B
B
C
```

aunque el cliente enviara solamente una vez cada mensaje.

El protocolo superior debe estar preparado para reconocer o tolerar estas duplicaciones si son importantes para la aplicación.

---

## Pérdida del orden

También puede enviarse:

```
1
2
3
```

y recibirse:

```
2
1
3
```

El sistema basado en datagramas no proporciona necesariamente el orden original.

Esto puede ser aceptable para algunas aplicaciones, pero no para otras.

---

## Elección del modo de comunicación

El tipo de aplicación determina qué garantías son necesarias.

Por ejemplo:

```
Transferencia de archivo
```

requiere típicamente una entrega confiable y ordenada.

En cambio:

```
actualización periódica de posición
```

puede tolerar la pérdida ocasional de un mensaje si pronto llegará uno nuevo con información más actual.

El punto importante es que el protocolo debe elegirse de acuerdo con las necesidades del servicio.

---

## Interacción síncrona

### Concepto:

En una interacción síncrona, el cliente realiza una petición y queda esperando mientras el servidor procesa la operación.

Esto se denomina una llamada **bloqueante**.

```
CLIENTE                         SERVIDOR

   |                               |
   |--------- request ------------>|
   |                               |
   |     cliente bloqueado         |
   |          espera               |
   |                               |
   |<-------- response ------------|
   |                               |
   |      continúa                 |
```

---

## Blocking call

Una llamada bloqueante puede imaginarse como:

```
resultado = servidor.calcular()
```

Mientras no exista:

```
resultado
```

la parte del cliente que depende de esa llamada no puede continuar.

Esto produce una programación fácil de seguir porque el flujo es secuencial:

```
1. solicitar
2. esperar
3. recibir
4. continuar
```

---

## Requisito de disponibilidad

El modelo síncrono requiere que ambas partes estén disponibles durante la interacción.

El cliente necesita al servidor en línea para obtener la respuesta.

```
Cliente online
+
Servidor online
+
Conexión disponible
```

Si uno de estos elementos falla, la llamada puede no completarse.

---

## Ventajas de la interacción síncrona

El material destaca dos ventajas principales:

- simplicidad para comprender e implementar;
    
- fallas relativamente sencillas de manejar.
    

  

La lógica suele verse como:

```
try:
    resultado = llamada()
catch:
    manejarError()
```

El flujo de control es directo.

---

## Desventajas de la interacción síncrona

El material señala:

- overhead de conexión;
    
- mayor probabilidad de fallas.
    

  

### Overhead:

Cada interacción puede requerir mantener una comunicación activa entre cliente y servidor.

### Mayor exposición a fallas:

Como ambas partes deben estar disponibles simultáneamente, existe una dependencia temporal fuerte.

```
Cliente listo
pero servidor caído
=
operación falla
```

---

## Posibles soluciones

El material menciona:

- transacciones;
    
- interacciones asíncronas.
    

Las transacciones pueden ayudar a controlar operaciones que deben ejecutarse de manera consistente ante errores.

La interacción asíncrona cambia directamente el modelo de comunicación.

---

## Interacción asíncrona

### Concepto:

En una interacción asíncrona, la llamada al servidor no bloquea necesariamente al cliente.

El cliente puede continuar ejecutándose después de enviar la solicitud.

```
Cliente
   |
   | enviar solicitud
   v
Servidor

Cliente continúa trabajando
```

Posteriormente puede comprobar si la respuesta está disponible.

---

## Non-blocking call

Una llamada no bloqueante puede modelarse así:

```
enviarSolicitud()

hacerOtraCosa()

if respuestaLista():
    procesarRespuesta()
```

En lugar de:

```
enviarSolicitud()
esperar()
esperar()
esperar()
respuesta
```

Esto permite aprovechar mejor el tiempo del cliente.

---

## Comprobación posterior del resultado

El material señala que los clientes pueden consultar en diferentes momentos si la respuesta está lista.

Conceptualmente:

```
Cliente:
¿Está lista?

Servidor:
No.

...

Cliente:
¿Está lista?

Servidor:
Sí.
```

También pueden existir otros mecanismos, dependiendo de la arquitectura.

---

## Colas de mensajes

La interacción asíncrona suele implementarse mediante **colas de mensajes**.

```
Cliente
   |
   | mensaje
   v
+----------------+
|      Cola      |
+----------------+
        |
        v
     Servidor
```

El cliente deposita el mensaje.

El servidor puede procesarlo posteriormente.

La existencia de la cola desacopla temporalmente a ambos extremos.

---

## Desacoplamiento temporal

Con una cola:

```
Cliente activo
Servidor temporalmente ocupado
```

no necesariamente implica que la solicitud falle inmediatamente.

La petición puede permanecer almacenada hasta que el servidor pueda procesarla.

Esto permite construir sistemas más flexibles.

---

## Ventajas de la interacción asíncrona

El material presenta varias ventajas.

### Mayor modularidad:

Los componentes pueden depender menos directamente unos de otros.

### Más posibilidades de distribución:

Se facilitan patrones como:

- multicast;
    
- replicación;
    
- agrupamiento de mensajes.
    

### Mejor adaptación a sistemas heterogéneos:

Las interacciones complejas entre sistemas diferentes pueden expresarse de forma más natural utilizando mensajes desacoplados.

---

## Desventaja de la interacción asíncrona

La principal desventaja mencionada es que introduce mayor complejidad en la arquitectura del cliente.

En una llamada síncrona:

```
resultado = llamar()
```

En una solución asíncrona puede ser necesario administrar:

```
identificador de solicitud
cola
estado de procesamiento
respuesta futura
timeout
reintentos
```

Por ello, la flexibilidad adicional tiene un costo de complejidad.

---

## Comparación entre comunicación síncrona y asíncrona

|Característica|Síncrona|Asíncrona|
|---|---|---|
|Cliente espera|Sí|No necesariamente|
|Llamada bloqueante|Sí|No|
|Cliente y servidor deben estar disponibles al mismo tiempo|Generalmente sí|No necesariamente|
|Implementación|Más simple|Más compleja|
|Acoplamiento|Mayor|Menor|
|Uso de colas|No obligatorio|Común|

---

## Modelo de ejecución del servidor

Una vez recibida una solicitud, debe decidirse cómo será ejecutada dentro del servidor.

El material distingue:

- ejecución iterativa;
    
- ejecución concurrente.
    

También presenta dos estrategias para administrar múltiples ejecuciones:

- crear procesos bajo demanda;
    
- utilizar un pool de procesos.
    

  

---

## Ejecución iterativa

### Concepto:

La ejecución iterativa utiliza un único proceso para atender las solicitudes.

El servidor funciona aproximadamente así:

```
while (true) {
    recibir petición
    procesar petición
    enviar respuesta
}
```

El material muestra la misma estructura:

```
receive(...)
extract(...)
do_service(...)
send(...)
```

  

---

## Flujo de un servidor iterativo

```
Cliente A ---> Servidor
                  |
                  | ejecutar A
                  v
              respuesta A

Cliente B ---> espera

Cliente C ---> espera
```

Mientras el servidor atiende una petición, las siguientes deben esperar.

---

## Ventaja del servidor iterativo

Su implementación es sencilla.

Existe básicamente:

```
un proceso
+
una solicitud en ejecución
```

No aparecen muchos de los problemas relacionados con sincronización interna.

---

## Desventaja del servidor iterativo

Si una operación tarda mucho:

```
Request A = 30 segundos
```

entonces:

```
Request B
Request C
Request D
```

deben esperar.

Esto limita considerablemente el rendimiento cuando existe una gran cantidad de clientes.

---

## Ejecución concurrente

### Concepto:

En un servidor concurrente, múltiples solicitudes pueden ejecutarse simultáneamente utilizando diferentes procesos o hilos.

```
Cliente A ---> Proceso 1
Cliente B ---> Proceso 2
Cliente C ---> Proceso 3
```

Esto permite que una operación lenta no bloquee necesariamente a todos los demás clientes.

---

## Creación de procesos bajo demanda

Una primera estrategia consiste en crear un nuevo proceso cuando llega una solicitud.

El servidor principal puede funcionar como un **proxy** o despachador.

El flujo básico es:

```
Cliente
   |
   | request
   v
Proxy
   |
   | create
   v
Nuevo proceso
   |
   | execute
   v
response
```

---

## Funcionamiento del proxy

El proceso principal ejecuta aproximadamente:

```
while (true) {
    receive(...)
    extract(...)
    create_process(...)
}
```

El nuevo proceso ejecuta:

```
do_service(...)
send(...)
exit
```

Así, el proceso principal vuelve rápidamente a recibir nuevas solicitudes.

---

## Ejemplo con varios clientes

```
Cliente A
   |
   v
Proxy ----> Proceso A

Cliente B
   |
   v
Proxy ----> Proceso B

Cliente C
   |
   v
Proxy ----> Proceso C
```

Cada solicitud puede ejecutarse de forma independiente.

---

## Ventaja de crear procesos bajo demanda

Cada solicitud recibe un proceso propio.

Esto proporciona un aislamiento claro y permite concurrencia.

---

## Desventaja de crear procesos bajo demanda

Crear un proceso nuevo puede tener un costo.

La operación requiere:

```
crear proceso
asignar memoria
inicializar recursos
programar ejecución
destruir proceso
```

Si llegan miles de solicitudes, crear un proceso para cada una puede ser costoso.

---

## Pool de procesos

Otra estrategia consiste en crear previamente un conjunto de procesos disponibles.

Este conjunto se denomina **pool de procesos**.

Por ejemplo:

```
Pool

Proceso 1: libre
Proceso 2: libre
Proceso 3: ocupado
Proceso 4: libre
```

Cuando llega una petición, el servidor selecciona uno de los procesos disponibles.

---

## Dispatcher

En este modelo aparece un **dispatcher**, encargado de asignar las solicitudes.

```
Cliente
   |
   | request
   v
Dispatcher
   |
   +--> Worker 1
   +--> Worker 2
   +--> Worker 3
```

El servidor principal recibe:

```
client_id
service_id
params
```

y posteriormente ejecuta:

```
dispatch(...)
```

para entregar la petición a un proceso disponible.

---

## Funcionamiento del pool

Supóngase:

```
Pool = 3 procesos
```

Llegan tres peticiones:

```
A
B
C
```

La asignación puede ser:

```
A -> Worker 1
B -> Worker 2
C -> Worker 3
```

Si llega:

```
D
```

cuando todos están ocupados, puede esperar hasta que uno termine.

```
Worker 2 termina B
        |
        v
Worker 2 ejecuta D
```

---

## Ventajas del pool de procesos

La principal ventaja es evitar la creación constante de procesos.

Los workers ya existen.

Por tanto:

```
sin pool:
request -> crear proceso -> ejecutar -> destruir

con pool:
request -> seleccionar proceso -> ejecutar
```

Esto puede reducir significativamente el costo de administración.

---

## Limitación del pool

El número de procesos disponibles es finito.

Si existen:

```
10 workers
```

y llegan:

```
100 solicitudes simultáneas
```

solo 10 pueden ejecutarse inmediatamente.

Las demás deben esperar.

Por tanto, el tamaño del pool influye directamente en:

```
rendimiento
uso de memoria
latencia
capacidad máxima
```

---

## Comparación de modelos de ejecución

|Modelo|Procesos|Concurrencia|Costo|
|---|---|---|---|
|Iterativo|1|No|Bajo|
|Bajo demanda|Uno nuevo por solicitud|Sí|Alto al crear procesos|
|Pool|Conjunto precreado|Sí|Menor costo por solicitud|

---

## Visión integrada de las características cliente-servidor

Las tres dimensiones pueden combinarse independientemente.

Por ejemplo, podría existir un servidor:

```
con datos persistentes
+
stateful
+
comunicación síncrona
+
orientada a conexión
+
pool de procesos
```

Otra aplicación podría utilizar:

```
sin persistencia
+
stateless
+
comunicación asíncrona
+
datagramas
+
ejecución concurrente
```

No existe una única arquitectura cliente-servidor.

La arquitectura concreta surge de las decisiones tomadas en cada dimensión.

---

## Ejemplo 1: Servicio matemático

Un servicio que calcula:

```
f(x)
```

puede ser:

```
sin persistencia
stateless
síncrono
concurrente
```

Cada llamada depende únicamente de sus parámetros.

Esto permite distribuir fácilmente el trabajo entre múltiples procesos.

---

## Ejemplo 2: Servidor de base de datos

Un servidor de base de datos utiliza:

```
datos persistentes
```

y debe controlar:

```
concurrencia
transacciones
fallas
```

La arquitectura debe ser mucho más cuidadosa porque las operaciones modifican un estado compartido.

---

## Ejemplo 3: Servicio de archivos secuencial

Un servicio que mantiene la posición de lectura de cada cliente es:

```
stateful
```

porque:

```
read siguiente
```

depende de:

```
posición anterior
```

El servidor debe conservar la información de sesión correspondiente.

---

## Ejemplo 4: Sistema basado en mensajes

Un sistema que coloca tareas en una cola puede utilizar:

```
comunicación asíncrona
```

El productor puede enviar:

```
procesarImagen(123)
```

y continuar trabajando.

Un consumidor procesa la tarea posteriormente.

---

## Relación entre estado y escalabilidad

Los servicios stateless suelen facilitar la distribución del trabajo.

Supóngase que existen tres servidores:

```
Servidor A
Servidor B
Servidor C
```

Si cada solicitud es independiente, puede enviarse cualquier petición a cualquier servidor.

```
Request 1 -> A
Request 2 -> C
Request 3 -> B
Request 4 -> A
```

No importa cuál recibió las solicitudes anteriores.

Esto facilita el balanceo de carga.

---

## Statefulness y afinidad

En un servicio stateful, puede ser necesario que el cliente continúe interactuando con el mismo servidor.

Por ejemplo:

```
Cliente
   |
   | petición 1
   v
Servidor A
   |
   | guarda estado
```

La siguiente petición debería regresar a:

```
Servidor A
```

porque:

```
Servidor B
```

podría no conocer ese estado.

Esto aumenta el acoplamiento entre cliente y servidor.

---

## Relación entre asincronía y desacoplamiento

La comunicación asíncrona puede reducir dos tipos de dependencia.

### Desacoplamiento temporal:

Cliente y servidor no necesitan estar activos exactamente al mismo tiempo.

### Desacoplamiento de velocidad:

Un productor rápido puede generar mensajes mientras un consumidor más lento los procesa gradualmente.

```
Productor rápido
      |
      v
    Cola
      |
      v
Consumidor lento
```

La cola absorbe temporalmente la diferencia de velocidad.

---

## Relación entre concurrencia y estado

La concurrencia mejora la capacidad del servidor para atender múltiples clientes, pero introduce nuevos problemas cuando existe estado compartido.

Por ejemplo:

```
Thread A ----\
              > saldo
Thread B ----/
```

Si ambos modifican:

```
saldo
```

debe existir alguna forma de coordinación.

Por tanto:

```
más concurrencia
```

puede significar:

```
más rendimiento
```

pero también:

```
más necesidad de sincronización
```

---

## Criterios para elegir una arquitectura cliente-servidor

Las decisiones dependen del problema.

Debe preguntarse:

```
¿Se necesita conservar estado?

¿Las peticiones dependen unas de otras?

¿Puede tolerarse pérdida de mensajes?

¿El cliente puede esperar?

¿Cuántos clientes pueden conectarse?

¿Cuánto tarda cada operación?

¿Debe soportarse concurrencia?

¿Cuánto cuesta crear procesos?
```

Las respuestas determinan la arquitectura adecuada.

Una petición cliente-servidor puede verse finalmente como:

```
   v
```

```
request -> response
```

puede ocultar muchas decisiones arquitectónicas.

# Ideas fundamentales de la clase

El modelo cliente-servidor separa a una entidad que solicita servicios de otra que los ejecuta. Aunque la interacción básica consiste en una petición y una respuesta, la arquitectura real depende de cómo se administre el estado, cómo se comuniquen las entidades y cómo se ejecuten las solicitudes en el servidor.

Un servidor puede trabajar con datos persistentes o no persistentes. Cuando no existe persistencia, cada ejecución depende principalmente de sus parámetros, lo que facilita la tolerancia a fallas y el control de concurrencia. Cuando existen datos persistentes, las operaciones pueden modificar el contexto del servidor y deben tratarse cuidadosamente los accesos concurrentes y la recuperación ante fallas.

Un servicio stateless procesa cada solicitud de manera independiente, sin necesitar recordar las solicitudes anteriores del cliente. Un servicio stateful, por el contrario, utiliza un estado creado por operaciones previas, por lo que el orden entre solicitudes es importante.

La comunicación también puede ser orientada a conexión o utilizar datagramas. Los mecanismos orientados a conexión proporcionan garantías mayores sobre entrega, orden y control de errores, mientras que los datagramas siguen una filosofía de best effort y pueden sufrir pérdidas, duplicaciones o alteraciones en el orden.

En una interacción síncrona, el cliente queda bloqueado mientras espera la respuesta del servidor. Este modelo es sencillo, pero crea una dependencia temporal fuerte entre ambos extremos. En una interacción asíncrona, el cliente puede continuar trabajando después de enviar la solicitud, aunque la arquitectura se vuelve más compleja y suele requerir mecanismos como colas de mensajes.

El servidor puede atender las solicitudes de forma iterativa utilizando un único proceso o de forma concurrente utilizando varios procesos o hilos. La concurrencia mejora la capacidad de servicio, pero puede aumentar los problemas relacionados con recursos compartidos.

En un modelo concurrente, los procesos pueden crearse bajo demanda o mantenerse previamente en un pool. Crear un proceso por petición proporciona aislamiento, pero introduce un costo de creación. Los pools reutilizan procesos existentes y reducen ese costo, aunque tienen una capacidad máxima determinada por el tamaño del conjunto.

Finalmente, las características de estado, comunicación y ejecución son dimensiones independientes que pueden combinarse de diferentes maneras. Diseñar una arquitectura cliente-servidor consiste precisamente en seleccionar la combinación adecuada para las necesidades de cada sistema.

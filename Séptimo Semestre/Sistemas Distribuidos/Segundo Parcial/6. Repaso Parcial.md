## Introducción

La arquitectura funcional de los sistemas distribuidos estudia cómo se organizan, comunican y coordinan las distintas entidades que participan en un sistema distribuido. A lo largo de este bloque aparecen varios conceptos que se conectan directamente entre sí: **middleware, modelo cliente-servidor, RPC, gestión de parámetros, IDL, XDR, RMI y modelos de ejecución del servidor**.

La lógica completa del tema puede entenderse como una progresión:

```
Sistema distribuido
        |
        v
Necesidad de ocultar complejidad
        |
        v
Middleware
        |
        v
Modelo cliente-servidor
        |
        v
RPC
        |
        v
Serialización + IDL + XDR
        |
        v
RMI
        |
        v
Objetos distribuidos
```

El punto central de todo el bloque consiste en **hacer que una interacción distribuida parezca más sencilla de lo que realmente es**, ocultando detalles de red, representación de datos, localización, sincronización y ejecución.

---

## Middleware

### Definición:

El **middleware** es una capa de software situada entre las aplicaciones y el sistema operativo de red.

Su función consiste en proporcionar un nivel de abstracción más alto para que las aplicaciones distribuidas puedan comunicarse sin manejar directamente todos los detalles de la infraestructura.

La estructura conceptual es:

```
Aplicación distribuida
        |
        v
Middleware
        |
        v
Sistema operativo / red
```

El middleware intenta esconder:

- distribución;
    
- heterogeneidad;
    
- diferencias de implementación;
    
- detalles de comunicación.
    

### Objetivo principal del middleware:

El middleware permite que un sistema distribuido pueda verse de forma más uniforme.

Aunque existan:

```
máquinas diferentes
sistemas operativos diferentes
lenguajes diferentes
redes diferentes
```

la aplicación puede trabajar mediante interfaces comunes.

Su propósito es reducir el acoplamiento entre la lógica de la aplicación y los mecanismos de bajo nivel.

### Funciones del middleware:

#### Ocultar distribución

Una aplicación no debería tener que preocuparse constantemente por saber si un recurso es local o remoto.

#### Ocultar heterogeneidad

Se busca facilitar la interoperabilidad entre sistemas diferentes.

#### Proporcionar interfaces de alto nivel

En lugar de trabajar directamente con paquetes o sockets, el desarrollador puede utilizar abstracciones como:

```
procedimientos
métodos
colas
objetos
```

#### Proporcionar servicios comunes

Puede ofrecer funciones reutilizables para múltiples aplicaciones distribuidas.

### Clasificación del middleware:

El middleware puede analizarse utilizando dos criterios principales:

```
1. Propiedades de comunicación
2. Arquitectura e interfaces
```

## Propiedades de comunicación

### Topología fija:

Las entidades permanecen en localizaciones relativamente estables.

```
Servidor A ---- Servidor B
      |
   Cliente
```

### Topología variable:

Las entidades pueden conectarse, desconectarse o cambiar de localización.

```
Nodo A
Nodo B
Nodo C entra/sale dinámicamente
```

## Sistemas predecibles y no predecibles

### Predecible:

El sistema puede establecer límites conocidos sobre ciertos factores de rendimiento.

Esto es importante en aplicaciones de tiempo real.

### No predecible:

El rendimiento puede variar según:

```
carga
congestión
uso compartido
estado de la red
```

Internet es el ejemplo típico.

---

## Combinaciones principales

| Topología | Comportamiento | Ejemplo                 |
| --------- | -------------- | ----------------------- |
| Fija      | No predecible  | Internet                |
| Fija      | Predecible     | Tiempo real             |
| Variable  | No predecible  | Sistemas móviles        |
| Variable  | Predecible     | No considerada habitual |

Una idea importante es:

> Una topología fija no implica que el comportamiento temporal sea predecible.

## Modelo cliente-servidor

El modelo cliente-servidor divide el sistema en dos roles principales:

```
Cliente:
consume un servicio

Servidor:
ofrece un servicio
```

La interacción básica es:

```
Cliente                  Servidor

   |                        |
   |------ request -------->|
   |                        |
   |       ejecución        |
   |                        |
   |<----- response --------|
```

Cliente y servidor son principalmente **roles de ejecución**.

Pueden encontrarse:

```
en la misma máquina
```

o:

```
en máquinas diferentes
```

Lo importante es quién solicita y quién proporciona el servicio.

---

## Interfaz del servicio

La interfaz define:

```
qué puede hacer el servidor
```

mientras que la implementación define:

```
cómo lo hace
```

Separar ambas permite modificar cliente y servidor con mayor independencia.

```
Interfaz
   |
   v
Contrato común
   |
   +--> Cliente
   |
   +--> Servidor
```

---

## Petición y respuesta

### Request:

Contiene la información necesaria para solicitar una operación.

Puede incluir:

```
nombre del servicio
procedimiento
parámetros
```

### Reply:

Devuelve:

```
resultado
```

o:

```
error
```

## Estado del servidor

Una de las dimensiones más importantes del modelo cliente-servidor es la administración del estado.

Se deben distinguir dos conceptos:

```
persistencia
statefulness
```

### Servidor sin datos persistentes:

Una ejecución depende solamente de sus parámetros.

Ejemplo:

```
f(x)
```

No modifica permanentemente el contexto del servidor.

Ventajas:

```
tolerancia a fallas más simple
concurrencia más sencilla
```

### Servidor con datos persistentes:

Cada ejecución puede modificar información que permanece en el sistema.

Ejemplos:

```
base de datos
sistema de archivos distribuido
```

Esto introduce problemas de:

```
concurrencia
consistencia
recuperación ante fallas
```

### Stateless:

Un servicio stateless no necesita recordar peticiones anteriores de un cliente.

Cada request contiene todo lo necesario para ejecutarse.

```
Request A
Request B
Request C

cada uno independiente
```

El orden generalmente no importa.

Ejemplo:

```
NTP
```

### Stateful:

Un servicio stateful utiliza el estado producido por operaciones previas.

```
Request 1
   |
   v
estado nuevo
   |
   v
Request 2
```

El orden sí importa.

Ejemplos:

```
lectura secuencial de archivo
objeto remoto con estado
```

---

## Persistencia y statefulness no son lo mismo

### Persistencia:

Pregunta:

```
¿Los datos permanecen entre ejecuciones?
```

### Stateful:

Pregunta:

```
¿La solicitud actual depende de solicitudes previas?
```

Un sistema puede tener datos persistentes y atender peticiones de manera stateless.

## Modelo de comunicación

Otra dimensión importante es cómo viajan los mensajes.

Puede ser:

```
orientado a conexión
```

o:

```
datagramas
```

y también:

```
síncrono
```

o:

```
asíncrono
```


### Comunicación orientada a conexión:

Proporciona mayores garantías.

Normalmente:

```
entrega confiable
orden respetado
detección/reintento de errores
```

Conceptualmente:

```
1
2
3

se reciben como:

1
2
3
```

### Comunicación basada en datagramas:

Sigue una estrategia de **best effort**.

Puede ocurrir:

```
pérdida
duplicación
desorden
```

Por ejemplo:

```
Enviado:
1 2 3

Recibido:
2 1 3
```

o:

```
1 3
```

### Interacción síncrona:

El cliente envía una solicitud y espera.

```
Cliente                  Servidor

   |------ request -------->|
   |                        |
   |     bloqueado          |
   |                        |
   |<----- response --------|
```

Es una llamada bloqueante.

Ventajas:

```
simple de comprender
simple de programar
```

Desventajas:

```
mayor acoplamiento temporal
más dependencia de disponibilidad
```

### Interacción asíncrona:

El cliente envía una solicitud y puede continuar.

```
Cliente
   |
   | request
   v
Cola
   |
   v
Servidor

Cliente sigue ejecutándose
```

Suele implementarse mediante colas de mensajes.

Ventajas:

```
desacoplamiento
modularidad
más flexibilidad
```

Desventaja principal:

```
mayor complejidad
```

---

## Modelos de ejecución del servidor

El servidor también puede variar en la forma en que procesa solicitudes.

Existen dos categorías básicas:

```
iterativo
concurrente
```

### Ejecución iterativa:

Utiliza un único proceso.

```
while (true) {
    recibir
    ejecutar
    responder
}
```

Solo atiende una solicitud a la vez.

```
A -> ejecución
B -> espera
C -> espera
```

Ventaja:

```
simplicidad
```

Desventaja:

```
poca capacidad ante múltiples clientes
```

### Ejecución concurrente:

Permite ejecutar múltiples peticiones simultáneamente.

Puede utilizar:

```
procesos
threads
```

Ejemplo:

```
Cliente A -> Worker 1
Cliente B -> Worker 2
Cliente C -> Worker 3
```

---

## Procesos creados bajo demanda

Cada nueva petición genera un nuevo proceso.

```
Request
   |
   v
Proxy
   |
   v
create process
   |
   v
ejecutar
```

Ventaja:

```
aislamiento
```

Desventaja:

```
costo de crear procesos constantemente
```

### Pool de procesos:

Los procesos ya existen antes de recibir peticiones.

```
Pool:
Worker 1
Worker 2
Worker 3
```

Un dispatcher asigna una petición a uno disponible.

```
Request
   |
   v
Dispatcher
   |
   +--> Worker libre
```

Esto reduce el costo de creación repetitiva.

## RPC

### Definición:

**Remote Procedure Call** permite ejecutar un procedimiento remoto con una apariencia similar a una llamada local.

El programador ve:

```
resultado = procedimiento(x, y)
```

pero internamente ocurre:

```
cliente
  |
  v
stub
  |
  v
mensaje
  |
  v
red
  |
  v
servidor
```

### Idea principal de RPC:

RPC intenta proporcionar la ilusión:

```
llamada remota ≈ llamada local
```

Sin embargo, físicamente sigue existiendo comunicación por red.

### Mensajes mínimos en RPC:

Una llamada RPC necesita al menos:

```
1. request
2. reply
```

#### Request

Contiene:

```
procedimiento
parámetros
```

#### Reply

Contiene:

```
resultado
```

o:

```
error
```

### Ventajas de RPC:

Las principales ventajas son:

```
apariencia de llamada local
simplicidad
validación local antes de distribuir
reducción de código de comunicación
```

### Problema principal de RPC:

Una llamada remota no tiene la misma semántica que una llamada local.

Pueden fallar de manera independiente:

```
cliente
servidor
red
```

Supóngase que el cliente no recibe respuesta.

No sabe directamente si:

```
la petición se perdió
el servidor falló
el procedimiento se ejecutó
la respuesta se perdió
la respuesta está retrasada
```

Esta incertidumbre es una característica fundamental de los sistemas distribuidos.

---

## Stub y Skeleton

RPC utiliza dos componentes principales.

### Stub cliente:

Recibe una llamada local y la transforma en comunicación remota.

```
Aplicación
   |
   v
Stub
   |
   v
mensaje
```

### Skeleton servidor:

Recibe el mensaje y reconstruye la llamada al procedimiento real.

```
mensaje
   |
   v
Skeleton
   |
   v
Procedimiento real
```

---

## Flujo completo de RPC

```
Aplicación cliente
       |
       v
Stub cliente
       |
       v
Marshalling
       |
       v
Red
       |
       v
Unmarshalling
       |
       v
Skeleton
       |
       v
Procedimiento servidor
       |
       v
Resultado
       |
       v
Marshalling
       |
       v
Red
       |
       v
Stub cliente
```

### Marshalling:

El **marshalling** convierte parámetros a una representación transmisible.

```
estructura en memoria
       |
       v
secuencia transmisible
```

### Unmarshalling:

Realiza el proceso inverso.

```
secuencia recibida
       |
       v
estructura en memoria
```

## Gestión de parámetros

Cliente y servidor poseen espacios de direccionamiento diferentes.

Esto significa que:

```
un apuntador del cliente
```

no tiene sentido directo en:

```
memoria del servidor
```

Por eso no puede enviarse una dirección de memoria como si fuera un valor universal.

### Apuntadores:

Supóngase:

```
ptr = 0x1000
```

En el cliente:

```
0x1000 -> dato A
```

En el servidor:

```
0x1000 -> otra cosa
```

o puede no existir.

Por ello los apuntadores deben transformarse a representaciones independientes de memoria.

## Serialización

La serialización transforma una estructura compleja en una secuencia lineal.

```
Objeto
├─ nombre
├─ edad
└─ datos

        |
        v

representación serializada
```

El receptor reconstruye una estructura equivalente.

## Problemas de representación

Máquinas diferentes pueden representar datos de forma distinta.

Los problemas incluyen:

```
little endian vs big endian
32 bits vs 64 bits
float vs double
cadenas
estructuras
alineamiento
```

### Little endian y big endian:

Un mismo valor:

```
0x12345678
```

puede almacenarse como:

```
12 34 56 78
```

o:

```
78 56 34 12
```

Si no existe una representación común, el receptor podría interpretar incorrectamente los datos.

### Representación externa común:

La solución general es definir un formato común:

```
Formato cliente
      |
      v
Formato externo común
      |
      v
Formato servidor
```

Esto reduce la dependencia entre arquitecturas.

## XDR

### Definición:

**XDR — External Data Representation** proporciona una representación externa común para transmitir datos.

La estructura es:

```
Formato interno cliente
        |
        v
XDR
        |
        v
Formato de red
        |
        v
XDR
        |
        v
Formato interno servidor
```

### Función de XDR:

XDR ofrece rutinas para convertir:

```
tipos simples
arreglos
cadenas
uniones
estructuras
apuntadores
```

Por ejemplo:

```
xdr_int(...)
xdr_array(...)
```

Una misma rutina puede utilizarse para:

```
encode
```

o:

```
decode
```

dependiendo del modo.

## IDL

### Definición:

**IDL — Interface Definition Language** describe abstractamente la interfaz entre cliente y servidor.

Define:

```
procedimientos
parámetros
resultados
excepciones
modos de paso
```

### Interfaz como contrato:

El IDL actúa como contrato común.

```
Cliente
   |
   v
IDL
   ^
   |
Servidor
```

Ambos deben respetar la misma definición.

### Independencia del IDL:

Un IDL intenta ser independiente de:

```
lenguaje
máquina
representación interna
```

Por ello puede utilizarse para generar código compatible con distintos entornos.

---

## Modos de parámetros

### IN:

Viaja del cliente al servidor.

```
Cliente ---> Servidor
```

### OUT:

Viaja del servidor al cliente.

```
Cliente <--- Servidor
```

### IN-OUT:

Viaja en ambos sentidos.

```
Cliente ---> Servidor
Cliente <--- Servidor
```

### Generación automática de talones:

A partir del IDL puede generarse:

```
stub cliente
skeleton servidor
rutinas de conversión
definiciones comunes
```

Esto automatiza buena parte de la infraestructura RPC.

### rpcgen:

Un ejemplo de herramienta es:

```
rpcgen
```

A partir de:

```
proc.x
```

puede producir:

```
proc_clnt.c
proc_svc.c
proc_xdr.c
proc.h
```

Así se separa:

```
código de aplicación
```

de:

```
código de infraestructura RPC
```

## Designación y ligado

Una llamada remota necesita responder dos preguntas:

```
¿Qué servicio quiero?
¿Dónde está?
```

### Designación:

Identifica el servicio mediante un nombre lógico.

```
"servicio_calculadora"
```

### Ligado:

Asocia ese nombre con una localización real.

```
"servicio_calculadora"
       |
       v
192.168.1.10:4500
```

#### Ligado estático

La ubicación del servidor se conoce desde compilación o configuración inicial.

Ventaja:

```
menos resolución en ejecución
```

Desventaja:

```
menor flexibilidad
```

#### Ligado dinámico

La ubicación se resuelve en tiempo de ejecución.

Puede utilizar un:

```
servicio de nombres
```

El flujo es:

```
Cliente
   |
   | nombre
   v
Servicio de nombres
   |
   | dirección
   v
Servidor
```

#### Ligado a la primera llamada

El servicio de nombres se consulta una sola vez.

```
Primera llamada:
cliente -> nombres -> servidor

Después:
cliente ----------> servidor
```

#### Ligado en cada llamada

Cada petición consulta de nuevo la ubicación.

```
cliente -> nombres -> servidor
cliente -> nombres -> servidor
cliente -> nombres -> servidor
```

Más flexible, pero con mayor costo.

## Directorio

Un servidor puede registrar:

```
<nombre, dirección, puerto>
```

El cliente consulta:

```
<nombre>
```

y recibe:

```
<dirección, puerto>
```

```
programa
   |
   v
portmapper
   |
   v
puerto
```

El material utiliza como puerto fijo del portmapper:

```
111

## RMI

### Definición:

**Remote Method Invocation** extiende RPC hacia objetos.

RPC:

```
procedimiento(x)
```

RMI:

```
objeto.metodo(x)
```

La diferencia es que RMI necesita identificar:

```
objeto
+
método
+
parámetros
```

### Objeto como unidad de distribución:

En RMI, el objeto remoto es una entidad distribuida.

Puede contener:

```
estado
métodos
identidad
```

Esto permite interactuar con un objeto ubicado en otra JVM.

### Java RMI:

Java RMI integra el modelo de objetos distribuidos directamente en Java.

La idea es:

```
objeto remoto
```

se utiliza de una forma parecida a:

```
objeto local
```

aunque la ejecución real ocurra en otra máquina.

### Interfaz Remote:

Una interfaz remota debe:

```
ser pública
extender java.rmi.Remote
```

Por ejemplo:

```
public interface Hello extends Remote
```

### RemoteException:

Cada método remoto debe declarar:

```
throws RemoteException
```

porque la llamada puede fallar por causas distribuidas.

Por ejemplo:

```
red caída
servidor no disponible
objeto remoto inaccesible
```

### Objetos serializables:

Un objeto local enviado mediante RMI se pasa por **valor**.

Debe implementar:

```
Serializable
```

El servidor recibe una copia.

```
Objeto O
   |
   v
serialización
   |
   v
clone_O
```


### Objetos Remote:

Un objeto remoto se pasa por **referencia**.

En lugar de copiar el objeto:

```
Objeto remoto
```

se transmite:

```
referencia remota / stub
```

El receptor continúa interactuando con el mismo objeto.

### Diferencia clave:

```
Serializable
    |
    v
copia

Remote
    |
    v
referencia
```

Esta es una de las ideas más importantes de Java RMI.

### Stub en RMI:

El stub representa localmente al objeto remoto.

El cliente ve:

```
obj.sayHello();
```

pero realmente:

```
obj
 |
 v
stub
 |
 v
red
 |
 v
servidor
 |
 v
objeto remoto
```

### rmiregistry:

Java RMI utiliza un servicio de nombres llamado:

```
rmiregistry
```

El servidor registra:

```
nombre -> referencia remota
```

Por ejemplo:

```
"Hello" -> stub
```

El cliente realiza:

```
lookup("Hello")
```

y obtiene una referencia al objeto.

### Flujo de Java RMI:

```
Servidor:

crear objeto
     |
     v
exportar objeto
     |
     v
obtener stub
     |
     v
registrar en rmiregistry


Cliente:

lookup
   |
   v
obtener stub
   |
   v
llamar método
```

### Ejemplo de interfaz RMI:

```
public interface Hello extends Remote {
    String sayHello() throws RemoteException;
}
```

Esto define el contrato remoto.

###### Ejemplo de cliente:

```
Hello obj =
    (Hello) Naming.lookup("//host:port/Hello");

String msg = obj.sayHello();
```

El código parece local, pero la operación ocurre remotamente.

## RPC frente a RMI

|RPC|RMI|
|---|---|
|Procedimientos|Métodos|
|`f(x)`|`obj.f(x)`|
|Identifica procedimiento|Identifica objeto + método|
|Puede usar IDL externo|Java puede actuar como IDL|
|Parámetros|Parámetros + referencias de objetos|

## Diferencias que deben quedar muy claras

### Stateless vs no persistente:

No persistente:

```
el servidor no conserva datos permanentes
```

Stateless:

```
una petición no depende de las anteriores
```

No son sinónimos.

### Síncrono vs orientado a conexión:

Síncrono:

```

copia

convierte datos a formato transmisible

## Flujo mental para resolver preguntas de examen

Cuando aparezca un problema, conviene preguntarse en este orden:

```
1. ¿Quién es cliente y quién es servidor?

2. ¿Existe estado?

3. ¿El estado es persistente?

4. ¿Las peticiones dependen entre sí?

5. ¿La comunicación es síncrona o asíncrona?

6. ¿La entrega necesita garantías?

7. ¿Cómo ejecuta el servidor las solicitudes?

8. ¿Es un procedimiento remoto o un objeto remoto?

9. ¿Cómo se transmiten los parámetros?

10. ¿Cómo se localiza el servicio?
```

Este razonamiento permite clasificar prácticamente cualquier arquitectura presentada dentro de este bloque.

## Ejemplo integrador

Supóngase un servicio remoto de cuentas bancarias.

El sistema contiene:

```
Cliente bancario
Servidor bancario
Base de datos
```

### Estado:

Los saldos deben conservarse:

```
persistente
```

Las operaciones pueden depender del estado previo:

```
stateful
```

### Comunicación:

Si el cliente ejecuta:

```
retirar(500)
```

y espera inmediatamente el resultado:

```
síncrona
```

### Ejecución:

El servidor atiende miles de clientes:

```
concurrente
```

posiblemente utilizando:

```
pool de procesos o threads
```

### RPC:

La operación podría exponerse como:

```
retirar(cuenta, monto)
```

### RMI:

En un modelo orientado a objetos:

```
cuenta.retirar(monto)
```

### Datos:

Los parámetros deben:

```
serializarse
```

y utilizar una representación compatible.

### Localización:

El cliente debe encontrar:

```
servidor
+
servicio
```

mediante algún mecanismo de designación y ligado.

Este ejemplo integra prácticamente todos los conceptos del parcial.

## Ideas fundamentales de la clase

La arquitectura funcional de los sistemas distribuidos busca ocultar la complejidad de trabajar con entidades ubicadas en diferentes máquinas. El middleware proporciona la capa de abstracción que permite construir interfaces más simples y uniformes sobre una infraestructura heterogénea.

El modelo cliente-servidor organiza la interacción alrededor de un consumidor y un proveedor de servicios. Su comportamiento real depende de tres dimensiones principales: administración del estado, modelo de comunicación y modelo de ejecución.

La distinción entre persistencia y statefulness es fundamental. La persistencia se refiere a si los datos permanecen entre ejecuciones, mientras que statefulness indica si una solicitud depende del estado producido por solicitudes anteriores.

La comunicación puede proporcionar diferentes garantías y puede ser síncrona o asíncrona. El modelo síncrono es más sencillo, pero genera un mayor acoplamiento temporal. El modelo asíncrono permite mayor desacoplamiento mediante mecanismos como colas de mensajes, a costa de una arquitectura más compleja.

La ejecución del servidor puede ser iterativa o concurrente. Los servidores concurrentes pueden crear procesos bajo demanda o utilizar pools, lo que permite atender múltiples solicitudes simultáneamente con distintos costos de administración.

RPC lleva el modelo cliente-servidor a una abstracción de llamada de procedimiento remoto. Para conseguirlo utiliza stubs, skeletons, marshalling, unmarshalling y mecanismos de localización.

Los parámetros no pueden transmitirse como simples referencias de memoria porque cliente y servidor poseen espacios de direccionamiento diferentes. Por ello deben serializarse y representarse de una forma independiente de la arquitectura de las máquinas.

XDR proporciona una representación externa común, mientras que un IDL define el contrato lógico entre cliente y servidor. El IDL describe operaciones y tipos; XDR describe cómo convertir los datos para su transmisión.

RMI extiende RPC al paradigma orientado a objetos. En lugar de invocar únicamente procedimientos remotos, permite ejecutar métodos sobre objetos remotos, manteniendo una identidad y potencialmente un estado asociado.

En Java RMI, los objetos serializables se transmiten por valor, mientras que los objetos remotos se transmiten por referencia. El stub actúa como representante local del objeto remoto y `rmiregistry` permite localizar las referencias mediante nombres.

La idea que conecta todo el parcial es la **transparencia**: el sistema intenta que una interacción distribuida parezca una operación local sencilla. Sin embargo, detrás de esa abstracción siguen existiendo redes, serialización, fallas parciales, localización, concurrencia y múltiples espacios de memoria.

## Introducción

Un sistema distribuido está formado por múltiples elementos de cómputo que colaboran entre sí a través de una red. Aunque estos elementos pueden encontrarse físicamente separados, utilizar sistemas operativos distintos o ejecutarse sobre arquitecturas de hardware diferentes, el objetivo es que puedan trabajar de manera coordinada como parte de un mismo sistema.

Uno de los principales problemas al desarrollar este tipo de sistemas consiste precisamente en manejar toda esa complejidad. Si cada aplicación tuviera que controlar directamente la comunicación por red, conocer las características particulares de cada máquina y resolver por sí misma aspectos como el intercambio de mensajes, la interoperabilidad o la localización de recursos, desarrollar software distribuido sería considerablemente más complicado.

Para solucionar este problema aparece la **capa middleware**, cuya función consiste en proporcionar una abstracción entre las aplicaciones distribuidas y la infraestructura de comunicación subyacente. Sobre esta base pueden construirse posteriormente modelos como **cliente-servidor** y mecanismos de comunicación remota como **RPC** y **RMI**.

---

## Capa middleware

### Concepto de middleware:

El **middleware** es una capa de software situada entre las aplicaciones y el sistema operativo de red. Su propósito es proporcionar servicios que simplifiquen la construcción y ejecución de aplicaciones distribuidas.

Puede visualizarse mediante la siguiente estructura conceptual:

```
+----------------------------------+
|       Aplicación distribuida     |
+----------------------------------+
|            Middleware            |
+----------------------------------+
| Sistema operativo / red / hardware |
+----------------------------------+
```

La aplicación no necesita interactuar directamente con todos los detalles de la red. En su lugar, utiliza las operaciones proporcionadas por el middleware.

Esto introduce un **nivel elevado de abstracción**. Desde el punto de vista del programador, muchas características complejas del sistema distribuido dejan de ser visibles directamente.

Por ejemplo, una aplicación podría solicitar una operación a un servidor remoto sin necesidad de encargarse explícitamente de:

- crear conexiones de red;
    
- construir manualmente los mensajes;
    
- determinar cómo representar los datos;
    
- conocer todos los detalles de la máquina remota;
    
- implementar desde cero los mecanismos necesarios para recibir la respuesta.
    

El middleware intenta que esas operaciones puedan realizarse mediante interfaces de mayor nivel.

### Transparencia:

La idea de **transparencia** consiste en ocultar al usuario o al programador determinados detalles propios de la distribución.

Un recurso podría encontrarse en otra computadora y, aun así, utilizarse mediante una interfaz semejante a la que se emplearía para acceder a un recurso local.

Esto no significa que la red desaparezca realmente. La comunicación continúa existiendo y sigue teniendo costos, retrasos y posibles errores. Lo que cambia es el nivel desde el cual se observa el sistema.

La aplicación puede trabajar con una abstracción más sencilla mientras el middleware se encarga de buena parte de la complejidad de comunicación.

## Utilidad del middleware

El middleware puede utilizarse en diferentes escenarios en los que varios sistemas o componentes necesitan colaborar.

### Reutilización de sistemas legados:

Un **sistema legado** es un sistema que ya existe y que normalmente continúa utilizándose porque contiene funcionalidad importante para una organización.

El problema aparece cuando ese sistema fue diseñado utilizando tecnologías antiguas o interfaces incompatibles con aplicaciones modernas.

El middleware puede actuar como intermediario entre el sistema legado y las nuevas aplicaciones.

```
Aplicación moderna
        |
        v
    Middleware
        |
        v
Sistema legado
```

De esta manera, no necesariamente resulta obligatorio modificar completamente el sistema antiguo. Puede agregarse una capa capaz de adaptar sus funciones a interfaces nuevas.

### Sistemas de mediación:

En un sistema de mediación, diferentes aplicaciones o fuentes de información necesitan intercambiar datos aunque utilicen estructuras, protocolos o representaciones diferentes.

El middleware puede encargarse de facilitar esta interacción.

La aplicación que solicita información no necesita conocer necesariamente todos los detalles internos de la aplicación que la proporciona.

### Arquitecturas basadas en componentes:

En una arquitectura basada en componentes, diferentes partes del software son desarrolladas como unidades relativamente independientes.

El middleware proporciona mecanismos mediante los cuales estos componentes pueden localizarse, comunicarse y utilizar servicios entre ellos.

Esto resulta especialmente útil cuando los componentes están distribuidos entre diferentes computadoras.

### Adaptación de clientes mediante proxies:

Un **proxy** puede actuar como intermediario entre un cliente y otro elemento del sistema.

Conceptualmente:

```
Cliente
   |
   v
 Proxy
   |
   v
Servidor
```

Para el cliente, el proxy puede presentar una interfaz determinada mientras internamente se encarga de adaptar la comunicación necesaria para interactuar con el servidor.

Estos escenarios —reutilización de sistemas legados, mediación, arquitecturas de componentes y adaptación mediante proxies— aparecen como ejemplos directos de utilización del middleware.

## Funciones principales del middleware

### Ocultar la distribución y la heterogeneidad:

Una de las funciones más importantes consiste en **esconder la distribución y la heterogeneidad** del sistema.

La **distribución** significa que los componentes pueden encontrarse físicamente en diferentes máquinas.

La **heterogeneidad** significa que esos componentes pueden ser distintos entre sí.

Las diferencias pueden aparecer en múltiples niveles:

```
Hardware diferente
        ↓
Sistemas operativos diferentes
        ↓
Lenguajes o plataformas diferentes
        ↓
Representaciones de datos diferentes
        ↓
Protocolos diferentes
```

El middleware busca proporcionar una interfaz común que permita trabajar con esas diferencias sin obligar al desarrollador a resolver cada una manualmente.

### Proporcionar interfaces de alto nivel:

En lugar de programar directamente sobre mecanismos de red de bajo nivel, el desarrollador recibe primitivas e interfaces más cercanas al problema que desea resolver.

Estas interfaces ayudan a que las aplicaciones distribuidas puedan:

- **interoperar**, es decir, comunicarse entre sistemas diferentes;
    
- **reutilizarse**, evitando reconstruir funcionalidad existente;
    
- **portarse**, facilitando su ejecución sobre otros entornos;
    
- **componerse**, combinando diferentes elementos para construir sistemas mayores.
    

Por tanto, el middleware no solamente facilita la comunicación. También ayuda a estructurar el desarrollo del sistema distribuido.

### Proporcionar servicios comunes:

Muchos sistemas distribuidos necesitan resolver problemas similares.

En lugar de implementar estas capacidades repetidamente dentro de cada aplicación, el middleware puede proporcionar servicios comunes de propósito general.

La idea fundamental puede representarse de la siguiente forma:

```
Aplicación A ─┐
Aplicación B ─┼──> Servicios comunes del middleware
Aplicación C ─┘
```

Esto reduce la duplicación de trabajo y establece mecanismos comunes para distintas aplicaciones.

## Clasificación del middleware

No todos los middlewares funcionan de la misma manera. Para estudiarlos pueden utilizarse principalmente dos criterios:

1. las **propiedades de la infraestructura de comunicación**;
    
2. la **arquitectura global y las interfaces proporcionadas**.
    

Estos son los dos criterios de clasificación establecidos en el material.

---

## Propiedades de la infraestructura de comunicación

La infraestructura puede analizarse desde dos perspectivas principales:

```
Movilidad de las entidades
        +
Predictibilidad del sistema
```

La combinación de ambas propiedades permite caracterizar distintos tipos de sistemas distribuidos.

### Topología fija:

En una **topología fija**, las entidades del sistema permanecen en localizaciones determinadas y la configuración de la red no cambia de manera significativa.

Por ejemplo:

```
Servidor A ---- Servidor B
     |
     |
 Cliente C
```

Si estas entidades permanecen siempre en las mismas localizaciones y mantienen una estructura estable, puede considerarse que existe una topología fija.

Esto no implica que la red sea necesariamente rápida o completamente predecible. Solamente indica que las entidades no cambian libremente su posición dentro del sistema.

### Topología variable:

En una **topología variable**, algunas o todas las entidades pueden:

- cambiar de localización;
    
- conectarse;
    
- desconectarse.
    

La estructura del sistema puede, por tanto, modificarse dinámicamente.

Un dispositivo móvil constituye un ejemplo sencillo: puede conectarse a una red, desplazarse, cambiar su punto de acceso o desconectarse completamente.

```
Instante 1:

A ---- B ---- C

Instante 2:

A ---- B

           C desconectado
```

El software debe ser capaz de funcionar pese a estos cambios.

---

## Predictibilidad

Además de conocer si las entidades permanecen fijas o pueden cambiar, debe analizarse qué tan predecible es el comportamiento de la infraestructura.

### Características predecibles:

Un sistema tiene **características predecibles** cuando pueden establecerse límites conocidos relacionados con determinados factores de eficiencia.

Esto resulta particularmente importante cuando una aplicación necesita garantizar ciertos tiempos de respuesta.

Por ejemplo, si una operación debe completarse antes de un límite determinado, el sistema necesita ofrecer garantías suficientemente conocidas para poder asegurar dicho comportamiento.

### Características no predecibles:

Un sistema presenta **características no predecibles** cuando no pueden establecerse con certeza esos límites.

El rendimiento puede depender de factores como:

- carga de la red;
    
- cantidad de usuarios;
    
- utilización de recursos compartidos;
    
- congestión;
    
- actividad de otros dispositivos.
    

Internet constituye un ejemplo claro.

Un mensaje puede llegar rápidamente en una determinada situación y tardar más en otra, aun cuando cliente y servidor permanezcan en las mismas ubicaciones.

---

## Combinación de las propiedades de comunicación

Las propiedades anteriores pueden combinarse para producir diferentes clases de sistemas.

|Topología|Comportamiento|Ejemplo característico|
|---|---|---|
|Fija|No predecible|Comunicación mediante Internet|
|Fija|Predecible|Sistemas especializados de tiempo real|
|Variable|No predecible|Dispositivos móviles y ambientes ubicuos|
|Variable|Predecible|Categoría considerada vacía en el material|

Estas combinaciones se presentan explícitamente como parte de la clasificación de la infraestructura.

### Sistema fijo y no predecible:

Este es señalado como el caso más frecuente.

Las entidades pueden encontrarse en lugares definidos, pero el rendimiento de la comunicación continúa siendo difícil de predecir.

Internet representa un buen ejemplo.

```
Cliente fijo
     |
     | Internet
     |
Servidor fijo
```

El cliente y el servidor no necesitan cambiar de ubicación para que el tiempo de transmisión varíe.

La congestión, la carga de los nodos intermedios o las condiciones de la red pueden modificar el comportamiento.

La lección importante es:

> **Una topología fija no implica automáticamente un rendimiento predecible.**

Son propiedades diferentes.

### Sistema fijo y predecible:

Aquí las entidades permanecen en lugares determinados y, además, el sistema ha sido construido para ofrecer determinadas garantías de funcionamiento.

Este tipo de infraestructura puede utilizarse en aplicaciones especialmente demandantes, entre ellas los **sistemas de tiempo real**.

En estos sistemas no solamente importa obtener una respuesta correcta.

También importa **cuándo** se obtiene la respuesta.

Una respuesta correcta producida después de su límite temporal puede dejar de ser útil.

### Sistema variable y no predecible:

Este caso aparece cuando existen entidades móviles y, además, no puede garantizarse completamente el comportamiento temporal del sistema.

Entre los ejemplos señalados se encuentran:

- PDAs;
    
- teléfonos celulares;
    
- ambientes ubicuos.
    

Un dispositivo puede aparecer o desaparecer dinámicamente de la red mientras las condiciones de comunicación también varían.

Esto introduce dos fuentes de incertidumbre simultáneas:

```
Incertidumbre espacial:
¿Dónde está la entidad?

            +

Incertidumbre temporal:
¿Cuánto tardará la comunicación?
```

### Sistema variable y predecible:

El material señala que, dadas las tecnologías de comunicación consideradas, esta categoría se encuentra vacía.

Conceptualmente implicaría permitir cambios dinámicos de ubicación o conexión y, al mismo tiempo, mantener límites de comportamiento perfectamente predecibles.

## Arquitectura global e interfaces

Además de estudiar la infraestructura de comunicación, el middleware puede analizarse según la arquitectura que proporciona a las aplicaciones.

En este caso aparecen tres funciones particularmente importantes:

- administrador de entidades;
    
- proveedor de estructura;
    
- proveedor de interfaces.
    

  

### Middleware como administrador de entidades:

El middleware puede administrar distintos tipos de entidades.

Estas entidades pueden diferir en:

- definición;
    
- propiedades;
    
- comportamiento;
    
- formas de comunicación.
    

Entre los ejemplos mencionados se encuentran:

```
Objetos
Agentes
Componentes
```

El middleware establece los mecanismos mediante los cuales estas entidades existen e interactúan dentro del sistema distribuido.

### Middleware como proveedor de estructura:

Otro aspecto importante consiste en determinar los **roles** de las entidades.

En algunas arquitecturas existen roles claramente diferenciados:

```
Cliente
Servidor
Suscriptor
Proveedor
```

Un servidor proporciona un servicio y un cliente lo consume.

Un proveedor publica cierta información y un suscriptor manifiesta interés en recibirla.

Sin embargo, no todas las arquitecturas requieren jerarquías rígidas.

En una arquitectura **peer-to-peer o P2P**, diferentes entidades pueden encontrarse al mismo nivel y asumir distintos roles según la situación.

```
Nodo A <------> Nodo B
   ^               |
   |               v
Nodo D <------> Nodo C
```

Un mismo nodo puede consumir recursos en un momento y proporcionarlos posteriormente.

Por ello, la estructura impuesta por el middleware influye directamente sobre cómo se organiza el sistema distribuido.

---

## Middleware como proveedor de interfaces

El middleware también define **cómo se realiza la comunicación** entre las entidades.

Una distinción esencial se encuentra entre comunicación **síncrona** y **asíncrona**.

### Comunicación síncrona:

En una comunicación síncrona existe una relación directa entre la solicitud de una operación y la espera de su resultado.

El flujo conceptual es:

```
Cliente                  Servidor
   |                         |
   |------ petición -------->|
   |                         |
   |       procesamiento     |
   |                         |
   |<----- respuesta --------|
   |                         |
```

El cliente envía una petición y normalmente espera la respuesta antes de continuar con la parte de su ejecución que depende de ese resultado.

Entre los paradigmas síncronos mencionados se encuentran:

- RPC;
    
- RMI.
    

### Comunicación asíncrona:

En una comunicación asíncrona, el emisor puede enviar información sin que necesariamente tenga que esperar de manera inmediata a que el receptor la procese y conteste.

Ejemplos indicados en el material:

- colas de mensajes;
    
- sistemas **publish-subscribe**.
    

Una cola podría funcionar conceptualmente así:

```
Productor
    |
    v
+-----------+
|   Cola    |
+-----------+
    |
    v
Consumidor
```

El productor deposita un mensaje y puede continuar trabajando. Posteriormente, el consumidor procesa el mensaje.

Esta diferencia entre sincronía y asincronía afecta profundamente la arquitectura y el comportamiento de una aplicación distribuida.

## Modelo cliente-servidor

El **modelo cliente-servidor** constituye una de las arquitecturas fundamentales de los sistemas distribuidos.

Se basa en la existencia de dos tipos principales de entidades de ejecución:

- un **servidor**, que ofrece un servicio;
    
- un **cliente**, que utiliza ese servicio.
    

  

Su estructura básica puede representarse como:

```
+---------+          +----------+
| Cliente | -------> | Servidor |
+---------+          +----------+
   solicita             ofrece
   servicio             servicio
```

La diferencia entre ambos no está determinada exclusivamente por la computadora en la que se ejecutan, sino por el **papel que desempeñan dentro de la interacción**.

---

## Cliente

### Función del cliente:

El cliente representa a la entidad que necesita utilizar una función proporcionada por otra entidad.

Por tanto, inicia una interacción solicitando un servicio.

Ejemplos conceptuales pueden ser:

```
Cliente → "Dame esta información"
Cliente → "Ejecuta esta operación"
Cliente → "Guarda estos datos"
Cliente → "Calcula este resultado"
```

El cliente conoce la interfaz mediante la cual puede solicitar el servicio, aunque no necesariamente conoce la implementación interna utilizada por el servidor.

---

## Servidor

### Función del servidor:

El servidor es la entidad encargada de proporcionar el servicio solicitado.

Normalmente permanece disponible para recibir peticiones de uno o más clientes.

Conceptualmente:

```
                +----------+
Cliente A ----->|          |
Cliente B ----->| Servidor |
Cliente C ----->|          |
                +----------+
```

Esto permite centralizar determinados recursos o funciones y compartirlos entre múltiples clientes.

---

## Separación lógica y separación física

Cliente y servidor constituyen dos **entidades de ejecución diferentes**, pero esto no obliga a que estén siempre en computadoras físicamente diferentes.

El material señala explícitamente que generalmente se encuentran en máquinas distintas, aunque esto no es obligatorio.

Por ejemplo, pueden existir dos situaciones:

```
CASO 1: Misma máquina

Computadora A
+----------------------+
| Cliente              |
| Servidor             |
+----------------------+


CASO 2: Máquinas diferentes

Computadora A            Computadora B
+----------+              +----------+
| Cliente  | ------------>| Servidor |
+----------+              +----------+
```

Por tanto, **cliente-servidor describe principalmente una relación arquitectónica entre entidades**, no simplemente una separación física entre computadoras.

---

## Interfaz del servicio

Uno de los conceptos más importantes del modelo consiste en separar la **interfaz del servicio** de su **implementación**.

La interfaz establece qué puede solicitar el cliente.

La implementación establece cómo realiza internamente esa operación el servidor.

Por ejemplo:

```
Interfaz:

calcularTotal(datos) → resultado
```

El cliente necesita conocer que existe la operación `calcularTotal` y qué información debe proporcionar.

Sin embargo, no tendría por qué conocer si el servidor implementa el cálculo utilizando:

- un algoritmo determinado;
    
- una base de datos;
    
- otro servicio remoto;
    
- diferentes estructuras internas.
    

Esto produce una separación:

```
QUÉ puede hacerse
       |
    Interfaz
       |
--------------------
       |
Implementación
       |
CÓMO se realiza
```

La definición de la interfaz del servicio proporciona así independencia con respecto a su implementación.

---

## Petición y respuesta

La interacción cliente-servidor puede modelarse mediante el intercambio de dos clases fundamentales de mensajes:

1. **petición o request**;
    
2. **respuesta o reply**.
    

  

### Petición o request:

La petición representa la solicitud enviada por el cliente.

Puede incluir información como:

- servicio requerido;
    
- nombre de un procedimiento;
    
- parámetros necesarios;
    
- código u operación que debe ejecutarse, dependiendo del modelo utilizado.
    

Conceptualmente:

```
REQUEST

Operación: obtenerUsuario
Parámetro: id = 25
```

El cliente expresa lo que desea que realice el servidor.

### Respuesta o reply:

Después de procesar la petición, el servidor genera una respuesta.

Esta respuesta puede contener:

- el resultado solicitado;
    
- información producida por la operación;
    
- un indicador de error.
    

Por ejemplo:

```
REQUEST:
obtenerUsuario(25)

REPLY:
Usuario encontrado
```

o:

```
REQUEST:
obtenerUsuario(999)

REPLY:
Error: usuario inexistente
```

La existencia del reply es importante porque no todas las operaciones pueden ejecutarse correctamente.

La respuesta permite comunicar tanto el éxito como un eventual error.

## Ejecución síncrona en el modelo cliente-servidor

El modelo mostrado utiliza una **ejecución síncrona**.

La secuencia abstracta es:

```
CLIENTE                         SERVIDOR

   |                               |
   |--------- petición ----------->|
   |                               |
   |              ejecuta          |
   |            operación          |
   |                               |
   |<-------- respuesta -----------|
   |                               |
```

Puede comprenderse como una llamada lógica:

```
Cliente:

resultado = solicitarServicio()
            |
            | espera
            v

Servidor:

recibe()
procesa()
responde()
```

El cliente realiza una petición y la parte de su ejecución que depende de esa operación queda a la espera del resultado.

El servidor:

1. recibe la petición;
    
2. interpreta la operación solicitada;
    
3. ejecuta el servicio;
    
4. genera una respuesta;
    
5. devuelve el resultado al cliente.
    

Esta abstracción de **petición → ejecución → respuesta** constituye la base sobre la cual pueden construirse mecanismos posteriores como RPC y RMI.

---

## Estructuración del modelo cliente-servidor

El modelo presenta varias características arquitectónicas importantes.

### Funciones bien definidas:

Cliente y servidor desempeñan responsabilidades diferenciadas.

El cliente se concentra principalmente en consumir el servicio.

El servidor se concentra en proporcionarlo.

Esta división permite evitar que ambos componentes tengan que resolver exactamente las mismas responsabilidades.

```
Cliente:
solicita

Servidor:
procesa y ofrece
```

### Separación entre servicio y realización:

La interfaz define el servicio disponible mientras que el servidor contiene su realización concreta.

Esto reduce el acoplamiento entre ambas partes.

Un cliente puede continuar utilizando una operación siempre que la interfaz siga siendo compatible, aunque la implementación del servidor cambie internamente.

### Modificación independiente:

Gracias a esa separación, cliente y servidor pueden modificarse o reemplazarse independientemente, siempre que se conserve el contrato establecido entre ambos.

Por ejemplo:

```
Versión inicial

Cliente A ---> Servidor v1


Después

Cliente A ---> Servidor v2
```

Si `Servidor v2` conserva la interfaz que utiliza `Cliente A`, el cliente no necesita conocer cómo cambió la implementación interna.

Del mismo modo, otro cliente podría utilizar el mismo servicio:

```
Cliente A ----\
Cliente B -----+----> Servidor
Cliente C ----/
```

---

## Protección en cliente-servidor

### Dominios de protección diferentes:

El material destaca que cliente y servidor pueden ejecutarse dentro de **dominios de protección diferentes**.

Un dominio de protección establece qué recursos puede utilizar una entidad y bajo qué permisos.

Separar cliente y servidor permite que un cliente no tenga necesariamente acceso directo a todos los recursos internos utilizados por el servidor.

En lugar de ello, solamente puede solicitar las operaciones que el servidor expone mediante su interfaz.

Conceptualmente:

```
CLIENTE
Dominio de protección A

      |
      | Interfaz permitida
      v

SERVIDOR
Dominio de protección B

Base de datos
Archivos
Recursos internos
```

El cliente utiliza el servicio sin recibir automáticamente acceso completo a los recursos internos del servidor.

---

## Administración de recursos

### Servidor compartido:

Otra ventaja importante del modelo es que un mismo servidor puede utilizarse por múltiples clientes.

```
Cliente 1 ----\
Cliente 2 -----\
Cliente 3 ------> Servidor ---> Recurso
Cliente 4 -----/
Cliente 5 ----/
```

Esto permite concentrar la administración de determinados recursos.

En lugar de que cada cliente mantenga una copia independiente del recurso o implemente por separado la misma funcionalidad, todos pueden acceder al servicio ofrecido por el servidor.

El servidor se convierte entonces en un punto encargado de controlar y compartir esos recursos.

---

## Relación entre middleware y cliente-servidor

Middleware y cliente-servidor representan conceptos relacionados, pero no equivalentes.

El **cliente-servidor** describe principalmente una forma de estructurar las entidades:

```
Cliente → solicita
Servidor → proporciona
```

El **middleware** proporciona mecanismos que permiten implementar y simplificar la comunicación entre esas entidades.

Una arquitectura completa puede visualizarse así:

```
           CLIENTE
              |
       API / interfaz
              |
        Middleware
              |
        Comunicación
              |
        Middleware
              |
       Implementación
              |
           SERVIDOR
```

El middleware puede ocultar los detalles de distribución mientras cliente y servidor conservan sus roles arquitectónicos.

Esta relación prepara directamente el estudio de mecanismos como **RPC** y **RMI**, los cuales permiten llevar la abstracción cliente-servidor hacia llamadas a procedimientos o métodos que se ejecutan remotamente.

## Una visión integrada de la arquitectura funcional

Todos los conceptos estudiados pueden relacionarse en una misma cadena lógica.

```
SISTEMA DISTRIBUIDO
        |
        v
Existen múltiples entidades
en diferentes entornos
```

## Ideas fundamentales de la clase

El **middleware** es una capa de software situada entre las aplicaciones y el sistema operativo de red. Su objetivo principal consiste en ocultar parte de la distribución y heterogeneidad propias de los sistemas distribuidos, proporcionando interfaces de mayor nivel y servicios comunes que simplifican el desarrollo.

La infraestructura de comunicación puede analizarse según dos propiedades diferentes: la movilidad de las entidades y la predictibilidad de su comportamiento. Una topología puede ser fija o variable, mientras que sus características pueden ser predecibles o no predecibles. Ambas propiedades deben analizarse independientemente; una red con entidades fijas puede continuar siendo impredecible en términos de tiempo de comunicación.

El middleware también determina cómo se estructuran las entidades y cómo pueden comunicarse. Puede administrar objetos, agentes o componentes, asignar roles como cliente, servidor, proveedor o suscriptor y ofrecer paradigmas de comunicación síncronos o asíncronos.

El **modelo cliente-servidor** separa claramente al consumidor de un servicio de la entidad encargada de proporcionarlo. Cliente y servidor son entidades de ejecución distintas, aunque no necesariamente deben encontrarse en máquinas físicamente diferentes.

La comunicación cliente-servidor se basa principalmente en el intercambio de una **petición** y una **respuesta**. En el modelo síncrono, el cliente solicita una operación, el servidor la ejecuta y posteriormente devuelve el resultado o un indicador de error.

La separación entre la interfaz de un servicio y su implementación constituye una de las propiedades más importantes de esta arquitectura. Mientras se conserve el contrato establecido por la interfaz, cliente y servidor pueden evolucionar con cierto grado de independencia.

Finalmente, la arquitectura cliente-servidor también facilita la protección y la administración de recursos. Cliente y servidor pueden ejecutarse en dominios de protección diferentes, mientras que un único servidor puede compartir sus servicios y recursos entre múltiples clientes.

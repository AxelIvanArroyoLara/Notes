## Introducción

Después de estudiar RPC como mecanismo para ejecutar procedimientos de forma remota, el siguiente paso consiste en extender esa misma idea al paradigma orientado a objetos. En lugar de pensar únicamente en funciones o procedimientos remotos, ahora se trabaja con **objetos distribuidos**, es decir, objetos que pueden encontrarse en otra máquina y cuyos métodos pueden invocarse a distancia.

Esta evolución conduce a **Remote Method Invocation**, o **RMI**, una forma de RPC orientada a objetos. La idea conserva muchos elementos ya conocidos: cliente, servidor, stubs, skeletons, servicio de nombres, serialización y comunicación remota. Sin embargo, cambia la unidad principal de interacción. En lugar de invocar un procedimiento aislado, el cliente trabaja con una **referencia a un objeto remoto** y ejecuta métodos sobre ese objeto.

En Java, RMI se integra directamente con el modelo de objetos del lenguaje. Esto permite que un objeto remoto se manipule, desde el punto de vista del programador, de una forma muy parecida a un objeto Java normal, aunque su ejecución real ocurra en otra máquina y dentro de otra máquina virtual.

---

## RPC orientado a objetos

### Motivación:

RPC fue diseñado alrededor de procedimientos:

```
procedimiento(parametros)
```

El paradigma orientado a objetos propone una estructura diferente:

```
objeto.metodo(parametros)
```

Esto introduce una nueva idea fundamental: el **objeto mismo se convierte en una unidad de designación y distribución**.

En RPC clásico podría pensarse:

```
insertar(nombre, numero)
```

Mientras que en un modelo orientado a objetos puede pensarse:

```
directorio.insertar(nombre, numero)
```

La diferencia parece pequeña, pero arquitectónicamente es importante.

En el segundo caso no solamente interesa saber qué método se ejecutará, sino también **sobre qué objeto** debe ejecutarse.

---

## Ventajas del modelo orientado a objetos

El material destaca varias propiedades del paradigma orientado a objetos que motivan su uso en sistemas distribuidos:

- encapsulación;
    
- modularidad;
    
- reutilización;
    
- polimorfismo;
    
- composición.
    

  

### Encapsulación:

Un objeto contiene:

```
estado
+
comportamiento
```

Por ejemplo:

```
CuentaBancaria
├── saldo
├── titular
├── depositar()
└── retirar()
```

El usuario del objeto no necesita conocer necesariamente cómo están implementados internamente sus métodos.

En un objeto remoto ocurre la misma idea, pero el estado y la ejecución pueden encontrarse en otra máquina.

### Modularidad:

Cada objeto puede verse como una unidad relativamente independiente.

```
Objeto A
Objeto B
Objeto C
```

Cada uno ofrece una interfaz definida.

Esto ayuda a dividir un sistema distribuido en piezas más claras.

### Reutilización:

Un mismo objeto servidor puede proporcionar funcionalidad a múltiples clientes.

```
Cliente 1 ----\
Cliente 2 -----+----> Objeto remoto
Cliente 3 ----/
```

### Polimorfismo:

Un cliente puede trabajar con una interfaz sin depender de una implementación concreta.

Por ejemplo:

```
interface ServicioPago
```

podría tener varias implementaciones.

El cliente necesita conocer la interfaz, no necesariamente la clase concreta que ejecuta el método.

### Composición:

Los objetos pueden utilizar otros objetos para construir servicios más complejos.

```
ObjetoPedido
   |
   +--> ObjetoInventario
   |
   +--> ObjetoPago
   |
   +--> ObjetoEnvio
```

En un sistema distribuido, algunos de estos objetos podrían encontrarse remotamente.

## Elementos de una llamada a objeto remoto

Una invocación remota sobre un objeto necesita más información que una llamada a procedimiento convencional.

El material identifica varios elementos fundamentales.

### Referencia al objeto:

Primero debe saberse **qué objeto remoto** recibirá la llamada.

Puede imaginarse como una especie de apuntador universal:

```
Referencia remota
        |
        v
Objeto remoto específico
```

No se trata de una dirección de memoria local tradicional.

Es una referencia distribuida que permite identificar al objeto dentro del sistema.

### Identificación del método:

Una vez identificado el objeto, también debe indicarse qué método se desea ejecutar.

```
objeto.metodo()
```

Por tanto, la llamada remota debe contener conceptualmente:

```
referencia al objeto
+
nombre o identificación del método
+
parámetros
```

### Parámetros de entrada y regreso:

La invocación puede incluir:

- argumentos;
    
- valores de retorno;
    
- excepciones.
    

Esto amplía el modelo RPC tradicional.

Una respuesta puede representar:

```
resultado correcto
```

o:

```
excepción
```

---

## Paso por valor y paso por referencia

En el modelo orientado a objetos aparecen dos formas importantes de transmitir parámetros.

### Paso por valor:

Los datos se copian.

```
Cliente                     Servidor

Objeto local
   |
   | serialización
   v
  copia ------------------> copia del objeto
```

El servidor recibe una representación independiente.

### Paso por referencia:

No se copia realmente el objeto remoto.

Se transmite una referencia que permite localizarlo.

```
Objeto remoto
     ^
     |
Referencia remota
     |
     +------ cliente
```

Estas dos posibilidades serán fundamentales en Java RMI.

---

## Objetos de lenguaje y objetos de sistema

El material distingue entre dos enfoques conceptuales.

### Objetos de lenguaje:

Son objetos directamente integrados con la representación del lenguaje de programación.

Por ejemplo:

```
Java object
=
instancia de una clase Java
```

Java RMI es el ejemplo presentado.

### Objetos de sistema:

Su representación puede estar definida de forma más arbitraria por el ambiente de ejecución.

El ejemplo mencionado es:

```
CORBA
```

Aquí el sistema de objetos distribuidos no depende necesariamente de que el objeto remoto sea simplemente una instancia ordinaria del mismo lenguaje.

---

## Extensión de RPC hacia objetos

### De procedimiento a método:

RPC clásico:

```
Cliente
   |
   | insertar(nombre, numero)
   v
Servidor
```

En orientación a objetos:

```
Cliente
   |
   | directorio1.insertar(nombre, numero)
   v
Objeto directorio1
```

La diferencia fundamental es que pueden existir múltiples objetos del mismo tipo.

Por ejemplo:

```
Directorio_1
Directorio_2
```

Ambos pueden tener:

```
insertar(nombre, numero)
```

pero la referencia remota determina sobre cuál se ejecutará el método.

---

## Remote Method Invocation

### Definición:

**RMI** es un RPC orientado a objetos integrado al lenguaje Java.

Su objetivo es permitir la interacción entre objetos situados en:

- espacios de direccionamiento diferentes;
    
- máquinas distintas.
    

Conceptualmente:

```
JVM Cliente                        JVM Servidor

Objeto cliente                    Objeto servidor
      |                                  ^
      |-------- llamada remota ----------|
```

Desde la perspectiva lógica, el cliente trabaja con el objeto remoto de forma similar a cualquier otro objeto Java.

---

## Java como IDL

En RPC tradicional se utilizaba un **IDL** para describir la interfaz entre cliente y servidor.

En Java RMI, el propio lenguaje Java cumple esa función.

El material lo expresa explícitamente:

> no existe un IDL separado; Java actúa como IDL.

Esto significa que una interfaz Java puede definir directamente el contrato remoto.

Por ejemplo:

```
public interface Hello extends Remote {
    String sayHello() throws RemoteException;
}
```

La interfaz especifica:

```
método disponible
tipo de retorno
parámetros
excepciones
```

---

## Servant

### Concepto:

El objeto que implementa realmente la interfaz remota puede entenderse como el **servant**.

```
Interfaz remota
       |
       v
Implementación
       |
       v
Servant
```

Es el objeto servidor que contiene la lógica real que se ejecutará cuando llegue la llamada remota.

## Arquitectura conceptual de RMI

Una interacción RMI contiene varios elementos:

```
Cliente
   |
   v
Stub cliente
   |
   v
Sistema de comunicación
   |
   v
Stub / skeleton servidor
   |
   v
Objeto servidor
```

Además, existe una referencia al objeto remoto que permite identificarlo.

El mensaje lógico de una llamada incluye:

```
referencia al objeto
+
método
+
argumentos
```

y la respuesta contiene:

```
resultado
o
excepción
```

Esto aparece directamente en el esquema funcional de RMI.

## Componentes funcionales de RMI

El material relaciona la ejecución RMI con varias funciones.

### Designación:

Es necesario identificar el objeto remoto.

```
nombre lógico
        |
        v
referencia remota
```

### Binding:

Consiste en asociar un nombre con un objeto o referencia remota.

### Ejecución de consulta:

Una vez obtenida la referencia, se ejecuta el método.

### Regreso de resultados:

El servidor devuelve:

```
resultado
```

o:

```
excepción
```

### Ciclo de vida:

También debe administrarse la existencia de los objetos distribuidos.

## Reglas de una interfaz remota

Para que una interfaz pueda utilizarse mediante Java RMI, debe cumplir ciertas reglas.

### Debe ser pública:

La interfaz debe poder ser conocida desde fuera de la clase.

```
public interface MiServicio
```

### Debe extender Remote:

Debe extender:

```
java.rmi.Remote
```

Por ejemplo:

```
public interface Hello extends Remote
```

Esto identifica la interfaz como una interfaz destinada a invocaciones remotas.

### Los métodos deben declarar RemoteException:

Cada método remoto debe declarar al menos:

```
throws RemoteException
```

Por ejemplo:

```
String sayHello() throws RemoteException;
```

Esto es importante porque una llamada remota puede fallar por causas que no aparecen normalmente en una llamada local.

Por ejemplo:

```
servidor caído
red interrumpida
problemas de comunicación
objeto remoto inaccesible
```

---

## RemoteException

### Por qué existe:

Una llamada local:

```
objeto.metodo()
```

depende principalmente del proceso local.

Una llamada RMI depende de:

```
cliente
+
red
+
servidor
+
objeto remoto
```

Por ello, el método debe reconocer explícitamente que puede ocurrir una falla de comunicación.

La excepción:

```
RemoteException
```

formaliza esta posibilidad.

---

## Paso de objetos en RMI

Java RMI distingue principalmente entre objetos locales y objetos remotos.

### Objetos locales: por valor:

Un objeto local se transmite como una copia.

Para ello debe ser serializable.

```
Objeto original
     |
     | serialización
     v
   bytes
     |
     | red
     v
   copia
```

Debe implementar:

```
java.io.Serializable
```

### Objetos remotos: por referencia:

Un objeto remoto no se copia.

Se transmite su referencia remota.

```
Objeto remoto
    ^
    |
  Stub
    ^
    |
Cliente
```

Por tanto:

```
objeto local        -> copia
objeto remoto       -> referencia
```

---

## Serializable

### Función:

`Serializable` permite convertir el estado de un objeto en una representación transportable.

Por ejemplo:

```
class Persona implements Serializable
```

Cuando un objeto serializable se envía a otro proceso:

```
Objeto Persona
     |
     | serialización
     v
representación
     |
     v
    RED
     |
     v
deserialización
     |
     v
copia Persona
```

El objeto recibido es una copia distinta del original.

---

## Objeto Remote

Un objeto que implementa:

```
Remote
```

se trata de forma distinta.

En vez de enviarse todo su estado, se transmite una referencia al objeto remoto.

```
Servidor
Objeto O
   ^
   |
 referencia
   |
Cliente
```

Por eso el cliente continúa ejecutando operaciones sobre el mismo objeto que reside en el servidor.

---

## Reglas del servant

La clase que implementa el objeto remoto debe cumplir varias reglas.

### Implementar una interfaz Remote:

Por ejemplo:

```
public class Servicio implements MiServicio
```

donde:

```
MiServicio extends Remote
```

### Uso de UnicastRemoteObject:

El material presenta como forma tradicional extender:

```
java.rmi.server.UnicastRemoteObject
```

aunque también señala que existen otras posibilidades.

Conceptualmente:

```
Clase servidor
   |
   +--> implementación de interfaz remota
   |
   +--> infraestructura RMI
```

### Métodos locales adicionales:

Una clase remota también puede contener métodos que no pertenezcan a la interfaz `Remote`.

Por ejemplo:

```
Métodos remotos:
consultar()
actualizar()

Métodos locales:
validarInternamente()
cargarConfiguracion()
```

Los métodos locales no están disponibles para clientes remotos.

---

## Reglas del servidor

El servidor debe realizar varias tareas.

### Definir referencias remotas:

Debe especificar los objetos remotos involucrados.

### Definir constructor:

La clase necesita poder crear una instancia del objeto remoto.

### Implementar métodos remotos:

Debe proporcionar el comportamiento real de los métodos definidos en la interfaz.

### Configuración de seguridad:

El material incluye la configuración del administrador de seguridad dentro de las responsabilidades del servidor.

### Crear una instancia:

No basta con definir la clase.

Debe existir al menos:

```
una instancia concreta
```

del objeto servidor.

### Registrar la instancia:

La instancia debe registrarse en un servicio de nombres.

En Java RMI, este servicio es:

```
rmiregistry
```

---

## rmiregistry

### Función:

`rmiregistry` es el servidor de nombres utilizado por Java RMI.

Permite asociar:

```
nombre
    ↓
referencia a objeto remoto
```

Por ejemplo:

```
"Hello"
   |
   v
Stub del objeto Hello
```

Entonces un cliente puede buscar:

```
"Hello"
```

y recibir una referencia que le permite comunicarse con el objeto remoto.

---

## Arquitectura general de Java RMI

Una vista simplificada es:

```
JVM CLIENTE                         JVM SERVIDOR

Cliente                              Objeto remoto
   |                                      ^
   v                                      |
Naming                                    |
   |                                      |
   v                                      |
rmiregistry -----------------------> referencia
   |
   v
Stub
   |
   |--------------------------------------> objeto
```

En la práctica, el registro almacena información que permite al cliente obtener un stub asociado al objeto remoto.

## Modo de operación en el servidor

El material describe el funcionamiento del servidor mediante una secuencia concreta.

### Creación del objeto:

Al crearse el objeto remoto se generan o preparan los mecanismos de comunicación necesarios.

En el esquema clásico se habla de:

```
stub
+
skeleton
+
puerto de comunicación
```

### Registro en Naming:

El servidor utiliza el mecanismo de `Naming` para registrar el objeto.

Por ejemplo:

```
rebind(...)
```

### Registro del stub:

El sistema registra el stub serializado ante `rmiregistry`.

Conceptualmente:

```
Objeto servidor
      |
      v
Stub
      |
      v
rmiregistry
```

### Servidor listo:

Una vez registrado, el servidor de nombres puede proporcionar esa referencia a los clientes.

---

## Modo de operación en el cliente

La secuencia del cliente continúa a partir de este punto.

### Lookup:

El cliente solicita el objeto mediante:

```
lookup(...)
```

Por ejemplo:

```
Naming.lookup("//host:port/Hello")
```

### Recuperación del stub:

El sistema obtiene el stub correspondiente al objeto servidor.

### Instalación de la referencia:

El cliente recibe una referencia que puede utilizar como si fuera un objeto Java.

### Invocación:

Después realiza:

```
obj.metodo()
```

y el stub se encarga de convertir esa llamada en comunicación remota.

## Flujo completo servidor-cliente

El funcionamiento puede visualizarse así:

```
SERVIDOR

1. Crear objeto remoto
       |
       v
2. Exportar / crear stub
       |
       v
3. Registrar nombre
       |
       v
4. rmiregistry guarda referencia


CLIENTE

5. lookup(nombre)
       |
       v
6. rmiregistry devuelve stub
       |
       v
7. cliente obtiene referencia
       |
       v
8. cliente invoca método
       |
       v
9. stub transmite llamada
       |
       v
10. servidor ejecuta método
```

## Interfaz RMI

Los principios básicos son similares a los de una interfaz local de Java.

Sin embargo, existen diferencias importantes.

### Interfaz pública:

```
public interface Servicio
```

### Extiende Remote:

```
extends Remote
```

### Métodos con RemoteException:

```
metodo() throws RemoteException;
```

### Referencias mediante interfaces:

El material señala que las referencias a objetos `Remote` o `Serializable` deben declararse como interfaces.

Esto permite mantener el contrato separado de la implementación concreta.

## Implementación del servidor

Una clase que implementa la interfaz remota debe definir:

```
constructor
+
métodos remotos
+
posibles métodos locales
```

También debe establecer qué objetos se transmitirán por copia y cuáles por referencia.

### Por copia:

```
implements Serializable
```

### Por referencia:

```
implements Remote
```

Finalmente debe:

```
crear al menos una instancia
+
registrarla en rmiregistry
```

## Ejemplo de interfaz Hello

El material presenta una interfaz mínima:

```
package example.hello;

import java.rmi.Remote;
import java.rmi.RemoteException;

public interface Hello extends Remote {
    String sayHello() throws RemoteException;
}
```

  

Este ejemplo contiene todos los elementos esenciales.

### `extends Remote`:

Indica que la interfaz representa un objeto remoto.

### `sayHello()`:

Es el método que podrá invocarse remotamente.

### `throws RemoteException`:

Reconoce explícitamente que la comunicación remota puede fallar.

---

## Ejemplo de servidor

El servidor implementa la interfaz:

```
public class Server implements Hello
```

y contiene un estado:

```
private String msg;
```

junto con un constructor:

```
public Server(String msg) {
    this.msg = msg;
}
```

Después implementa:

```
public String sayHello() {
    return "Hello world: " + msg;
}
```

  

Esto muestra que el objeto remoto sigue siendo conceptualmente un objeto Java normal con:

```
estado
+
métodos
```

La diferencia es que algunos métodos pueden invocarse desde otra máquina.

---

## Exportación del objeto remoto

El ejemplo del material crea un objeto:

```
Server obj = new Server("Coucou");
```

y posteriormente lo exporta:

```
Hello stub =
    (Hello) UnicastRemoteObject.exportObject(obj, 0);
```

  

La exportación prepara el objeto para recibir llamadas remotas.

Puede entenderse así:

```
Objeto Java ordinario
        |
        | exportObject
        v
Objeto accesible mediante RMI
        |
        v
Stub
```

---

## Registro en el Registry

El servidor obtiene el registro:

```
Registry registry = LocateRegistry.getRegistry();
```

y posteriormente registra:

```
registry.bind("Hello", stub);
```

Esto crea una relación lógica:

```
"Hello"
   |
   v
stub
   |
   v
objeto servidor
```

El cliente no necesita conocer directamente la implementación concreta.

Busca el nombre `"Hello"`.

## Creación programática del Registry

El material también muestra que el registro puede crearse desde código:

Registry registry =

Después puede construirse una URL semejante a:

```

```

y registrarse el objeto utilizando:

```

```

Sus componentes son:

## Ejemplo de cliente

El cliente recupera el objeto mediante:

```
Hello obj =
    (Hello) Naming.lookup("//host:port/Hello");
```

Después invoca:

```
String msg = obj.sayHello();
```

y finalmente puede utilizar el resultado:

```
System.out.println(msg);
```

  

Desde el punto de vista del código:

```
obj.sayHello()
```

parece una llamada ordinaria.

Internamente:

```
obj
 |
 v
stub
 |
 v
red
 |
 v
objeto remoto
```

## Transparencia de RMI

Este ejemplo muestra la abstracción principal de RMI.

El programador ve:

```
obj.sayHello();
```

Pero el sistema realiza:

```
1. identificar objeto remoto
2. identificar método
3. serializar argumentos
4. enviar llamada
5. ejecutar método
6. serializar respuesta
7. devolver resultado
```

La distribución se oculta parcialmente detrás de la sintaxis orientada a objetos.

## Ejecución

El flujo de ejecución presentado es:

```
1. rmiregistry
2. servidor
3. cliente
```

  

### Registry:

```
rmiregistry
```

debe proporcionar el servicio de nombres.

### Servidor:

Publica el objeto remoto.

### Cliente:

Localiza la referencia y ejecuta los métodos.

---

## Caso 1: Método sin parámetros

El primer caso conceptual es:

```
R_objeto1.m()
```

El cliente posee una referencia remota:

```
R_objeto1
```

La llamada viaja mediante:

```
stub
→
skeleton
→
Objeto1.m()
```

  

Conceptualmente:

```
Cliente
   |
   | R_objeto1.m()
   v
Stub
   |
   v
RED
   |
   v
Skeleton
   |
   v
Objeto1.m()
```

---

## Caso 2: Objeto serializable

Ahora el método recibe:

```
O2
```

donde `O2` es un objeto serializable.

La llamada es:

```
R_objeto1.m(O2)
```

El objeto se transmite **por valor**.

Por ello:

```
O2 original
   |
   | serialización
   v
RED
   |
   v
clone_O2
```

El servidor obtiene una copia.

### Consecuencia:

Si el servidor modifica:

```
clone_O2
```

no modifica automáticamente:

```
O2 original
```

porque son objetos diferentes.

## Caso 3: Objeto remoto por referencia

En el tercer caso se envía:

```
R_O2
```

que representa una referencia remota.

La llamada es:

```
R_objeto1.m(R_O2)
```

En este caso no se crea una copia completa del objeto `O2`.

Se transmite una referencia que permite al servidor llamar posteriormente al objeto remoto correspondiente.

La estructura conceptual es:

```
Cliente
   |
   | referencia R_O2
   v
Servidor
   |
   | usa stub R_O2
   v
Objeto O2 remoto
```

La operación se identifica principalmente mediante:

# Ideas fundamentales de la clase

RMI extiende el concepto de RPC hacia el paradigma orientado a objetos. En lugar de invocar únicamente procedimientos remotos, permite ejecutar métodos sobre objetos que pueden residir en otra máquina y otro espacio de direccionamiento.

La llamada remota necesita identificar no solamente el método, sino también el objeto específico sobre el cual debe ejecutarse. Por ello, las referencias remotas se convierten en una pieza fundamental del sistema.

Java RMI integra directamente este modelo con el lenguaje Java. La propia interfaz Java funciona como descripción del contrato remoto, por lo que no se requiere un IDL separado. Una interfaz remota debe ser pública, extender `java.rmi.Remote` y declarar `RemoteException` en los métodos remotos.

Los objetos locales transmitidos como parámetros se pasan por valor y deben ser serializables. Esto significa que el receptor obtiene una copia independiente. En cambio, los objetos remotos se pasan por referencia, por lo que el receptor obtiene una referencia que le permite seguir interactuando con el mismo objeto remoto.

El stub actúa como representante local del objeto remoto. El cliente realiza una llamada sobre el stub como si se tratara de un objeto ordinario, mientras la infraestructura RMI se encarga de identificar el objeto, serializar parámetros, transmitir la llamada, ejecutar el método en el servidor y devolver el resultado o una excepción.

`rmiregistry` proporciona el servicio de nombres de Java RMI. El servidor registra una referencia remota bajo un nombre lógico y el cliente utiliza mecanismos como `lookup` para recuperar esa referencia antes de realizar las llamadas.

El servidor debe implementar la interfaz remota, crear al menos una instancia del objeto y registrarla. El cliente únicamente necesita conocer la interfaz y localizar el objeto remoto para poder utilizarlo.

Java RMI constituye un ejemplo muy claro de cómo el middleware busca ocultar la distribución. Una llamada como `obj.metodo()` puede parecer completamente local, aunque detrás de ella exista una interacción entre dos JVM, serialización, stubs, un servicio de nombres, comunicación de red y un objeto remoto.

Finalmente, RMI conserva los mismos problemas fundamentales de cualquier sistema distribuido: la red puede fallar, los objetos viven en espacios de memoria diferentes y la comunicación tiene costos reales. La transparencia facilita la programación, pero no elimina la naturaleza distribuida del sistema.

## Introducción

Después de estudiar el papel del middleware y el modelo cliente-servidor, el siguiente paso consiste en analizar una de las herramientas clásicas utilizadas para implementar este tipo de interacción: **Remote Procedure Call**, normalmente abreviado como **RPC**.

RPC intenta que la ejecución de una operación remota se parezca, desde la perspectiva del programador, a la llamada normal de un procedimiento local. Esto es importante porque permite trabajar con una abstracción familiar: en vez de pensar constantemente en sockets, paquetes, direcciones de red y protocolos de comunicación, el desarrollador puede formular una operación como si estuviera invocando una función ordinaria.

Sin embargo, detrás de esa aparente simplicidad existe una infraestructura considerable. Una llamada RPC debe localizar al servidor, transformar parámetros en mensajes, transmitirlos por la red, reconstruirlos en el destino, seleccionar el procedimiento correcto, ejecutarlo y devolver los resultados. Además, debe considerar fallas independientes del cliente, del servidor y de la propia red.

---

## Remote Procedure Call

### Concepto general de RPC:

**Remote Procedure Call** es una herramienta de alto nivel para implementar el modelo cliente-servidor.

La idea central consiste en permitir que un programa invoque un procedimiento ubicado en otra máquina utilizando una forma similar a una llamada local.

En una ejecución local podría existir:

```
Programa
   |
   v
P(x, y)
   |
   v
Procedimiento P
```

Con RPC se intenta conservar aproximadamente la misma idea, aunque el procedimiento esté en otra máquina:

```
Cliente                           Servidor

p(x, y)
   |
   |------------------------------> P(x, y)
               RED
```

Desde la perspectiva lógica, el cliente realiza una llamada.

Desde la perspectiva física, esa llamada necesita transformarse en comunicación de red.

Esta diferencia entre la **visión lógica** y la **realización física** es fundamental para comprender RPC.

---

## Llamada local frente a llamada remota

### Llamada local:

Cuando un procedimiento se encuentra en el mismo proceso o sistema, la llamada puede realizarse directamente.

Por ejemplo:

```
resultado = sumar(4, 7)
```

El programa conoce dónde se encuentra la función, pasa sus argumentos y recibe el resultado.

Conceptualmente:

```
Programa
   |
   | llamada
   v
sumar(4, 7)
   |
   | ejecución local
   v
11
```

No es necesario enviar ningún dato por una red.

### Llamada remota:

En una llamada remota, el procedimiento está en otro proceso y posiblemente en otra computadora.

Por tanto:

```
resultado = sumar(4, 7)
```

puede parecer una llamada ordinaria para el programador, pero internamente debe realizarse algo semejante a:

```
Cliente
   |
   | convertir llamada a mensaje
   v
RED
   |
   v
Servidor
   |
   | reconstruir llamada
   v
sumar(4, 7)
   |
   v
11
   |
   | convertir resultado a mensaje
   v
RED
   |
   v
Cliente
```

RPC se encarga de ocultar buena parte de esta complejidad.

---

## Intercambio básico de mensajes en RPC

Una llamada RPC requiere, como mínimo, el intercambio de **dos mensajes**.

### Primer mensaje: llamada:

El primer mensaje corresponde a la consulta del cliente.

Contiene la información necesaria para representar la llamada al procedimiento, incluyendo sus parámetros.

Por ejemplo:

```
Mensaje RPC de solicitud

Procedimiento: multiplicar
Parámetro 1: 5
Parámetro 2: 8
```

El servidor recibe este mensaje y puede reconstruir conceptualmente:

```
multiplicar(5, 8)
```

### Segundo mensaje: respuesta:

Después de ejecutar el procedimiento, el servidor genera un mensaje de respuesta que contiene los resultados.

```
Mensaje RPC de respuesta

Resultado: 40
```

Por tanto, el flujo mínimo es:

```
CLIENTE                             SERVIDOR

   |                                   |
   |------ llamada + parámetros ------>|
   |                                   |
   |             ejecuta               |
   |                                   |
   |<------ resultado -----------------|
   |                                   |
```

Se utiliza la expresión **al menos dos mensajes** porque una implementación real podría necesitar comunicación adicional para localizar servicios, confirmar operaciones o resolver problemas de ejecución.

---

## Objetivo principal de RPC

RPC busca que una llamada remota tenga una forma semejante a una llamada local.

Por ejemplo:

```
resultado = consultarSaldo(cuenta)
```

El cliente debería poder utilizar esta operación sin tener que escribir explícitamente:

```
crear socket
conectar al servidor
serializar parámetros
enviar mensaje
esperar respuesta
recibir bytes
deserializar resultado
cerrar conexión
```

Ese trabajo se delega al sistema RPC y a su middleware.

---

## Ventajas de RPC

El material destaca varias ventajas principales del modelo RPC.

### Apariencia semejante a una llamada local:

Una de sus ventajas más importantes es que la **forma y el efecto** de la llamada pueden parecerse a los de una llamada local.

El programador puede trabajar con:

```
resultado = procedimiento(parametros)
```

en lugar de manejar directamente mecanismos de red de bajo nivel.

Esto eleva considerablemente el nivel de abstracción.

### Facilita la transición hacia distribución:

Una aplicación puede diseñarse inicialmente utilizando procedimientos locales.

Posteriormente, ciertas operaciones pueden trasladarse hacia una ejecución remota mediante RPC.

La intención es reducir las modificaciones necesarias en la lógica principal de la aplicación.

Conceptualmente:

```
ETAPA 1

Programa
   |
   v
Procedimiento local


ETAPA 2

Programa
   |
   v
RPC
   |
   v
Procedimiento remoto
```

La interfaz utilizada por el programa puede conservarse aunque cambie la localización de la ejecución.

### Validación local antes de distribuir:

Otra ventaja consiste en poder validar inicialmente la lógica utilizando procedimientos locales.

Una vez comprobado el comportamiento funcional, puede añadirse posteriormente la infraestructura distribuida.

Esto ayuda a separar dos problemas diferentes:

```
Problema 1:
¿La lógica del procedimiento funciona?

Problema 2:
¿La comunicación distribuida funciona?
```

De esta forma, los errores pueden localizarse con mayor facilidad.

### Simplicidad de uso:

El objetivo general de RPC es reducir la complejidad visible para quien desarrolla la aplicación.

El programador utiliza procedimientos mientras la infraestructura RPC se encarga de la interacción remota.

---

## Problemas de RPC

La similitud con las llamadas locales es útil, pero también puede resultar engañosa.

Una llamada remota nunca es exactamente igual a una llamada local porque la red introduce nuevas fuentes de incertidumbre.

### Fallas independientes:

En un sistema distribuido, cliente y servidor pueden fallar independientemente.

Por ejemplo:

```
Cliente             Servidor

activo               activo
activo               falla
falla                activo
falla                falla
```

Además, la red puede fallar aunque ambas aplicaciones continúen funcionando.

```
Cliente ----X---- Servidor
           RED
```

Esto hace mucho más complejo interpretar el resultado de una llamada.

### Incertidumbre de la red:

Supóngase que el cliente envía una solicitud y no recibe respuesta.

¿Qué ocurrió?

Podrían existir varias posibilidades:

```
Caso A:
La solicitud nunca llegó.

Caso B:
La solicitud llegó, pero el servidor falló.

Caso C:
La solicitud llegó y se ejecutó,
pero la respuesta se perdió.

Caso D:
La operación continúa ejecutándose.

Caso E:
La respuesta simplemente está retrasada.
```

Desde el punto de vista del cliente, muchos de estos casos pueden observarse exactamente de la misma manera:

```
No llegó respuesta.
```

Por ello, el material señala que RPC posee una **semántica compleja en caso de falla**.

---

## Restricciones sobre parámetros

Una llamada local puede utilizar estructuras muy complejas porque todos los datos se encuentran dentro de un mismo entorno de ejecución.

En RPC, los parámetros deben atravesar una red.

Esto introduce restricciones.

### Parámetros simples:

Valores como:

```
entero
real
cadena
booleano
```

suelen ser relativamente sencillos de transmitir.

### Estructuras complejas:

La transmisión de estructuras complejas es posible, pero más difícil.

Por ejemplo:

```
Cliente:

Objeto usuario
 ├─ nombre
 ├─ dirección
 │   ├─ ciudad
 │   ├─ calle
 │   └─ código postal
 └─ pedidos[]
```

Toda esta estructura debe convertirse a una representación que pueda transmitirse por la red y reconstruirse correctamente en el servidor.

Aquí aparecen los conceptos de **marshalling** y **unmarshalling**.

---

## Primitivas de bajo nivel

Antes de entender cómo RPC simplifica la comunicación, conviene observar qué tendría que realizar manualmente una aplicación sin esta abstracción.

El material muestra varias tareas de bajo nivel:

- protocolo de interacción;
    
- empaquetado del mensaje;
    
- desempaquetado del mensaje.
    

  

Una implementación directa tendría aproximadamente este flujo:

```
CLIENTE

1. Elegir protocolo
2. Empacar parámetros
3. Construir mensaje
4. Enviar mensaje
5. Esperar respuesta
6. Recibir respuesta
7. Desempacar resultado


SERVIDOR

1. Recibir mensaje
2. Desempacar parámetros
3. Interpretar operación
4. Ejecutar procedimiento
5. Empacar resultados
6. Enviar respuesta
```

RPC introduce componentes específicos para automatizar estas tareas.

---

## Stub y Skeleton

Dos piezas esenciales de una implementación RPC son el **stub** del cliente y el **skeleton** del servidor.

El material remarca que este código puede ser generado automáticamente.

La arquitectura puede visualizarse así:

```
CLIENTE                                  SERVIDOR

Aplicación                               Procedimiento
   |                                         ^
   v                                         |
Stub cliente                            Skeleton
   |                                         ^
   v                                         |
Middleware RPC  <------ RED ------> Middleware RPC
```

Estos componentes actúan como intermediarios entre la lógica de la aplicación y la comunicación de red.

---

## Talón cliente o Stub

### Función general:

El **stub cliente** recibe una llamada local realizada por la aplicación y la transforma en una llamada remota.

Según el material, realiza cuatro tareas fundamentales.

### Recibir una llamada local:

El cliente realiza algo semejante a:

```
resultado = sumar(5, 8)
```

Sin embargo, la función que recibe inicialmente esa invocación puede ser el stub.

```
Aplicación
    |
    v
Stub sumar()
```

La aplicación tiene la impresión de estar llamando a un procedimiento normal.

### Transformar la llamada en una llamada a distancia:

El stub toma los parámetros y los convierte en un mensaje.

```
sumar(5, 8)

        ↓

Mensaje RPC:
{
  operación = sumar
  x = 5
  y = 8
}
```

Después envía ese mensaje hacia el servidor.

### Recibir los resultados:

Una vez que el servidor ejecuta la operación, el stub recibe el mensaje de respuesta.

```
Mensaje:
resultado = 13
```

### Regresar el resultado como retorno del procedimiento:

Finalmente, el stub presenta el resultado a la aplicación como si hubiera sido devuelto por una función local.

```
resultado = 13
```

Por tanto:

```
Aplicación
     |
     | llamada local
     v
Stub cliente
     |
     | mensaje remoto
     v
Servidor
```

El stub constituye el puente entre ambos mundos.

---

## Talón servidor o Skeleton

El **skeleton** realiza el proceso inverso en el lado servidor.

### Recibir la llamada como mensaje:

El servidor recibe una representación de la operación:

```
Mensaje RPC:
operación = sumar
x = 5
y = 8
```

### Seleccionar el procedimiento correspondiente:

El skeleton interpreta el mensaje y determina qué procedimiento debe ejecutarse.

```
operación = sumar

        ↓

seleccionar:
sumar(x, y)
```

### Ejecutar el procedimiento:

Una vez identificado, invoca el procedimiento real del servidor:

```
sumar(5, 8)
```

### Retransmitir los resultados:

El resultado:

```
13
```

se convierte nuevamente en un mensaje RPC y se envía hacia el cliente.

---

## Flujo completo de una llamada RPC

La secuencia completa puede representarse así:

```
CLIENTE                                      SERVIDOR

Aplicación
   |
   | 1. llamada
   v
Stub cliente
   |
   | 2. marshalling
   v
Middleware
   |
   | 3. mensaje
   |============================>
                                      Middleware
                                           |
                                           | 4. recepción
                                           v
                                      Skeleton
                                           |
                                           | 5. unmarshalling
                                           v
                                      Procedimiento
                                           |
                                           | 6. ejecución
                                           v
                                       Resultado
                                           |
                                           | 7. marshalling
                                           v
                                      Skeleton
                                           |
   <=============================|
   |          8. respuesta
Middleware
   |
   v
Stub cliente
   |
   | 9. unmarshalling
   v
Aplicación
   |
   v
Resultado
```

Aunque el programador puede percibir únicamente:

```
resultado = procedimiento(parametros)
```

internamente se realiza toda esta secuencia.

## Marshalling

### Concepto:

**Marshalling** es el proceso de transformar parámetros o resultados en una representación adecuada para transmitirlos.

Por ejemplo:

```
Datos originales:

nombre = "Ana"
edad = 21
activo = true
```

deben convertirse a una secuencia transmisible:

```
[ longitud ][ "Ana" ][ 21 ][ 1 ]
```

El formato concreto dependerá de la implementación.

La idea fundamental es:

```
ESTRUCTURA EN MEMORIA
        |
        | marshalling
        v
REPRESENTACIÓN TRANSMISIBLE
```

---

## Unmarshalling

El **unmarshalling** es la operación inversa.

```
REPRESENTACIÓN TRANSMITIDA
        |
        | unmarshalling
        v
ESTRUCTURA UTILIZABLE
```

El receptor toma los datos recibidos y reconstruye los parámetros originales.

Por tanto:

```
Cliente:
objeto
  |
  | marshalling
  v
bytes
  |
  | RED
  v
bytes
  |
  | unmarshalling
  v
objeto
Servidor
```

Estos mecanismos son esenciales porque cliente y servidor no comparten directamente la misma memoria.

---

## Principios de implementación de RPC

El material presenta una serie de preguntas fundamentales que cualquier sistema RPC debe resolver.

### Localización del servidor:

La primera pregunta es:

> ¿Cómo conoce el cliente la dirección del servidor?

El cliente necesita localizar el proceso remoto que proporciona el servicio.

Puede necesitar información como:

```
Dirección IP
+
Número de puerto
```

o algún identificador equivalente.

Esto conduce al problema de **designación y ligado**.

### Transmisión de parámetros:

También debe decidirse cómo transportar los parámetros entre cliente y servidor.

Aquí aparecen varias cuestiones:

- paso por valor o referencia;
    
- estructuras complejas;
    
- marshalling;
    
- unmarshalling;
    
- heterogeneidad entre máquinas.
    

### Tratamiento de errores:

Debe definirse:

- qué fallas se consideran posibles;
    
- cómo pueden detectarse;
    
- qué significa una llamada cuando ocurre un error.
    

Esto es particularmente complejo debido a la naturaleza distribuida del sistema.

### Construcción de talones:

Stub y skeleton pueden generarse automáticamente.

Esto evita que el programador tenga que implementar manualmente toda la lógica de comunicación.

### Administración de ejecución:

También debe administrarse la inicialización del servidor.

Antes de responder llamadas, el servidor debe encontrarse disponible y preparado para recibirlas.

---

## Paso de parámetros

### Paso por valor:

En un paso por valor se transmite el contenido del parámetro.

Por ejemplo:

```
Cliente:

x = 10
```

Se envía:

```
10
```

El servidor obtiene una copia.

```
Cliente x = 10

       ↓

Servidor x = 10
```

Modificar posteriormente la copia del servidor no modifica automáticamente la variable original del cliente.

### Paso por referencia:

El paso por referencia es más problemático en sistemas distribuidos.

En una llamada local podría pasarse una dirección de memoria:

```
0x7FFE1234
```

Pero esa dirección solo tiene sentido dentro del espacio de memoria de una máquina determinada.

En otra computadora:

```
0x7FFE1234
```

podría referirse a algo completamente diferente o no existir.

Por eso las referencias no pueden transmitirse de forma ingenua.

Es necesario utilizar mecanismos adicionales que representen recursos remotos mediante identificadores o referencias distribuidas.

---

## Heterogeneidad

Cliente y servidor pueden ejecutarse sobre arquitecturas diferentes.

Por ejemplo:

```
Cliente:
Arquitectura A

Servidor:
Arquitectura B
```

Los datos pueden representarse internamente de manera distinta.

Esto puede afectar:

- tamaño de los tipos;
    
- orden de bytes;
    
- codificación de texto;
    
- alineamiento;
    
- representación de estructuras.
    

Por ello, el sistema RPC necesita una representación suficientemente común para que ambos extremos interpreten los datos de la misma manera.

El marshalling forma parte de esta solución.

---

## Designación y ligado

Una llamada remota necesita determinar **qué servicio se desea utilizar** y **dónde se encuentra**.

El material distingue dos conceptos relacionados:

- **designación**;
    
- **ligado**.
    

  

### Designación:

Designar significa identificar el servicio o proceso que se desea utilizar.

Una buena designación debería poder ser independiente de la localización física.

Por ejemplo, resulta preferible identificar:

```
"servicio_impresion"
```

que depender permanentemente de:

```
192.168.1.50:8300
```

La primera forma identifica **qué servicio es**.

La segunda especifica **dónde está en un momento determinado**.

Separar ambos conceptos permite reconfigurar el sistema.

### Ventaja de separar nombre y localización:

Supóngase:

```
Servicio:
procesar_pagos
```

Inicialmente:

```
Servidor A
192.168.1.20
```

Después puede trasladarse:

```
Servidor B
192.168.1.80
```

Si el cliente utiliza un nombre lógico, el cambio de ubicación puede ocultarse mediante un mecanismo de resolución.

Esto permite responder mejor a situaciones como:

- fallas;
    
- redistribución;
    
- balanceo de carga;
    
- cambios en la infraestructura.
    

---

## Ligado

El **ligado** consiste en asociar una designación lógica con una ubicación o entidad concreta.

Conceptualmente:

```
Nombre del servicio
        |
        | ligado
        v
Servidor concreto
```

Por ejemplo:

```
"servicio_archivos"

        ↓

192.168.1.40 : 5000
```

El material distingue ligado **precoz** y **tardío**.

---

## Ligado estático

En el ligado estático, la localización del servidor se conoce desde el momento de composición o compilación.

```
Cliente
   |
   | ya conoce
   v
Servidor X
```

No es necesario consultar un servicio de nombres durante la ejecución.

El material indica explícitamente que en este caso la llamada se resuelve en tiempo de compilación.

### Ventaja:

Existe menos trabajo durante la ejecución.

### Desventaja:

La configuración es más rígida.

Si el servidor cambia de dirección, puede ser necesario modificar o recompilar la aplicación.

---

## Ligado dinámico

En el ligado dinámico, la localización del servidor se determina durante la ejecución.

```
Cliente
   |
   | ¿Dónde está servicio X?
   v
Servicio de nombres
   |
   | dirección
   v
Servidor
```

Esto proporciona más flexibilidad.

El servidor puede cambiar de localización sin obligar necesariamente a modificar el cliente.

---

## Ligado a la primera llamada

Existe una estrategia intermedia: consultar el servicio de nombres únicamente la primera vez.

  

El flujo sería:

```
PRIMERA LLAMADA:

Cliente
   |
   v
Servicio de nombres
   |
   v
Servidor


LLAMADAS SIGUIENTES:

Cliente
   |
   +------------------> Servidor
```

La dirección obtenida puede almacenarse para reutilizarla.

Esto reduce el número de consultas.

---

## Ligado a cada llamada

En esta estrategia, el cliente consulta el servicio de nombres antes de cada invocación.

```
Llamada 1:
Cliente → nombres → servidor

Llamada 2:
Cliente → nombres → servidor

Llamada 3:
Cliente → nombres → servidor
```

Esto ofrece mayor dinamismo porque cada llamada puede resolverse hacia una ubicación actualizada.

Sin embargo, introduce más trabajo y más comunicación.

---

## Comunicación lógica y comunicación física

El modelo RPC permite distinguir entre dos niveles.

### Comunicación lógica:

Desde la perspectiva del programa:

```
Programa cliente
       |
       | llamada
       v
Programa servidor
```

Parece existir una relación directa.

### Comunicación física:

Realmente la comunicación puede recorrer:

```
Programa cliente
        |
        v
Stub cliente
        |
        v
Mecanismo de comunicación
        |
        v
RED
        |
        v
Mecanismo de comunicación
        |
        v
Skeleton
        |
        v
Programa servidor
```

La abstracción RPC oculta estas capas.

---

## Servicio de nombres

Para realizar ligado dinámico puede utilizarse un **servicio de nombres**.

El cliente conoce un nombre simbólico y necesita obtener información concreta sobre dónde se encuentra el servicio.

```
Cliente:
"Quiero servicio S"

        ↓

Servicio de nombres:
"Está en servidor A, puerto 4000"

        ↓

Cliente conecta con servidor A
```

Este mecanismo desacopla el nombre lógico de la ubicación física.

---

## Directorio de servicios

El material presenta un esquema basado en un **directorio**.

El proceso ocurre en dos fases principales.

### Registro del servidor:

El servidor se registra en el directorio proporcionando información semejante a:

```
< nombre,
  dirección del servidor,
  número de puerto >
```

Por ejemplo:

```
< "calculadora",
  192.168.1.10,
  4500 >
```

El directorio mantiene esta asociación.

### Búsqueda del cliente:

Cuando el cliente desea utilizar el servicio, consulta:

```
< nombre >
```

El directorio responde:

```
< dirección,
  puerto >
```

Por ejemplo:

```
Cliente:
buscar("calculadora")

Directorio:
192.168.1.10 : 4500
```

Después de conocer esta información, el cliente puede iniciar la llamada RPC.

---

## Flujo del directorio

La idea puede representarse como:

```
          REGISTRO

Servidor
   |
   | nombre + dirección + puerto
   v
Directorio


          BÚSQUEDA

Cliente
   |
   | nombre del servicio
   v
Directorio
   |
   | dirección + puerto
   v
Cliente
   |
   | RPC
   v
Servidor
```

Este esquema separa tres responsabilidades:

```
Servidor:
ofrece y registra el servicio

Directorio:
mantiene la asociación nombre-localización

Cliente:
busca y utiliza el servicio
```

---

## Portmapper

Otro mecanismo presentado en el material es el **portmapper**.

El portmapper es especialmente útil cuando el cliente ya conoce el servidor, pero necesita saber en qué puerto se encuentra un determinado servicio.

### Problema:

El cliente conoce:

```
Servidor A
```

pero desconoce:

```
¿En qué puerto escucha el programa p?
```

### Solución:

Consulta al portmapper local del servidor.

Por convención, el material indica que el portmapper utiliza el puerto fijo:

```
111
```

  

---

## Registro ante el portmapper

El servicio registra el puerto en el que está escuchando.

Por ejemplo:

```
Programa p
Puerto real = 4345
```

Se registra:

```
Registrar(programa p, 4345)
```

El portmapper almacena:

```
programa p → 4345
```

Mientras tanto, el servicio comienza a escuchar en ese puerto.

---

## Consulta al portmapper

Cuando el cliente desea localizar el servicio:

```
Buscar(programa p)
```

el portmapper responde:

```
4345
```

Entonces el cliente puede comunicarse directamente con el servicio RPC.

```
Cliente
   |
   | 1. consultar puerto 111
   v
Portmapper
   |
   | 2. responder 4345
   v
Cliente
   |
   | 3. llamada RPC a puerto 4345
   v
Servicio p
```

---

## Diferencia entre directorio y portmapper

Aunque ambos ayudan a localizar servicios, resuelven problemas ligeramente diferentes.

### Directorio:

Puede resolver una designación completa:

```
nombre del servicio
        ↓
servidor + puerto
```

### Portmapper:

Normalmente ya se conoce el servidor.

Solo se necesita resolver:

```
programa
    ↓
puerto dentro de ese servidor
```

Puede resumirse así:

|Mecanismo|Información conocida|Información buscada|
|---|---|---|
|Directorio|Nombre lógico|Servidor y puerto|
|Portmapper|Servidor y programa|Puerto|

## La abstracción central de RPC

La idea puede resumirse mediante dos vistas distintas.

### Lo que ve el programador:

```
resultado = procedimiento(parametros)
```

### Lo que ocurre realmente:

```
procedimiento(parametros)
        |
        v
stub
        |
        v
marshalling
        |
        v
mensaje
        |
        v
red
        |
        v
unmarshalling
        |
        v
skeleton
        |
        v
procedimiento remoto
        |
        v
resultado
        |
        v
marshalling
        |
        v
red
        |
        v
unmarshalling
        |
        v

```

La potencia de RPC surge precisamente de ocultar esta segunda estructura sin eliminarla.

## Importancia de distinguir llamada local y RPC

Aunque RPC intenta parecer una llamada local, no debe olvidarse que existen diferencias esenciales.

Una llamada local:

```
función()
```

normalmente depende de un único entorno de ejecución.

Una llamada remota depende de:

```
cliente
+
stub
+
red
+
servidor
+
skeleton
+
procedimiento
```

Cada elemento puede introducir errores o retrasos.

Por ello:

> **La transparencia de RPC simplifica la programación, pero no elimina la naturaleza distribuida de la ejecución.**

Este principio resulta esencial para razonar correctamente sobre sistemas distribuidos.

# Ideas fundamentales de la clase

**RPC** permite implementar el modelo cliente-servidor utilizando una abstracción semejante a una llamada de procedimiento local. El cliente invoca aparentemente una función ordinaria, aunque el procedimiento real puede ejecutarse en otra máquina.

Una llamada RPC implica como mínimo dos mensajes: uno transporta la solicitud y los parámetros de llamada, y otro devuelve los resultados. Aunque este intercambio queda parcialmente oculto al programador, sigue existiendo físicamente sobre la red.

Los **stubs** y **skeletons** permiten esconder la complejidad de la comunicación. El stub del cliente convierte una llamada local en un mensaje remoto, mientras que el skeleton del servidor recibe ese mensaje, selecciona el procedimiento correspondiente, ejecuta la operación y retransmite sus resultados.

El **marshalling** transforma parámetros y resultados en una representación transmisible, mientras que el **unmarshalling** reconstruye esos valores en el extremo receptor. Estos procesos permiten transportar datos entre espacios de memoria separados y ayudan a tratar diferencias de representación entre máquinas heterogéneas.

Una implementación RPC debe resolver problemas adicionales que no existen de la misma forma en una llamada local: localizar al servidor, transmitir correctamente los parámetros, manejar estructuras complejas, tratar fallas parciales, generar los talones y administrar la inicialización del servidor.

La **designación** identifica un servicio, mientras que el **ligado** establece la asociación entre ese nombre lógico y una ubicación concreta. El ligado puede realizarse de forma estática, en la primera llamada o en cada llamada, dependiendo del nivel de flexibilidad requerido.

Los **servicios de nombres**, directorios y mecanismos como el **portmapper** permiten resolver dinámicamente la localización de los servicios. Un directorio puede traducir un nombre lógico en dirección y puerto, mientras que un portmapper permite localizar el puerto de un servicio dentro de un servidor ya conocido.

Finalmente, aunque RPC intenta proporcionar la ilusión de una llamada local, la red continúa introduciendo incertidumbre. Cliente, servidor y red pueden fallar independientemente, por lo que la semántica de una llamada remota siempre resulta más compleja que la de una llamada realizada dentro de un único proceso.

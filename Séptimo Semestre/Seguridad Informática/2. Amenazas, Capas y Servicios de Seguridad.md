Cada capa del modelo TCP/IP cumple con una función distinta y agrega información para que los datos puedan llegar desde una aplicación en una computadora hasta otra en cualquier otra parte del mundo.

Esta organización es uno de los pilares fundamentales para comprender la ciberseguridad: Un atacante puede actuar sobre una capa particular: aprovechar los campos de los encabezados o atacar alguno de sus protocolos. Por esta razón, todo ataque debe estudiarse desde el conocimiento de cuatro cuestionamientos:

1. ¿En qué capa ocurre?
2. ¿Qué protocolo, sistema o recurso aprovecha?
3. ¿Qué propiedad de seguridad intenta comprometer?
4. ¿Qué mecanismo puede prevenirlo, detectarlo o corregirlo?

Se dice que la seguridad no comienza desde la instalación de una herramienta, sino desde la comprensión de lo que se requiere proteger y las amenazas que existen para ello.

## Los Ataques Dentro del Modelo TCP/IP

El modelo TCP/IP cuenta con 5 capas, cada una con sus propias particularidades:

```
┌──────────────────────────────────────────────────────────┐
│ CAPA DE APLICACIÓN                                       │
│ HTTP, HTTPS, DNS, SMTP, FTP, VoIP                        │
│ Unidad de datos: mensaje                                 │
├──────────────────────────────────────────────────────────┤
│ CAPA DE TRANSPORTE                                       │
│ TCP o UDP                                                │
│ Direcciones: puertos de origen y destino                 │
│ Unidad de datos: segmento TCP o datagrama UDP            │
├──────────────────────────────────────────────────────────┤
│ CAPA DE RED                                              │
│ IP                                                       │
│ Direcciones: IP de origen y destino                      │
│ Unidad de datos: datagrama o paquete IP                  │
├──────────────────────────────────────────────────────────┤
│ CAPA DE ENLACE                                           │
│ Ethernet o Wi-Fi                                         │
│ Direcciones: MAC de origen y destino                     │
│ Unidad de datos: trama                                   │
├──────────────────────────────────────────────────────────┤
│ CAPA FÍSICA                                              │
│ Cable, fibra óptica y ondas de radio                     │
│ Unidad de datos: bits representados mediante señales     │
└──────────────────────────────────────────────────────────┘
```

Cada ataque puede ser clasificado de acuerdo con la capa en la que actúa, aunque algunos pueden afectar a varias de manera simultánea:

| Capa       | Ejemplos de ataques o amenazas                                 |
| ---------- | -------------------------------------------------------------- |
| Aplicación | Phishing, malware, SQL injection, DNS spoofing y sitios falsos |
| Transporte | SYN flood, escaneo de puertos e inundaciones TCP o UDP         |
| Red        | IP spoofing, manipulación de rutas y ataques de fragmentación  |
| Enlace     | MAC spoofing, ARP spoofing e interceptación en una red local   |
| Física     | Corte de cables, interferencia, robo o destrucción de equipos  |

Ahora bien, la capa en donde se observa el ataque no siempre es coincidente con el objetivo final. Por ejemplo, el phishing se da principalmente en la capa de aplicación y consiste en la explotación de una vulnerabilidad humana, pero tiene como objetivo la obtención de acceso a servidores, cuentas, bases de datos e incluso redes completas.

## Protocolos de Aplicación y sus Puertos

Un **protocolo** se define como un conjunto de reglas que permiten acordar la construcción, envío e interpretación de mensajes enviados a través de la red:

### - HTTP y HTTPS:

- **HTTP:** Se utiliza para solicitar y enviar contenido web. Tradicionalmente un servidor HTTP escucha en el puerto *TCP 80*.
- **HTTPS:** Es una comunicación HTTP protegida a través de *TLS*. Suele utilizar el puerto *TCP 443*.

A su vez, TLS puede proporcionar servicios de confidencialidad (cifra la información), integridad (detecta modificaciones) y autenticación (comprueba la identidad del servidor).

De manera particular, HTTPS no es un protocolo simple para transmisión de contenido, sino que puede definirse como un HTTP transmitido dentro de un canal protegido mediante criptografía.

## - DNS:

Traduce las direcciones en lenguaje natural a direcciones IP:

```
www.udlap.mx ──consulta DNS──► dirección IP del servidor
```

Sin DNS, tendrían que recordarse todas las IP para cada sitio. Este utiliza el *puerto 53*. Además, puede hacer uso de UDP para muchas consultas ordinarias y TCP en casos que requieran respuestas grandes, transferencias de zona y otras operaciones específicas.

### - SMTP:

Este se utiliza principalmente en el envío de correos electrónicos y suele usar el puerto *TCP 25* para la comunicación entre los servidores de correo. Para efectuar envíos autenticados desde un cliente, suele usarse el puerto *587*.

### - FTP:

Es un protocolo clásico de transferencia de archivos. 

Tiene una conexión de control que utiliza el puerto *TCP 21*, así como una conexión de datos que toma el *20*.

Algo a destacar es que este protocolo no cifra nativamente las credenciales ni los archivos, ni funciona igual que SFTP (SSH).

### - TFTP:

Es un protocolo sencillo de transferencia de archivos que con regularidad utiliza el puerto *UDP 69*. Tiene menos funciones que FTP y no cuenta con autenticación ni cifrado. Es significativamente menos moderno que FTP.

### - VoIP:

Significa literalmente transmisión de voz mediante redes IP. No es un solo protocolo y por ello, no cuenta con un solo puerto universal, sino que puede hacer uso de distintos protocolos para establecer llamadas y transportar el audio.

## Puertos

Una dirección IP permite identificar un dispositivo o una interfaz de red. Sin embargo, al poder una computadora ejecutar un gran número de programas simultáneamente, el sistema operativo necesita saber a cuál entregar los datos. Este es el objetivo del número de puerto.

Retomando la analogía del capítulo previo:

```
Dirección IP = dirección de un edificio
Puerto       = número de departamento
Aplicación   = persona que ocupa el departamento
```

Por su parte, una comunicación TCP puede contener:

```
IP de origen:       192.168.1.20
Puerto de origen:   51842

IP de destino:      203.0.113.50
Puerto de destino:  443
Protocolo:          TCP
```

Aquí, el puerto origen de un cliente puede ser uno temporal seleccionado por el sistema operativo, mientras que el de destino suele corresponderse con el servicio solicitado.

En caso de los encabezados de TCP y UDP, se reservan 16 bits para cada número de puerto; existiendo $2^{16}$ valores posibles:

```
Cantidad de puertos posibles = 65 536
Puerto máximo                = 65 535
```

## Encapsulación de la Información

Cuando una aplicación produce información, las capas inferiores van añadiendo encabezados al momento que entran en contacto con el recurso. 

Asúmase que se escriben las credenciales de un usuario en el portal de su banco; la aplicación genera un mensaje y procede a encapsular:

```
Capa de aplicación:
[ DATOS ]

Capa de transporte:
[ ENCABEZADO TCP | DATOS ]

Capa de red:
[ ENCABEZADO IP | ENCABEZADO TCP | DATOS ]

Capa de enlace:
[ ENCABEZADO ETHERNET | PAQUETE IP | TRÁILER ]

Capa física:
010010101101... representados mediante señales
```

Dentro del encabezado TCP se encuentran campos como:

- Puerto de origen.
- Puerto de destino.
- Número de secuencia.
- Número de confirmación.
- Barreras como SYN, ACK, RST y FIN.
- Tamaño de la ventana de recepción.
- Checksum.

En el header IP, por su parte:

- IP de origen.
- IP de destino.
- Información relacionada con la fragmentación.
- Límite de saltos.
- Identificación del protocolo transportado.

En el frame Ethernet:

- Dirección MAC de origen.
- Dirección MAC de destino.
- Identificación del protocolo transportado.
- Código para detectar errores.

La capa física no incluye un encabezado ya que su función se limita a la representación de los bits mediante señales eléctricas, luminosas o de radio.

## Segmentación, Fragmentación y Offset

### - Segmentación por TCP:

El TCP primeramente divide un flujo de datos en **segmentos** y utiliza números secuenciales para así indicar la posición de la información, ya que los segmentos no necesariamente recorren el mismo camino, ni tampoco llegan en el mismo orden de envío:

```
Orden de envío:
segmento 1 → segmento 2 → segmento 3

Orden de llegada:
segmento 2 → segmento 1 → segmento 3

Orden entregado a la aplicación:
segmento 1 → segmento 2 → segmento 3
```

De manera particular, gracias a los segmentos es posible:

- Colocar la información en el orden correcto.
- Identificar datos faltantes.
- Reconocer datos duplicados.
- Solicitar o realizar retransmisiones.

### - Fragmentación de un datagrama IP:

Un **datagrama IP** puede llegar a ser demasiado grande para lograr pasar a través de los escenarios necesarios. En IPv4, puede optar por dividirse en fragmentos, cada uno conteniendo información que permite determinar:

- A qué datagrama original pertenece.
- Qué posición ocupa. 
- Si todavía existen más fragmentos.

Por ejemplo, el **fragment offset** se encarga de indicar la posición relativa del fragmento dentro del datagrama original:

```
Números de secuencia TCP
→ ordenan el flujo transportado por TCP.

Fragment offset de IPv4
→ ayuda a reensamblar los fragmentos de un datagrama IP.
```

El offset entonces, no reorganiza los datagramas, sino que simplemente participa en el reensamblado de los fragmentos pertenecientes a un mismo datagrama.

## TCP como Protocolo Orientado a Conexión

El protocolo TCP se denomina como orientado a conexión debido a que, previo al intercambio de datos, suele establecer una conexión lógica entre los extremos. Esto se logra logrando que cada uno de los equipos mantenga en su memoria la información sobre el estado de comunicación entre ambos. 

### - Three-way handshake:

La apertura de una conexión TCP suele realizarse mediante tres mensajes:

```
Cliente A                                      Servidor B

   ─────────────── SYN ─────────────────────────►
       “Quiero iniciar una conexión”

   ◄────────── SYN + ACK ───────────────────────
       “Recibí tu solicitud y también estoy listo”

   ─────────────── ACK ─────────────────────────►
       “Confirmo tu respuesta”

                 CONEXIÓN ESTABLECIDA
```

A este intercambio se le conoce como **three-way handshake**.

### - Banderas TCP:

Para lograr establecer la comunicación adecuadamente, se hace uso de una serie de banderas de estado:

- **SYN:** Inicia la conexión y sincroniza los números de secuencia.
- **ACK:** Indica que el campo de confirmación es válido.
- **FIN:** Solicita cerrar ordenadamente una dirección de la conexión.
- **RST:** Reinicia o rechaza inmediatamente una conexión.
- **URG:** Indica que existen datos marcados como urgentes.
- **PSH:** Solicita que los datos sean entreCliente A                                      Servidor B

Tras haber efectuado el handshake, comienza el intercambio de los datos:

```
A ───────────── DATA ─────────────► B
A ◄───────────── ACK ────────────── B

A ◄──────────── DATA ────────────── B
A ────────────── ACK ─────────────► B
```

En donde TCP hace uso de confirmaciones acumulativas; una bandera *ACK* puede indicar la correcta recepción de todos los bytes anteriores a cierto número y que el receptor se encuentra esperando el siguiente.

---

## Conexiones Semiabiertas

Tras haber recibido un SYN, el servidor responde con SYN + ACK, reservando temporalmente recursos para la conexión.

En caso de que nunca se reciba el ACK final, la conexión se denomina (temporalmente) como **half-open**.

```
Cliente o atacante                              Servidor

   ───────────── SYN ────────────────────────────►
   ◄────────── SYN + ACK ─────────────────────────

   El ACK final nunca llega.
   El servidor conserva temporalmente el estado.
```

Esta falla puede aparecer por un ataque o una falla legítima como la pérdida de conexión a internet durante la transmisión del último ACK.

En forma de ataque, esto se logra enviando una cantidad gigantesca de conexiones incompletas.

---

## SYN flood

Ahora bien, el **SYN flood** es una de las formas de denegación de servicio, y abusa del proceso de apertura de TCP. El ataque consiste en el envío de numerosos SYN, pero sin llegar a completar el handshake:

```
             SYN ─────►
Atacante     SYN ─────►
             SYN ─────►  Servidor
             SYN ─────►  [muchas conexiones pendientes]
             SYN ─────►
```

El servidor responde predeterminadamente con SYN + ACK, manteniendo temporalmente información sobre cada una de las conexiones. Sin embargo, si la cantidad de solicitudes alcanza un número suficientemente grande, el servidor se queda sin espacio en memoria o capacidad para atender conexiones legítimas.

El objetivo principal se encuentra en comprometer la *disponibilidad*.

Entre las defensas posibles pueden encontrarse:

- SYN cookies.
- Límites de solicitudes.
- Reducción del tiempo de espera.
- Filtrado de direcciones falsificadas.
- Firewalls e IPS.
- Balanceadores de carga.
- Servicios de mitigación DDoS.

## DoS y DDoS

### DoS

DoS significa _Denial of Service_ o denegación de servicio. Busca impedir que los usuarios legítimos accedan a un sistema, aplicación o red.

```
Una fuente atacante ─────────► servidor víctima
```

Un DoS no tiene que utilizar TCP. Puede buscar consumir:

- Ancho de banda.
- Memoria.
- Procesador.
- Espacio de almacenamiento.
- Conexiones disponibles.
- Recursos de una aplicación.
- Capacidad de un firewall o router.

### DDoS

DDoS significa _Distributed Denial of Service_. En este caso, el ataque proviene de numerosas máquinas distribuidas:

```
Equipo comprometido 1 ─┐
Equipo comprometido 2 ─┤
Equipo comprometido 3 ─┼────► servidor víctima
Equipo comprometido 4 ─┤
Equipo comprometido 5 ─┘
```

Estas máquinas pueden pertenecer a una botnet. Al proceder el tráfico de numerosos lugares, bloquearlo resulta más complicado. Una regla demasiado agresiva también podría bloquear usuarios legítimos.

La diferencia fundamental es:

```
DoS  = una o pocas fuentes atacantes
DDoS = muchas fuentes distribuidas
```

Un ataque también puede abusar de conexiones TCP completas. En ese caso, el atacante termina el handshake y después envía solicitudes que consumen muchos recursos.

Por tanto, debemos distinguir:

- **Half-open attack:** deja numerosas conexiones pendientes.
- **Full-open attack:** establece las conexiones y después abusa del servicio.

## UDP y las Inundaciones de Tráfico

UDP, a diferencia de TCP, es un protocolo no orientado a conexión, motivo por el que no realiza el three-way handshake de TCP:

```
Emisor ───────── datagrama UDP ─────────► receptor
```

Y de igual manera, es incapaz de garantizar la llegada en orden, no duplicada y completa del datagrama. Esta carga reducida es, entonces, lo que le permite mantener una latencia mínima, característica que lo convierte en un protocolo ideal para aplicaciones sensibles al tiempo: voz, video, juegos y muchas consultas DNS.

Sin embargo, al ser tan abierto en contraste con TCP, es sumamente fácil de inundar, particularmente porque el emisor no necesita establecer una conexión previa.

En este caso, un UDP flood puede afectar:

- Ancho de banda de la víctima.
- Capacidad de procesamiento.
- Recursos del firewall.
- Los recursos de una aplicación UDP.

Si bien, esto no convierte a UDP en un sistema naturalmente inseguro, implica que ofrece una menor confiabilidad que TCP y que la aplicación debe implementar cualquier propiedad adicional que llegue a requerir.

## Checksum y Detección de Errores

Con regularidad los datos suelen corromperse durante el proceso de transmisión debido a factores como ruido, fallas del medio o problemas de hardware. TCP, UDP e IP entonces, utilizan **checksums** para detectar dichos errores.

El procedimiento consiste en:

```
Emisor:
datos ──cálculo──► checksum

Transmisión:
[ datos | checksum ]

Receptor:
datos recibidos ──mismo cálculo──► resultado
```

Si el resultado calculado por el receptor no coincide con el valor recibido, se detecta la alteración. Sin embargo, un checksum convencional tiene un enfoque para detectar puramente errores accidentales, no ofreciendo una protección suficiente frente a atacantes, quienes podrían modificar los datos y garantizar un checksum correcto.

Por su parte, el handshake TCP no supone un mecanismo para la detección de errores en los bits, dado que su propósito es establecer la conexión y sincronizar el estado de los extremos. Por este motivo, implementa:

- Checksum para detectar alteraciones accidentales.
- Números de secuencia para ordenar la información.
- ACK para confirmar recepción.
- Temporizadores para reconocer posibles pérdidas.
- Retransmisiones para recuperar información no recibida.

---

## CRC

Por sus siglas, el **Cyclic Redundancy Check** es una comprobación utilizada por Ethernet para detectar errores dentro de un frame.

El CRC-32 produce un valor de 32 bits tal y como lo indica en su nombre, y es un mecanismo sumamente útil para detectar errores accidentales aun sin ser una función hash criptográfica. Desafortunadamente, un atacante que modifica los datos también es capaz de recalcular un CRC válido para el resultado comprometido.

La diferencia central entre el CRC y el checksum convencionales con los hashes criptográficos, es el hecho de que estos primeros detectan principalmente los errores accidentales, mientras que el otro está específicamente diseñado para resistir manipulaciones intencionales. Por su parte, el HMAC o firma digital son mecanismos que permiten verificar la integridad y la autenticidad.


---

## Corrección de Errores Backward y Forward

La detección de errores no se basa necesariamente en la corrección de los mismos. Existen dos enfoques generales:

### - Backward Error Correction:

Consiste en solicitar o realizar una retransmisión cuando la información no llega a su destino correctamente. Es también conocida como *ARQ*:

```
Emisor ───────── datos dañados ─────────► receptor
Emisor ◄──────── NACK o falta de ACK ─── receptor
Emisor ───────── retransmisión ─────────► receptor
```

*NACK* significa literalmente una confirmación negativa; sin embargo, TCP normalmente se basa en ACK, ACK duplicados, temporizadores y retransmisiones, no en un NACK general con ese nombre.

### - Forward Error Correction:

Bajo este enfoque, el emisor añade una cantidad de bits redundantes suficiente para que el receptor logre corregir los errores sin tener que recurrir a una retransmisión:

```
Datos originales + redundancia ─────────► receptor
                                             │
                                      corrige el error
```

Este método resulta de utilidad en casos donde una retransmisión puede ser sumamente compleja o directamente imposible; por ejemplo:

- Comunicaciones satelitales.
- Transmisiones en tiempo real.
- Señales inalámbricas con pérdidas.
- Sistemas en donde el emisor no puede repetir la información.

---

## Hashes Criptogrpaficos

Una **función hash criptográfica** recibe información de cualquier tamaño, produciendo un resumen de tamaño fijo:

```
Mensaje de cualquier tamaño
             │
             ▼
          SHA-256
             │
             ▼
Resumen de 256 bits
```

A este resultado se le conoce como:

- Hash.
- Digest.
- Resumen.
- Huella digital.

Cualquier cambio en el mensaje producirá modificaciones significativas en el resultado:

```
“Transferir $100” → hash A
“Transferir $900” → hash completamente diferente
```

En el caso particular de *SHA-256*, este genera un resumen de 256 bits y a diferencia de CRC-32, está diseñado para resistir ataques deliberados, pudiendo detectarlos además de los errores accidentales. Sin embargo, para utilizarlo no basta con enviar simplemente el mensaje y el hash, ya que este podría ser recalculado por un atacante; debe utilizarse además una clave secreta o firma digital.

---
## HMAC y Firmas Digitales

### - Código de autenticación de mensajes:

Un **MAC criptográfico** como **HMAC** consiste en embeber los datos con una clave secreta. Solo quienes la conocen pueden generar correctamente el código, permitiendo comprobar:

- Los datos no fueron modificados.
- Los datos fueron producidos por una entidad que conoce la clave.

### - Firma digital:

Para generar una **firma digital**, un emisor hace uso de su clave privada; primero calcula el hash del mensaje y posteriormente se aplica la operación de firma:

```
Mensaje ──► SHA-256 ──► resumen
                           │
                    clave privada
                           │
                           ▼
                         firma
```

El receptor entonces, utiliza la clave pública correspondiente para verificar que sea correcta. 

De manera particular, el hash se considera un resumen compacto, mientras que la firma es un valor criptográfico que relaciona el mensaje con la clave privada del firmante.

## Ataques

### - Spoofing:

_Spoofing_ significa falsificación o suplantación. El atacante intenta que determinada información parezca provenir de una fuente distinta.

#### DNS spoofing

En DNS spoofing, la víctima recibe una respuesta DNS falsa o manipulada.

```
Víctima:
“¿Cuál es la dirección de banco.example?”

Respuesta legítima:
203.0.113.10

Respuesta falsificada:
198.51.100.66  ← servidor controlado por el atacante
```

La víctima puede escribir correctamente el dominio y aun así ser dirigida hacia otro servidor.

#### IP spoofing

En IP spoofing, el atacante coloca una dirección de origen falsa en el encabezado IP.

Es parecido a enviar una carta escribiendo en el sobre la dirección de otra persona.

Esto no significa automáticamente que el atacante pueda recibir la respuesta. Por ello se utiliza principalmente cuando:

- No necesita recibir una respuesta.
- Busca ocultar el origen.
- Participa en un ataque de reflexión.
- Intenta engañar algún filtro basado únicamente en direcciones.

Completar una conexión TCP convencional con una dirección falsa es más difícil, porque la respuesta SYN+ACK se dirige hacia la dirección suplantada.

#### MAC spoofing

En MAC spoofing, un dispositivo utiliza una dirección MAC diferente de la que normalmente tiene asignada.

#### ARP spoofing

ARP relaciona direcciones IP con direcciones MAC dentro de una red local. En ARP spoofing, el atacante envía información falsa para conseguir que otros dispositivos asocien su dirección MAC con la IP de otro equipo, como el router.

Esto puede permitirle interceptar o redirigir tráfico dentro de la red local.

### - Eavesdropping y alteración de datos:

#### Eavesdropping

_Eavesdropping_ significa escucha clandestina. Un atacante observa una comunicación sin autorización.

Si la comunicación no está cifrada, podría obtener:

- Contraseñas.
- Correos.
- Archivos.
- Consultas DNS.
- Información personal.
- Datos sobre los sistemas utilizados.

Es principalmente un ataque pasivo contra la confidencialidad.

#### Data alteration

La alteración de datos ocurre cuando alguien modifica información sin autorización.

Ejemplos:

- Cambiar el monto de una transferencia.
- Modificar una calificación.
- Alterar una dirección de entrega.
- Manipular un archivo descargado.
- Modificar una respuesta DNS.

La propiedad afectada es principalmente la integridad.

### - Phishing e ingeniería social:

Phishing es un engaño diseñado para provocar que la víctima revele información o ejecute una acción.

```
“Detectamos un problema con tu cuenta.
Inicia sesión inmediatamente mediante este enlace.”
```

El enlace puede llevar a una página que imita la apariencia de una organización legítima.

#### Variantes del phishing

- **Spear phishing:** ataque dirigido a una persona u organización específica.
- **Smishing:** phishing mediante SMS o mensajes de texto.
- **Vishing:** engaño mediante llamadas o mensajes de voz.
- **Pretexting:** construcción de una historia o identidad falsa para obtener la confianza de la víctima.

El término correcto es **spear phishing**, no “spare phishing”.

La ingeniería social explota características humanas como:

- Urgencia.
- Miedo.
- Autoridad.
- Curiosidad.
- Confianza.
- Deseo de ayudar.
- Promesas de premios.

Ejemplo:

```
Atacante:
“Soy del área de sistemas. Necesito tu código de
autenticación para reparar tu cuenta.”

Víctima:
Entrega un código válido.

Resultado:
El atacante evita los controles técnicos manipulando
a la persona.
```

### - Pharming:

Pharming consiste en redirigir automáticamente a los usuarios hacia un sitio falso. Esto puede conseguirse manipulando DNS o el archivo local de nombres del dispositivo.

La diferencia con phishing es:

```
Phishing
→ convence a la víctima para abrir un enlace o entregar datos.

Pharming
→ altera la resolución para redirigirla automáticamente.
```

En ambos casos, la víctima puede terminar en un sitio falso, pero el mecanismo utilizado es diferente.

### - Malware:

Malware significa software malicioso. Es una categoría general que incluye diferentes tipos de programas.

#### Ransomware

Cifra o bloquea la información y exige un pago para recuperarla.

#### Gusano

Se propaga automáticamente entre sistemas o redes, normalmente aprovechando vulnerabilidades.

#### Troyano

Aparenta ser un programa legítimo, pero ejecuta acciones maliciosas.

#### Backdoor

Crea un acceso oculto que evita el procedimiento normal de autenticación.

#### Spyware

Recopila información sobre el usuario y la envía a otra entidad sin autorización adecuada.

#### Bot

Convierte un dispositivo en una máquina que puede ser controlada remotamente.

#### Botnet

Es una red de numerosos dispositivos comprometidos y controlados por un operador. Puede utilizarse para DDoS, envío de spam, robo de información o distribución de malware.

#### Cryptojacking

Utiliza los recursos de procesamiento de la víctima para minar criptomonedas sin autorización.

#### Drive-by attack

Un _drive-by attack_ intenta descargar o ejecutar contenido malicioso cuando el usuario visita un sitio comprometido.

El término correcto es **drive-by attack**, no “device by attack”.


### - Ping of Death:

Este es un ataque histórico que enviaba paquetes IP o ICMP malformados o fragmentados de manera que, al reensamblarse, superaban el tamaño permitido, bloqueando los sistemas de inmediato.

Este proceso no implica enviar una gran cantidad de pings (lo que sería una inundación ICMP), sino que se vale del uso de paquetes inválidos, fragmentación y errores en el reensamblado.

Los sistemas modernos suelen encontrarse bastante protegidos contra la versión clásica de este ataque.

## Vulnerabilidades Zero-Day


Una **vulnerabilidad zero-day** es una falla que se explota previo a que exista una corrección disponible o antes de que se tenga el tiempo para responder al ataque.

Un detector basado en firmas suele fallar dado que aun no existen firmas conocidas para el nuevo ataque; motivo por el que se combinan distintas técnicas:

- FIrmas.
- Detección de anomalías.
- Análisis de comportamiento.
- Aislamiento.
- Mínimos privilegios.
- Actualizaciones.
- Monitoreo.
- Segmentación de redes.

Esta clase de vulnerabilidades no son una forma de ingeniería social, sino una condición relacionada con una vulnerabilidad desconocida o no corregida.

## Ciberseguridad y Seguridad de la Información

### - Ciberseguridad:

La **ciberseguridad** se encarga en la protección de un ecosistema sumamente amplio:

```
Dispositivos + redes + aplicaciones + identidades
+ infraestructura + servicios + datos
```

Incluye equipos de cómputo, teléfonos, servidores, routers, cuentas, programas, sistemas industriales y servicios digitales.

## Introducción

La **preparación de datos** es la etapa que transforma observaciones imperfectas en entradas numéricas suficientemente confiables para que un modelo de Machine Learning pueda aprender de ellas. Un algoritmo más sofisticado no puede compensar datos mal definidos, inconsistentes o contaminados; si las entradas contienen errores, el modelo puede aprender patrones incorrectos con mucha confianza.

El flujo general de un experimento puede representarse como:

```
Datos crudos X, y
        ↓
Preparar features
        ↓
Dividir observaciones
        ↓
Entrenar modelo
        ↓
Evaluar honestamente
```

La pregunta central de esta etapa es:

> ¿Cómo se convierten observaciones imperfectas en entradas numéricas confiables?

La preparación no consiste solamente en “limpiar” una tabla. También implica decidir **qué puede aprender el modelo**, qué información estaría disponible al momento de realizar una predicción y qué transformaciones deben aprenderse exclusivamente de los datos de entrenamiento. 

---

## La calidad de los datos limita al modelo

Un optimizador puede encontrar parámetros que se ajusten muy bien a los datos proporcionados, pero no puede saber por sí mismo que:

- una fila está duplicada;
- una unidad es incorrecta;
- una etiqueta está mal capturada;
- una variable contiene información del futuro;
- una categoría está escrita de varias formas.

Por ello se utiliza la idea:

> **Garbage in, confident garbage out.**

El problema no es únicamente producir predicciones incorrectas. Un modelo puede obtener métricas aparentemente excelentes mientras está aprendiendo relaciones artificiales.

La responsabilidad durante la preparación consiste en procurar que cada columna sea:

- significativa;
- comparable;
- válida;
- disponible al momento real de la predicción.



---

## Auditoría inicial de los datos

Antes de modificar una tabla conviene **identificar los problemas existentes sin intentar corregirlos todavía**.

Considérese:

|id|city|age|spend|plan|churn|
|---|---|---|---|---|---|
|101|Puebla|24|499|Basic|0|
|102|puebla|—|1,299|premium|1|
|103|CDMX|240|799|Premium|0|
|103|CDMX|240|799|Premium|0|
|104|Puebla|31|$699 MXN|Basic|1|
|105|Toluca|45|12,999|—|0|

En una tabla tan pequeña ya aparecen varios problemas:

- valores faltantes;
- texto inconsistente;
- una edad imposible;
- una fila duplicada;
- formatos numéricos mezclados;
- un gasto extremadamente alto.

La inspección previa evita aplicar transformaciones automáticas sin comprender primero qué significan los datos. 

---

## Función de las columnas

No todas las columnas cumplen el mismo propósito.

Una observación puede dividirse conceptualmente en:

```
ID | Features X | Target y
```

En el ejemplo:

- `id` identifica al cliente.
- `age`, `spend`, `city` y `plan` son posibles features.
- `churn` es el target que se desea aprender.

### Identificador:

Un identificador sirve para distinguir observaciones, pero normalmente **no representa una característica predictiva útil**.

Por ejemplo:

```
cliente 101
cliente 102
cliente 103
```

Los números no significan que el cliente 103 sea “más grande” o “más importante” que el 101.

### Features:

Las **features $X$** son los valores que estarán disponibles antes de producir la predicción.

### Target:

El **target $y$** representa aquello que se quiere predecir.

La distinción es fundamental porque utilizar información del target dentro de las features puede generar **leakage**. 

---

## Inspección inicial con Pandas

Un conjunto reducido de operaciones permite descubrir muchos problemas antes de comenzar la preparación:

```
df.shapedf.head()df.info()df.describe(include="all").Tdf.isna().sum()df.nunique()df.duplicated().sum()
```

Estas instrucciones permiten revisar:

- dimensiones;
- primeras observaciones;
- tipos de datos;
- estadísticas descriptivas;
- valores faltantes;
- cantidad de valores únicos;
- duplicados.

Sin embargo, los resultados técnicos no sustituyen la interpretación.

Para cada columna debe preguntarse:

- ¿Qué mide?
- ¿Qué tipo debería tener?
- ¿Qué valores son plausibles?
- ¿Cuándo estará disponible?

No debe confiarse únicamente en `dtype`. Una variable almacenada como número puede ser categórica y una cadena de texto puede contener una medición numérica. 

---

## Dimensiones de la calidad de datos

Una tabla puede estar “limpia” desde el punto de vista sintáctico y aun así ser un mal dataset de entrenamiento.

La calidad involucra diferentes dimensiones:

|Propiedad|Significado|
|---|---|
|**Complete**|existen los valores necesarios|
|**Valid**|los valores cumplen reglas del dominio|
|**Consistent**|el mismo concepto mantiene el mismo significado|
|**Unique**|no existen repeticiones indebidas|
|**Available**|la información existe al momento de predecir|
|**Representative**|los datos representan el contexto de uso|

Por ejemplo, eliminar todos los valores faltantes no garantiza:

- etiquetas correctas;
- muestra representativa;
- ausencia de leakage.

Por ello, **data quality es un concepto más amplio que ausencia de `NaN`**. 

---

## Valores faltantes

### Significado de un valor faltante:

Un valor faltante no significa automáticamente cero.

Puede representar:

- una medición que nunca se realizó;
- una característica no aplicable;
- un fallo del sistema;
- una respuesta omitida voluntariamente.

Si se reemplazan todos los faltantes por:

```
0
```

se está inventando una medición que puede tener un significado completamente diferente.

Por ejemplo:

```
ingresos = 0
```

no necesariamente significa lo mismo que:

```
ingresos = desconocidos
```



---

### Estrategias para valores faltantes:

La estrategia debe seleccionarse según **el significado y el costo de perder información**.

|Estrategia|Útil cuando|Riesgo|
|---|---|---|
|Eliminar filas|pocas observaciones faltan aleatoriamente|perder datos o distorsionar la muestra|
|Eliminar columna|casi toda la columna falta y aporta poco|eliminar señal útil|
|Mediana|variable numérica y posiblemente sesgada|ocultar grupos o incertidumbre|
|Moda|categoría estable|exagerar la categoría dominante|
|`"Unknown"`|la ausencia tiene significado propio|crear una nueva categoría|
|Modelo de imputación|existen relaciones fuertes entre variables|mayor complejidad y riesgo de leakage|

Una regla práctica es comenzar con un **baseline sencillo** y solamente introducir estrategias más complejas si la evaluación demuestra que realmente ayudan. 

---

## Imputación

La **imputación** consiste en sustituir valores faltantes utilizando una regla.

Por ejemplo:

```
from sklearn.impute import SimpleImputerimputer = SimpleImputer(strategy="median")X_train_num = imputer.fit_transform(    X_train[["age", "spend"]])X_test_num = imputer.transform(    X_test[["age", "spend"]])
```

Aquí aparecen dos operaciones diferentes.

### `fit`:

`fit` **aprende información a partir de los datos**.

En este caso calcula las medianas de las columnas usando solamente el conjunto de entrenamiento.

### `transform`:

`transform` aplica posteriormente esas mismas medianas.

Por tanto:

```
TRAIN
↓
fit
↓
aprender medianas

TEST
↓
transform
↓
usar las medianas ya aprendidas
```

No debe ejecutarse `fit` sobre test, porque entonces la distribución del conjunto de prueba influiría en decisiones tomadas durante el entrenamiento. 

---

## Limpieza de categorías

Antes de codificar una variable categórica deben unificarse etiquetas que representan exactamente el mismo concepto.

Por ejemplo:

```
Puebla
puebla
" Puebla "
PUEBLA
```

probablemente deberían representar una sola categoría.

La normalización podría incluir:

```
Eliminar espacios
        ↓
Uniformar mayúsculas/minúsculas
        ↓
Corregir alias conocidos
        ↓
Puebla
```

Esta clase de reglas se considera **limpieza determinista** cuando no aprende estadísticas de la población.

Por ejemplo:

```
city = city.strip().lower()
```

no depende de calcular una media, frecuencia o umbral sobre el dataset.

Por ello, este tipo de reglas puede definirse antes del split.

Sin embargo, cada regla debe documentarse porque una corrección demasiado agresiva podría fusionar categorías que en realidad tienen significados distintos. 

---

## Variables categóricas

Las categorías son **etiquetas**, no cantidades.

Existen principalmente dos tipos.

### Categorías nominales:

No poseen un orden natural.

Por ejemplo:

\[ city\in\{\text{Puebla},\text{CDMX},\text{Toluca}\} \]

No tiene sentido afirmar:

\[ \text{Toluca}>\text{Puebla} \]

ni tampoco que CDMX se encuentre matemáticamente “entre” Puebla y Toluca.

Por ello sería incorrecto codificar:

```
Puebla = 1
CDMX   = 2
Toluca = 3
```

porque se inventaría un orden y distancias que no existen.

Para este caso suele utilizarse **one-hot encoding**.

---

### Categorías ordinales:

Poseen un orden significativo.

Por ejemplo:

\[ plan\in\{\text{Basic},\text{Plus},\text{Premium}\} \]

Aquí sí existe una jerarquía conceptual:

```
Basic < Plus < Premium
```

por lo que podría utilizarse un mapeo explícito ordenado cuando sea apropiado para el problema. 

---

## One-hot encoding

El **one-hot encoding** crea una feature binaria por categoría.

Por ejemplo:

|city|Puebla|CDMX|Toluca|
|---|---|---|---|
|Puebla|1|0|0|
|CDMX|0|1|0|
|Toluca|0|0|1|

Así no se introduce artificialmente ningún orden.

En `scikit-learn` puede utilizarse:

```
OneHotEncoder(handle_unknown="ignore")
```

La opción:

```
handle_unknown="ignore"
```

permite que una categoría nueva durante la predicción no provoque que el modelo falle.

Por ejemplo, si durante entrenamiento solo aparecieron:

```
Puebla
CDMX
Toluca
```

y posteriormente llega:

```
Monterrey
```

el pipeline puede continuar procesando la observación. 

---

## Escalamiento de features

### Problema de escalas diferentes:

Considérense:

```
age   → decenas
spend → miles
```

Si ambas variables entran directamente en ciertos algoritmos, `spend` puede dominar los cálculos simplemente porque utiliza valores numéricamente mayores.

Esto afecta especialmente:

- métodos basados en distancia;
- modelos entrenados mediante gradientes;
- PCA;
- modelos regularizados.

---

### Estandarización:

Una transformación común es:

\[ z=\frac{x-\mu_{train}}{\sigma_{train}} \]

donde:

- $x$ es el valor original;
- $\mu_{train}$ es la media del entrenamiento;
- $\sigma_{train}$ es la desviación estándar del entrenamiento.

Después de estandarizar:

- $z=0$ representa la media de entrenamiento;
- $z=1$ representa una desviación estándar por encima;
- $z=-1$ representa una desviación estándar por debajo.



---

### Ejemplo:

Supóngase:

\[ \mu=50 \]\[ \sigma=10 \]

y:

\[ x=70 \]

Entonces:

\[ z=\frac{70-50}{10} \]\[ z=2 \]

Esto indica que el valor se encuentra **dos desviaciones estándar por encima de la media**.

La información relativa no se pierde; cambia la representación numérica.

Por ello:

> **Standardization changes coordinates, not information.**



---

### ¿Todos los modelos necesitan escalamiento?:

No.

Normalmente es importante para:

- modelos basados en gradientes;
- algoritmos basados en distancia;
- PCA;
- modelos regularizados.

En cambio, suele ser innecesario para:

- árboles de decisión;
- ensembles de árboles.

Esto sucede porque los árboles trabajan principalmente con reglas del tipo:

```
age < 35
```

y no dependen directamente de las magnitudes relativas entre diferentes features.

---

## Outliers

Un **outlier** es una observación que se encuentra lejos del comportamiento típico.

Por ejemplo:

```
spend = 12,999
```

cuando la mayoría de valores se encuentran muy por debajo.

Sin embargo:

> **un outlier no es automáticamente un error.**

Puede representar distintos escenarios.

### Error:

El valor proviene de una captura incorrecta.

En ese caso debería corregirse o eliminarse **si existe evidencia**.

### Caso raro:

La observación es poco frecuente, pero real.

Debe conservarse y quizá utilizar métodos más robustos.

### Distribution shift:

El dato puede indicar que el proceso de recolección o la población está cambiando.

Entonces debe investigarse el origen.

La regla importante es:

> No se elimina una observación únicamente porque sea incómoda para el modelo.

Deben utilizarse conocimiento del dominio, visualización y análisis de sensibilidad. 

---

## Duplicados

Los duplicados modifican el **peso de la evidencia**.

Si un mismo cliente aparece accidentalmente tres veces:

```
cliente A
cliente A
cliente A
```

el modelo recibe indirectamente tres veces más evidencia sobre ese caso.

### Duplicados exactos:

Pueden generarse por:

- exportaciones repetidas;
- errores en joins;
- concatenaciones incorrectas.

Debe revisarse cuál es la clave que define una observación única.

### Repetición legítima:

No todas las filas parecidas son duplicados.

Por ejemplo:

```
cliente A — compra lunes
cliente A — compra martes
cliente A — compra viernes
```

pueden ser tres transacciones reales.

En ese caso deben conservarse características como:

- tiempo;
- identidad de grupo;
- contexto de la observación.



---

## Target leakage

El **target leakage** ocurre cuando una feature contiene directa o indirectamente información que no estaría disponible al momento real de hacer la predicción.

Este problema puede producir modelos con resultados sorprendentemente altos pero completamente inútiles.

### Ejemplo:

Supóngase que se quiere predecir si un cliente abandonará un servicio.

Se utiliza como feature:

```
account_closed_date
```

Pero esa fecha solamente existe **después de que el cliente ya abandonó**.

El flujo sería:

```
Momento de predicción
        ↓
Ocurre churn
        ↓
Se registra account_closed_date
```

Utilizar esa variable durante entrenamiento equivale a mostrarle al modelo una consecuencia del resultado que intenta predecir.

La prueba práctica es:

> **¿Este valor existiría exactamente en el momento en que debe realizarse la predicción?**

Si la respuesta es no, existe un fuerte riesgo de leakage. 

---

## Preprocessing leakage

El leakage también puede aparecer durante el preprocesamiento aunque ninguna columna revele directamente el target.

Considérese este procedimiento:

```
Todos los datos
      ↓
Calcular scaler
      ↓
Split
      ↓
Evaluar
```

Esto es incorrecto porque las medias y desviaciones del conjunto de test influyeron en la transformación.

El procedimiento correcto es:

```
Split
  ↓
Fit preprocessing únicamente en train
  ↓
Transform train
  ↓
Transform test usando lo aprendido
  ↓
Evaluar
```

La regla general es:

> **Cualquier transformación que aprenda de los datos debe hacer `fit` exclusivamente sobre las filas de entrenamiento.**



---

## Qué puede realizarse antes y después del split

No todas las operaciones deben ocurrir en el mismo momento.

### Antes del split:

Pueden aplicarse reglas que **definen o verifican el significado del dataset** sin aprender estadísticas de las observaciones:

- aclarar el target;
- definir el momento de predicción;
- corregir valores imposibles mediante reglas del dominio;
- normalizar formatos de texto deterministas;
- eliminar duplicados de exportación confirmados;
- definir identificadores de fila, grupo o tiempo.

### Después del split:

Las transformaciones que **aprenden algo de los datos** deben ajustarse únicamente sobre training:

- valores de imputación;
- parámetros de escalamiento;
- vocabulario de codificación;
- selección de features;
- umbrales estadísticos para outliers.

Una regla práctica es:

> Si una transformación calcula una estadística, frecuencia, umbral, vocabulario o ranking a partir de las filas, debe pertenecer al pipeline de entrenamiento.



---

## Orden correcto de preparación

El orden protege la validez del experimento.

```
Auditar esquema y significado
            ↓
Aplicar reglas fijas de validez
            ↓
Dividir las observaciones
            ↓
Ajustar preprocessing solo en train
            ↓
Entrenar
            ↓
Evaluar
```

La división tampoco debe tratarse como un simple:

```
70 % train
30 % test
```

La estrategia depende de cómo se generaron los datos.

### Random split:

Útil cuando las filas pueden considerarse independientes.

### Stratified split:

Busca preservar la proporción de clases, especialmente cuando alguna es poco frecuente.

### Group / Time split:

Debe utilizarse cuando existen dependencias entre observaciones pertenecientes al mismo grupo o cuando importa el orden temporal.

Por tanto, **elegir el split forma parte de la definición del problema**. 

---

## Pipelines de preprocessing

Diferentes tipos de features requieren transformaciones diferentes.

Por ejemplo:

```
age, spend
→ numéricas

city, plan
→ categóricas
```

Puede crearse un pipeline numérico:

```
numeric = Pipeline([    ("imputer", SimpleImputer(strategy="median")),    ("scaler", StandardScaler())])
```

y otro categórico:

```
categorical = Pipeline([    ("imputer", SimpleImputer(strategy="most_frequent")),    ("onehot", OneHotEncoder(handle_unknown="ignore"))])
```

Después se combinan mediante:

```
preprocess = ColumnTransformer([
    ("num", numeric, ["age", "spend"]),
    ("cat", categorical, ["city", "plan"])
])
```

Así cada columna recibe las transformaciones adecuadas. 

---

## ColumnTransformer

El propósito de `ColumnTransformer` es convertir el esquema original:

```
age
spend
city
plan
```

en una matriz completamente numérica:

\[ X' \]

mediante diferentes rutas:

```
age, spend
    ↓
imputar
    ↓
escalar
    ┐
    │
    ├──→ X'
    │
city, plan
    ↓
imputar
    ↓
one-hot
```

Una ventaja importante es que **un mismo objeto recuerda toda la receta de preparación**.

De esta manera, entrenamiento y predicciones futuras reciben las mismas transformaciones en el mismo orden. 

---

## Pipeline completo con el modelo

El preprocessing puede conectarse directamente al clasificador:

```
from sklearn.linear_model import LogisticRegressionmodel = Pipeline([    ("prep", preprocess),    ("clf", LogisticRegression(max_iter=500))])
```

Posteriormente:

```
model.fit(X_train, y_train)
```

Durante `fit` se aprenden, utilizando únicamente training:

- valores de imputación;
- escalas;
- categorías;
- parámetros del modelo.

Después:

```
y_pred = model.predict(X_test)
```

reutiliza exactamente esas transformaciones en las nuevas observaciones.

El pipeline reduce la posibilidad de:

- olvidar una transformación;
- utilizar parámetros diferentes;
- hacer accidentalmente `fit` sobre test;
- preparar producción de manera distinta al entrenamiento.



---

## Preparación de datos como decisión de modelado

Cada transformación introduce una **suposición**.

El razonamiento correcto sigue:

```
Problema observado
       ↓
Significado en el dominio
       ↓
Decisión de preparación
       ↓
Impacto sobre el modelo
```

Por ejemplo:

```
age = 240
```

no debería conducir automáticamente a:

```
eliminar fila
```

Primero debe establecerse:

1. por qué el valor es imposible;
2. qué pudo haber ocurrido;
3. qué información se perdería;
4. qué regla se aplicará a futuras observaciones similares.

Por esta razón conviene mantener un **preparation log**.

Para cada cambio deben registrarse:

- problema detectado;
- regla aplicada;
- justificación;
- forma de reproducirla sobre datos futuros.



---

## Principio de reproducibilidad

La preparación aplicada durante el desarrollo también debe poder ejecutarse sobre datos futuros.

No serviría realizar manualmente:

```
"este dato lo cambio porque se ve raro"
```

si posteriormente nadie conoce la regla utilizada.

Una transformación útil debe poder expresarse como una regla reproducible:

```
Entrada nueva
     ↓
Mismas reglas de limpieza
     ↓
Misma imputación aprendida
     ↓
Misma codificación
     ↓
Mismo escalamiento
     ↓
Modelo
```

Por ello los pipelines no solo facilitan el código: ayudan a mantener la **consistencia entre entrenamiento y producción**.

---

## Protección de la evaluación

La evaluación solamente es confiable si el conjunto de test representa información realmente desconocida para el proceso de entrenamiento.

Por ello debe preservarse la secuencia:

```
Auditar
   ↓
Split
   ↓
Fit preprocessing en train
   ↓
Fit modelo en train
   ↓
Transform test
   ↓
Predecir test
   ↓
Evaluar
```

Si test influye en:

- medias;
- medianas;
- escalas;
- categorías;
- selección de features;
- umbrales;

entonces deja de ser completamente desconocido y la evaluación puede volverse artificialmente optimista.

---

## Relación entre los problemas principales de calidad

Los diferentes problemas pueden organizarse conceptualmente así:

|Problema|Pregunta principal|
|---|---|
|Missing|¿por qué falta el dato?|
|Invalid|¿el valor puede existir?|
|Inconsistent|¿dos representaciones significan lo mismo?|
|Duplicate|¿es la misma observación repetida?|
|Outlier|¿es error, caso raro o cambio de distribución?|
|Unrepresentative|¿estos datos representan el escenario de uso?|
|Leakage|¿esta información debería estar disponible al predecir?|

Esta clasificación ayuda a evitar que todas las anomalías reciban el mismo tratamiento.

---

## Flujo completo de Data Preparation

El proceso puede resumirse como:

```
Datos crudos
    ↓
Entender filas y columnas
    ↓
Auditar calidad
    ↓
Corregir reglas deterministas
    ↓
Definir X, y e identificadores
    ↓
Definir momento de predicción
    ↓
Realizar split adecuado
    ↓
TRAIN
 ├── aprender imputación
 ├── aprender escalamiento
 ├── aprender categorías
 └── aprender modelo
    ↓
TEST
 ├── aplicar imputación aprendida
 ├── aplicar escalamiento aprendido
 ├── aplicar encoding aprendido
 └── generar predicciones
    ↓
Evaluación honesta
```

La preparación no termina cuando se divide el dataset. En realidad, el **split marca el punto a partir del cual las transformaciones aprendidas pueden comenzar de manera segura**, porque desde ese momento se conoce exactamente qué filas pertenecen al entrenamiento y cuáles deben permanecer desconocidas. 

# Ideas fundamentales de la clase

La preparación de datos determina qué información puede utilizar realmente un modelo. Un algoritmo avanzado no puede identificar por sí solo que una unidad es incorrecta, una fila está duplicada o una feature contiene información del futuro. Por ello, antes del entrenamiento debe comprenderse el significado de cada columna y la forma en que estará disponible durante una predicción real.

Los valores faltantes, las categorías inconsistentes, los outliers y los duplicados no tienen una solución universal. Cada decisión depende de su significado dentro del dominio. Preparar datos implica formular hipótesis sobre ellos, por lo que cada transformación constituye también una decisión de modelado.

Debe distinguirse entre transformaciones deterministas y transformaciones aprendidas. Reglas fijas como normalizar espacios o corregir un valor imposible mediante conocimiento del dominio pueden definirse antes del split. En cambio, cualquier proceso que aprenda estadísticas, frecuencias, vocabularios o umbrales debe hacer `fit` exclusivamente sobre los datos de entrenamiento.

El **data leakage** ocurre cuando el proceso de entrenamiento recibe información que no debería poseer. Puede aparecer directamente mediante una feature posterior al target o indirectamente al calcular imputaciones y escalas usando también el conjunto de test. La regla fundamental es que test debe permanecer desconocido hasta la evaluación.

Los pipelines permiten expresar de forma reproducible toda la preparación. Mediante `ColumnTransformer` pueden aplicarse transformaciones distintas a variables numéricas y categóricas, y posteriormente conectar el preprocessing directamente con el modelo. Así se garantiza que entrenamiento, evaluación y predicciones futuras utilizan exactamente la misma receta.

En última instancia, una evaluación confiable depende tanto del modelo como de la preparación previa. La secuencia **auditar → aplicar reglas fijas → dividir → ajustar preprocessing en train → entrenar → evaluar** protege el experimento y permite que las métricas representen de manera más realista la capacidad del modelo para generalizar.
